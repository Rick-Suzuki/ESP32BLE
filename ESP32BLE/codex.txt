No files were modified. No build, run, commit, backup, logging, or configuration change was performed.

A. Executive summary

CONFIRMED FROM SOURCE

The iPhone CSS cascade specifies a smaller paragraph/list font than the HTML h2:

• iPhone h2: 1.0625rem
• iPhone paragraph/list text: inherited 0.875rem

Under ordinary CSS layout, the h2 must render larger than the paragraphs. There is no CSS selector conflict that would make paragraphs larger.

INFERENCE

The reported iPhone landscape result is most consistent with iOS WebKit text autosizing/inflation affecting paragraph-like text blocks independently. The stylesheet currently has no text-size-adjust declaration to control that behavior.

RECOMMENDATION

Use one CSS-only, iPhone-scoped controlled change in a future stage:

html.esp-iphone {
	-webkit-text-size-adjust: 100%;
	
	text-size-adjust: 100%;
	
}

Do not simultaneously add paragraph/list font-size overrides. First control WebKit’s apparent autosizing while retaining the already-correct authored hierarchy.

E. CSS inheritance and specificity

CONFIRMED FROM SOURCE

• The iPhone body selector has greater specificity than the base body selector, so its 0.875rem size and 1.5 line height apply.
• The iPhone h2 selector has greater specificity than the base h2 selector, so its 1.0625rem size applies.
• The iPhone paragraph selector changes only margin-bottom. It does not change font-size.
• Paragraph and list-item font sizes inherit from body.
• The iPhone and iPad selectors are independent; one cannot override the other because the HTML root receives only one device-family class.
• Browser default h2 styling can provide weight and other defaults, but not a larger competing font-size after the explicit h2 rules.

G. WebKit text autosizing assessment

WEBKIT-DEPENDENT BEHAVIOR

iOS WebKit can apply text autosizing/inflation to improve readability, particularly for prose-like blocks. Its visible result may differ between a paragraph and a short heading, even when their authored CSS font sizes are ordered correctly.

The current viewport declaration is appropriate and normally reduces unwanted layout scaling, but source inspection alone cannot prove that it prevents all WebKit text autosizing in this embedded landscape WKWebView.

The absence of text-size-adjust means WebKit’s default behavior remains in control.

INFERENCE

The observed result—h2 visibly responding to the iPhone CSS reduction while paragraphs appear disproportionately large—fits paragraph-specific WebKit autosizing more closely than a CSS cascade error.

H. -apple-system-body findings

CSS-STANDARD BEHAVIOR

The base font shorthand is declared before the explicit font-size declaration:

font: -apple-system-body;
font-size: 1rem;

The later font-size declaration supplies the authored size. The iPhone body selector then further overrides it with 0.875rem.

The p elements inherit the resulting body font family and size. The h2 inherits the family but receives its own explicit size.

WEBKIT-DEPENDENT BEHAVIOR

-apple-system-body is an Apple system-font mechanism and may participate in platform typography behavior. However, there is no source evidence that it alone causes the paragraphs to exceed the h2.

Replacing it would change font metrics and is not justified for the first correction.

I. Comparison of correction options

A. iPhone-scoped text-size-adjust: 100%

Expected benefit: Directly targets the most likely cause, while retaining the intended CSS font hierarchy.

Scope: CSS only; iPhone only.

iPad effect: None when scoped to html.esp-iphone.

Accessibility: May reduce WebKit’s automatic readability enlargement. Test normal and large accessibility text settings before accepting it.

Assessment: Preferred first correction.

B. Explicit iPhone p font-size

Expected benefit: None to the authored cascade; p already inherits 0.875rem.

Risk: WebKit could still autosize the paragraph, and list items remain unaddressed.

Assessment: Not recommended as the first correction.

C. Explicit paragraph and list-item font sizes

Expected benefit: More explicit authored values.

Risk: Does not directly address text autosizing and duplicates the existing inheritance model.

Assessment: Not recommended initially.

D. Change root font-size

Expected benefit: Reduces all rem-based elements, including layout padding and list indentation.

Risk: Broad, unnecessary geometry change.

Assessment: Not recommended.

E. Replace -apple-system-body

Expected benefit: Potentially changes metrics.

Risk: Changes the established system typography without evidence that it is the cause.

Assessment: Not recommended.

F. Change the viewport tag

Expected benefit: Could alter overall viewport scaling.

Risk: The current viewport is appropriate; changing it could affect layout and text broadly.

Assessment: Not recommended.

G. Change WKWebView configuration

Expected benefit: No demonstrated relevant configuration exists.

Risk: Broadens scope beyond the stylesheet.

Assessment: Not recommended.

K. Accessibility implications

The proposed setting should be physically tested with the user’s normal and enlarged system text settings. It may intentionally suppress WebKit’s automatic enlargement of prose, so the resulting 0.875rem iPhone text must remain comfortably readable.

Native SwiftUI Help title, native navigation controls, VoiceOver semantics, offline loading, and the existing iPad appearance are unaffected by a CSS-only iPhone-scoped rule.
