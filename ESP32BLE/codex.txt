1. Current Back Delete availability conditions

Main_Screen.swift:5051-5054 disables the active delete.left.fill button when canDeleteSmartEditorBackward is false.

Main_Screen.swift:5095-5126 requires all of these:

• editingSlotIndex is non-nil.
• smartPasteTarget.textView exists.
• The text view is attached to a window.
• The text view is first responder.
• Live UITextView text equals softEditorAccessoryTargetText.
• Live selectedRange is valid for the live UTF-16 text.
• Live selection exactly equals the tracked selection:
   • Command: smartScriptEditingModel.selectionRange.
   • Button: smartButtonPreviewSelectionRange.
• Selection has length, or cursor location is greater than zero.

Main_Screen.swift:5129-5147 makes the symbol gray if disabled and red if enabled.

2. Command deletion sequence

Current Command path:

• Main_Screen.swift:4976-4977 invokes deleteSmartEditorBackward().
• Lines 5026-5039 validate the live target, copy its current selection into smartScriptEditingModel, delete from the model, then write smartActionTextBinding.
• Main_SmartScriptEditingModel.swift:217-237 removes the selected text or one composed character before the cursor, and immediately changes the model selection to the new cursor position.
• smartActionTextBinding at Main_Screen.swift:3718-3733 updates the stored edited-slot text.
• SwiftUI then re-evaluates views.
• SmartScriptTextEditor.updateUIView at Main_SmartEditorTextInputs.swift:48-61 later copies the new model text to the live UITextView and applies the new selection.

Confirmed synchronization defect:

Immediately after Command deletion, the model has the new text and new cursor, but the live UITextView can still have the old text and old cursor until updateUIView runs.

During that interval, canDeleteSmartEditorBackward fails both of these checks:

• Line 5100: live text differs from softEditorAccessoryTargetText.
• Line 5122: live selection differs from smartScriptEditingModel.selectionRange.

This is sufficient to produce the observed red → gray transition.

After updateUIView synchronizes the UITextView, its selection is applied under isApplyingSelectedRange at Main_SmartEditorTextInputs.swift:174-187. That intentionally prevents the delegate from writing another tracked-selection update. Therefore, there may be no subsequent SwiftUI state change to re-evaluate the gray button. Moving the cursor creates a new delegate selection update at lines 163-171, causing a fresh evaluation and restoring red. This exactly matches the reported device behavior.

3. Button deletion sequence

Button path:

• Main_Screen.swift:5040-5041 calls the active UITextView.deleteBackward() directly.
• SmartPreviewTextView.Coordinator.textViewDidChange at Main_SmartEditorTextInputs.swift:302-306 handles the change.
• syncTextAndSelection at lines 542-553 schedules both Button text and smartButtonPreviewSelectionRange updates on the main queue.
• textViewDidChangeSelection at lines 334-342 independently schedules selection updates.

Difference from Command:

• Command changes the model first, then waits for SwiftUI to update UIKit.
• Button changes UIKit first, then waits for coordinator callbacks to update the model.

Button can also have a temporary live/model mismatch, but the coordinator normally schedules both text and selection together in textViewDidChange, so it has a better opportunity to settle correctly. Static inspection cannot prove the final callback ordering for every UIKit deletion event. The same gray-state defect is possible if SwiftUI evaluates after one asynchronous state update but before the corresponding text or selection update.

4. First-responder findings

canDeleteSmartEditorBackward requires textView.isFirstResponder at line 5099.

No source code in deleteSmartEditorBackward() explicitly resigns first responder or restores it. A SwiftUI button interaction may affect responder state at runtime, but source inspection cannot prove that it does in this case.

This condition can cause gray if focus is lost, but it is not needed to explain the confirmed failure: text and selection mismatches alone occur directly in the Command deletion sequence.

5. Forward Delete comparison

Forward Delete is simpler:

• Main_Screen.swift:5002-5005 calls smartScriptEditingModel.deleteForward().
• Its disabled state is only !smartScriptEditingModel.canDeleteForward at lines 5084-5085.
• canDeleteForward in Main_SmartScriptEditingModel.swift:131-134 uses only tracked model text and selection.

Forward Delete does not require live UITextView text equality, first-responder status, or live/tracked selection equality. Consequently, it does not have the same UIKit/SwiftUI synchronization dependency.

It is not a full Command/Button equivalent: its action is Command-model-only, whereas Back Delete’s new helper supports both active Command and Button targets.

6. Most likely root cause

Confirmed source-level cause for Command:

Back Delete availability combines model state from after deletion with UITextView state from before updateUIView synchronization. The equality checks at Main_Screen.swift:5100 and 5122 reject this normal transitional state. updateUIView then fixes UIKit without emitting a new SwiftUI state change, leaving the rendered button gray until a cursor movement generates one.

The first-responder check may contribute on device, but requires runtime observation to establish.

7. Smallest safe correction

Keep deleteSmartEditorBackward() unchanged, including its live target safety validation.

Change only UI availability calculation in canDeleteSmartEditorBackward at Main_Screen.swift:5095:

• Derive text length and selection availability from existing observable editor state:
   • Command: smartScriptEditingModel.scriptText and .selectionRange.
   • Button: smartButtonEditablePreviewTextBinding.wrappedValue and smartButtonPreviewSelectionRange.
• Retain only appropriate active-target existence/attachment/focus checks for display.
• Do not require live UITextView text to equal the model.
• Do not require live UITextView selection to equal the tracked selection for display.
• Continue using selected length greater than zero or cursor location greater than zero.

That separates display availability from the existing immediate action validation, avoiding the known post-delete transition while keeping deletion safe against stale targets.
