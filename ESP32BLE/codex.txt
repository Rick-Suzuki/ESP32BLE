11. Best architectural location for future pre-command authentication gating

Cleanest location:
MacConnectionManager.sendKeyboardTokens(_:)

Reason:
It is the common public send entry point for normal Mac commands before conversion/final send. A future authenticated == true check there could reject normal commands before they become network payloads.

Second useful location:
MacConnectionManager.handleConnectionState(_:) at .ready

Reason:
That is where the TCP connection first becomes ready. A future handshake could begin there, with status/auth state separated so normal command sending is not allowed until the handshake completes.

Conceptual future flow:
NWConnection.State.ready
start authentication handshake
authenticated = true only after success
sendKeyboardTokens(_:) permits normal CMD/TEXT/KEY traffic only when authenticated

16. Behavior when disconnected/reconnecting

If browser fails:
browser.stateUpdateHandler checks .failed and calls restartSearch() unless deliberately stopped.

If connection fails or is cancelled:
handleConnectionState(_:) checks .failed and .cancelled and calls restartSearch() unless deliberately stopped.

If send completion reports an error:
connection.send completion calls restartSearch() unless deliberately stopped.

Manual stop/output mode change:
ContentView.updateTransportStateForOutputMode()
• .none: macConnection.stop(), ble.stop()
• .esp32: macConnection.stop(), ble.startScan()
• .mac: ble.stop(), macConnection.start()

Commands while not ready:
sendKeyboardTokens(_:) checks canSend. If not connected, it returns false. There is no queue for Mac commands while disconnected/connecting.

17. Architectural constraints relevant to future authentication

Current status conflates “TCP connected” with “safe to send commands”:
canSend is true when status == .connected.

A future auth design probably needs a separate authentication state, because .ready currently immediately becomes .connected and canSend immediately becomes true.

There is no receive path in MacConnectionManager visible in the inspected code, so any challenge/response handshake would likely need new receive handling on the ESP side.

Current discovery has no persistent helper identity, because it connects to results.first?.endpoint only.

Current transport is plain TCP, so any future secret-based protocol would need to account for local-network sniffing/replay unless transport security or an authenticated protocol is added later.
