MIDI-012 IMPLEMENTATION REPORT

1. Exact file modified

Production ESPMacHelper:

ESPMacHelper/MIDIOutputService.swift

MacNetworkServer.swift was not modified.

ESP32BLE and the experimental Test Area Helper were not modified.

The existing Xcode UserInterfaceState.xcuserstate modification was already present and was not intentionally changed.


2. Old ownership representation

The previous representation was:

[NoteKey: Set<NoteOwner>]

A Set could record that a client owned a note, but could not represent multiple simultaneous presses from that same client.


3. New ownership representation

The new representation is:

[NoteKey: [NoteOwner: Int]]

NoteKey remains:

note
CoreMIDI channel

NoteOwner remains:

menuTest
networkClient(clientID)

Each owner now has an independent positive active-press count.


4. Note On handling

startNote now:

Submits every accepted Note On through the existing sendMessage function.
Preserves the supplied velocity and channel.
Increments the matching owner’s count only after successful CoreMIDI submission.
No longer suppresses Note On because the note or owner is already active.

No preliminary Note Off is generated.


5. Note Off handling

stopNote now:

Rejects unmatched ownership safely.
Reads only the requesting owner’s count.
Decrements the count by exactly one.
Removes the owner when its count reaches zero.
Sends no CoreMIDI Note Off while another count remains.
Sends one CoreMIDI Note Off when the complete NoteKey becomes unowned.
Removes the empty NoteKey only after successful Note Off submission.

Counts cannot become negative.


6. Same-client overlapping behavior

For one client pressing the same note/channel twice:

First Note On:

Count becomes 1.
CoreMIDI Note On is submitted.

Second Note On:

Count becomes 2.
Another CoreMIDI Note On is submitted.

First release:

Count becomes 1.
No CoreMIDI Note Off is submitted.

Final release:

Count reaches zero.
One CoreMIDI Note Off is submitted.
The NoteKey is removed.

The result is the same regardless of which physical button releases first because both presses intentionally share the same client/note/channel counter.


7. Multi-client behavior

Different clients have separate NoteOwner keys.

For two clients holding the same NoteKey:

Both Note On messages are forwarded to CoreMIDI.
Each client receives its own count.
One client’s Note Off changes only that client’s count.
No final Note Off is sent while the other client still owns the note.
The final owner’s release sends CoreMIDI Note Off.


8. Multichannel compatibility

NoteKey continues to include the CoreMIDI channel.

The same note on channels 1 and 2 remains two independent NoteKeys.

Different notes on the same channel also remain independent.

Network-channel conversion remains in MacNetworkServer and was not changed.


9. Disconnect cleanup

releaseNetworkNotes(for:) now locates every NoteKey with ownership counts for the disconnecting client.

releaseAllPresses removes that client’s entire count for each affected NoteKey.

If other owners remain:

Their counts are preserved.
No CoreMIDI Note Off is sent.

If the disconnected client was the final owner:

One CoreMIDI Note Off is sent.
The empty NoteKey is removed.

No loop emits multiple Note Off events for multiple presses belonging to the same disconnected client.


10. Menu-test compatibility

menuTest remains a distinct NoteOwner.

The menu-test Note On is always forwarded and receives its own count.

If a network client holds the same NoteKey:

Releasing the menu test removes only the menu-test ownership.
No Note Off is sent while the network owner remains.

The existing menu-test timer and controls were not changed.


11. Server shutdown

releaseAllActiveNotes continues to:

Send one Note Off for every active NoteKey.
Clear all ownership state.
Dispose of the existing CoreMIDI endpoint through the unchanged shutdown path.

No second CoreMIDI output mechanism was introduced.


12. Submission failure consistency

A Note On count is added only after sendMessage succeeds.

For the final Note Off, ownership is removed only after sendMessage succeeds.

If final Note Off submission fails, the original ownership remains available for later cleanup rather than being silently discarded.

Nonfinal releases require no CoreMIDI submission and commit their reduced count immediately.

15. Known MIDI limitation

Reference counting guarantees:

Every successful press forwards Note On.
Overlapping presses are counted.
The first release does not prematurely send final Note Off.
The final release sends Note Off.

MIDI Note Off still contains only note and channel. It cannot identify an individual physical button or synthesized voice.

Receiving instruments may retrigger, stack, replace, or release overlapping identical notes differently. This implementation does not attempt synthesizer-specific voice management.
