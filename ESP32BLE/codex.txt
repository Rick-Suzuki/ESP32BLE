ESP-SOFT-001 — Read-only investigation

Two findings are clear:

The right-hand preview supports native iOS text editing and does not explicitly disable Paste. However, the custom clipboard button targets only the action/script field. The reported native Paste failure cannot yet be assigned a confirmed root cause.

Displaying an image filename inside a button is a new capability in the inspected code. Neither the current Soft Editor preview nor the Main Screen button label implements it.

3. Paste findings and likely explanations

Confirmed:
• No canPerformAction override, custom edit-menu suppression or pasteDelegate was found in the active text wrapper.
• The paste override calls the standard UIKit implementation.
• No general character-count limit rejects ordinary pasted text.
• The manual newline limit explicitly exempts paste.
• There is no filename-specific clipboard filter.
• The right-hand preview has no custom long-press recognizer replacing text selection.

The custom clipboard button is different:
• Main_Screen.swift:4924–4925 always calls pasteSmartActionTextFromSystemClipboard.
• Lines 5100–5107 always insert into smartScriptEditingModel and smartActionTextBinding.
• It does not inspect whether the right-hand preview is focused.

Therefore, if the reported failure concerns that clipboard button, its action-only routing is the confirmed explanation.

For the native iOS Paste menu, these remain hypotheses:

A. Hit testing or focus
The clear “x” overlays the preview at Main_Screen.swift:4398–4399. Its label has a 46-by-46 rectangular hit area plus padding at lines 4415–4428. Tapping that area clears the text instead of placing the caret. This occupies a substantial portion of a small iPhone preview.

The decorative preview border also overlays the content without an explicit allowsHitTesting(false). Its actual effect needs runtime inspection.

B. Text/selection synchronization
The wrapper queues binding updates asynchronously, while updateUIView writes binding text and selection back into UIKit at lines 206–220. An intervening update could potentially restore stale text or move the selection. No observed event sequence currently proves this occurs.

C. Content-specific parsing
The combined slot format uses the last “::” as the action/right-text separator at Main_Screen.swift:3767–3773. Pasting text containing “::” can therefore change how the draft is partitioned. This is distinct from ordinary text or photo.jpg failing to paste.

None of these establishes a universal native Paste failure.

5. Text transformations and restrictions

Confirmed behavior:
• Actual CRLF, CR, LF and tab characters become escaped storage sequences.
• displayText converts stored backslash-n and backslash-t back for display: Main_ButtonBehavior.swift:365–368.
• Manual Return is limited to four logical lines: Main_SmartEditorTextInputs.swift:427–446.
• Pasted multiline content is not generally capped at four lines.
• An unfocused preview displays at most four logical lines; editing enables scrolling.
• Ordinary right-hand text is not generally trimmed during commit.
• SF Symbol subtitle text is trimmed during commit: Main_Screen.swift:3825–3830.
• The double-space period correction can also match a pasted “. ” replacement because that branch does not check isHandlingPaste.

There is no explicit emoji rejection. UTF-16 selection ranges are used, so any correction must preserve Unicode-aware range handling.

6. Smallest recommended Paste correction

First distinguish the custom clipboard button from the native menu.

If the custom clipboard button is intended to paste into the currently edited field, the smallest logical change is focus-aware routing using the existing right-hand binding and selection range. It requires no toolbar or geometry change.

If native Paste fails:
• Reproduce it before changing code.
• If hit testing is responsible, correct only the blocking interaction.
• If inserted text is overwritten, correct the text/selection synchronization in SmartPreviewTextView.
• Do not replace the input control, alter fonts or redesign the editor speculatively.

A safe diagnostic sequence is to paste plain “photo.jpg” using the native menu, away from the clear button, then compare with the custom clipboard button. Debugger breakpoints at paste, shouldChangeTextIn, textViewDidChange and updateUIView can distinguish menu failure, rejection, insertion and overwrite without source changes.

10. Recommended image behavior

Use one shared, side-effect-free filename resolver for editor and Main Screen labels.

Recommended rules:
• Match the entire right-hand display text after removing an existing color prefix.
• Trim surrounding whitespace for lookup only.
• Preserve spaces inside filenames.
• Use the existing Settings image extension set.
• Search Documents first, with case-insensitive fallback.
• Require successful image decoding.
• Fall back silently to existing text for missing, unsupported or unreadable images.
• Do not interpret the filename as an internal command.
• Preserve existing widget, SF Symbol and emoji handling.

Render with aspect-fit inside the existing dimensions, clipped to the existing rounded boundary. This preserves the complete image without distortion; unused space retains the existing background.

The same image should appear on the actual Main Screen button when its display mode shows the right-hand content. Otherwise the editor preview would misrepresent the saved button.

11. Important editing ambiguity

The preview is also the text input. Simply replacing its UITextView with an Image would remove the way to edit the filename.

Recommended interaction: show the image when not editing; tapping it enters text editing within the same existing footprint. Keep the text control active while editing so typing or pasting a valid filename does not abruptly remove focus.

This is an interaction decision requiring agreement before implementation.

For “photo.jpg plus other text”, recommend retaining text. Do not extract filename-looking substrings: spaces may belong to the actual filename.

Display-mode behavior for left/right/both/last should also be specified before implementing Main Screen rendering.

12. Platform differences and preservation risks

Both platforms use smartButtonPreview, SmartPreviewTextView and the same storage bindings.

Their surrounding layouts differ:
• iPad uses the floating panel/shell.
• iPhone uses its existing full-screen shell; the source currently selects its experimental shell variant at Main_Screen.swift:25.
• Both shell variants feed the same button panel logic.

Logical fixes can serve both without changing column widths, heights, keyboard placement, spacing, alignment or preview dimensions.

Keep all current font fitting, emoji sizing and SF Symbol sizing untouched. Image recognition must not replace symbols merely because their subtitles mention filenames, or alter multiline text that does not exactly identify an image.
