finished the read-only trace. I’ll summarize the current behavior and recommended architecture without changing or building anything.Findings

• Export single document:
   • Implemented in Set_Screen.swift.
   • prepareSingleFileExport() calls makeSingleFileExportURL().
   • makeSingleFileExportURL() returns selectedDocumentFileURL when the selected file is .txt.
   • If no selected .txt URL is available, it writes only documentEditorText to a temporary .txt file.
   • Current export is only the .txt file.
   • Matching .config.json is not included.
   • ScreenConfig helpers are not used in single-file export.

• Export archive .zip:
   • Implemented in Set_Screen.swift.
   • prepareArchiveExport() uses archiveTextDocumentURLs.
   • archiveTextDocumentURLs is based on availableDocumentURLs.
   • availableDocumentURLs filters only regular .txt files.
   • makeArchiveData(from:) creates zip entries from the passed fileURLs only.
   • Current archive includes all .txt documents.
   • Config files are not included.
   • Images are not included.
   • Sounds are not included.
   • PDFs are not included.
   • document-backgrounds.json is not included unless it somehow appears in the passed text list, which it does not.

• Import:
   • Implemented in Set_Screen.swift.
   • fileImporter allows multiple selection.
   • activeImportContentTypes depends on list mode:
      • files: .data, then code accepts only .txt
      • images: .image
      • sounds: .data, then code checks supported sound extensions
      • pdfs: .pdf
      • all: .data
   • handleImportedSelection() creates a PendingImportSession and calls processPendingImportSession().
   • processPendingImportSession() imports .txt, images, sounds, and PDFs by extension.
   • .config.json is not recognized as a document config file.
   • If a .config.json is selected, it does not match .txt/image/sound/pdf paths and is effectively ignored.
   • If only a .txt exists, it imports normally.
   • There is no pairing logic for Screen.txt plus Screen.config.json.
   • There is no zip import/unarchive path.

• Rename:
   • Implemented in ContentView.swift, renameSelectedDocument(to:).
   • Renames only the selected .txt file using FileManager.moveItem.
   • Moves legacy AppStorage font and grid entries to the new .txt filename.
   • Does not rename the matching .config.json.
   • The old config remains behind as an orphan.
   • The new .txt will get a new/default config through existing refresh/load paths.

• Delete:
   • Implemented in ContentView.swift, deleteDocument(_:).
   • Deletes only the .txt file using FileManager.removeItem.
   • Removes legacy AppStorage font and grid entries.
   • Does not delete the matching .config.json.
   • Matching config remains behind as an orphan.
   • Assets are not deleted.

• Duplicate:
   • Implemented in ContentView.swift, duplicateDocument(_:).
   • Copies only the .txt file using FileManager.copyItem.
   • Writes defaultDocumentFontSize into legacy AppStorage for the duplicate.
   • Copies legacy grid dimensions if present.
   • Does not duplicate the matching .config.json.
   • The duplicate gets a new/default generated config, not a copy of the source config.
   • Assets are not duplicated.

Recommended architecture

• Add a small document package helper, probably in a new DocumentPackage/ScreenDocumentFiles helper file or near ScreenConfig.swift.
• Treat a screen document as:
   • primary file: Screen.txt
   • sidecar config: Screen.config.json
• The UI should continue showing only .txt files as user-managed documents.
• Config files should remain hidden implementation files.
• All document lifecycle operations should go through helper functions:
   • configURL(forDocumentURL:)
   • ensure config exists for txt
   • copy txt plus matching config
   • move txt plus matching config
   • delete txt plus matching config
   • export txt plus matching config
   • import txt plus matching config when both are present
• Rename should move Old.txt to New.txt and Old.config.json to New.config.json when present.
• Delete should remove Screen.txt and Screen.config.json. It should not delete images, sounds, or PDFs.
• Duplicate should copy Screen.txt and copy Screen.config.json to the duplicate config filename. If no config exists, create a default one for the duplicate.
• Import should accept .txt plus optional .config.json, pair by base name, and hide config files from the user workflow.
• Export single document should probably become a small package export, not just a raw .txt, if the file picker can support multiple related files. If it must stay single-file, export a zip containing Screen.txt and Screen.config.json.
• Export archive should include:
   • all .txt documents
   • matching .config.json files for each .txt
   • images
   • sounds
   • PDFs
   • optionally legacy document-backgrounds.json during transition
• Archive import should eventually support unzipping and importing all recognized files, including sidecar configs.

Suggested implementation order

   1. Add helper functions for document sidecar operations:
   • matchingConfigURL(forDocumentURL:)
   • ensureConfigExists(forDocumentURL:)
   • copyDocumentPackage(from:to:)
   • moveDocumentPackage(from:to:)
   • deleteDocumentPackage(at:)
   • documentPackageExportURLs(for:)

   2. Update rename/delete/duplicate first.
   • These are contained in ContentView.swift and give immediate cleanup of orphan configs.

   3. Update import of selected loose files.
   • Recognize .config.json internally.
   • Pair configs with selected .txt files by base name.
   • Ignore config-only imports unless their matching .txt is also selected or already exists.

   4. Update archive export.
   • Include all .txt and matching .config.json.
   • Then add images, sounds, PDFs.
   • Keep document-backgrounds.json temporarily for compatibility.

   5. Decide single-file export behavior.
   • Either keep it as text-only and label it honestly as text export.
   • Or replace it with a package/zip export for one document plus config.

   6. Add archive import/unzip support after export format is stable.

   7. After migration is stable, remove legacy write paths later, not as part of this document-management pass.
