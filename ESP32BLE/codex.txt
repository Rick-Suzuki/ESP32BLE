1. Executive summary

Warning A and Warning B are produced by different synchronous operations:

Warning A:
ESP32BLE/ESP32BLE/Scrns/Main_Screen/Speech Recognition/SR_Support.swift:303

Offending call:

try? audioSession.setCategory(
.playback,

mode: .spokenAudio,

options: [.duckOthers]

)

This is a synchronous AVAudioSession category change. It runs on MainActor and can cause an immediate audio-route reconfiguration when the shared session is already active.

Despite its location in SR_Support.swift, this function does not start or stop speech recognition. It prepares the shared audio session for speech synthesis and sound playback.

Warning B:
ESP32BLE/ESP32BLE/Scrns/Main_Screen/Main_ButtonBehavior.swift:1498

Offending call:

player.prepareToPlay()

Apple documents that prepareToPlay() preloads buffers, acquires audio hardware, and activates the audio session. It is synchronous. The enclosing Task inherits MainActor, so preparation occurs on the main thread.

The warnings are therefore different operations sharing an underlying audio-session ownership problem:

• Several features independently reconfigure the same AVAudioSession.
• Playback setup remains MainActor-isolated.
• Session configuration and player preparation are not centrally serialized.
• Playback can potentially reconfigure a speech-recognition session.
• Playback activation is partly redundant: the code explicitly activates the session and then calls prepareToPlay(), which may activate it again.

Both warnings represent responsiveness risks. Warning A also exposes a potential speech-recognition/playback conflict.

The safest approach is two implementation stages:

1. Move and serialize AVAudioSession configuration and activation away from MainActor while preserving strict ordering.
2. Prepare AVAudioPlayer away from MainActor, returning to MainActor only to update SwiftUI state and begin/store playback.

Simply dispatching individual calls to an arbitrary global queue is not recommended because category changes, activation, deactivation, AVAudioEngine startup, and player preparation must remain ordered.

No source files were modified. No build or runtime testing was performed.

2. Warning A — exact cause

Location:

activateAudioSessionForSpeechPlayback()

2.1 API

The API is:

func setCategory(
_ category: AVAudioSession.Category,

mode: AVAudioSession.Mode,

options: AVAudioSession.CategoryOptions = []

) throws

It synchronously sets the shared audio session to:

Category: playback
Mode: spokenAudio
Options: duckOthers

2.2 Synchronous behavior

setCategory is not async. There is no asynchronous setCategory equivalent in the installed iOS 27 SDK.

Apple documents that changing category or mode while a session is active causes an immediate route change. That reconfiguration can require communication with audio services and hardware.

2.3 Is the session active?

The source does not check whether the session is already active.

It can be active for several reasons:

• A preceding playback operation activated it.
• An AVAudioPlayer prepared or started playback.
• AVSpeechSynthesizer is using the application audio session.
• Speech recognition activated the session as .record.
• Another sound or ambient-sound command remains active.

Therefore, the warning’s “while the audio session is active” condition is reproducible from the source-level design, although the exact active state for a particular runtime warning requires runtime observation.

2.4 Why it runs on the main thread

The project settings are:

SWIFT_VERSION: 5.0
SWIFT_DEFAULT_ACTOR_ISOLATION: MainActor
SWIFT_STRICT_CONCURRENCY: minimal
IPHONEOS_DEPLOYMENT_TARGET: 17.6

MainScreen and its extension methods are MainActor-isolated under the project’s default isolation.

Callers use:

A Task created from a MainActor context inherits that actor. Declaring a function async does not automatically move its synchronous work off MainActor.

The setCategory call occurs before the first suspension inside activateAudioSessionForSpeechPlayback, so it executes synchronously on MainActor.

3.1 API

The API is:

func prepareToPlay() -> Bool

The return value is currently ignored.

3.2 What it does

Apple documents that prepareToPlay:

• Preloads audio buffers.
• Acquires audio hardware needed for playback.
• Activates the audio session.
• Is automatically performed by play() if it was not done explicitly.
• Reduces delay between play() and audible output.

It is therefore more than a memory-only preparation call.

3.3 Activation or deactivation

prepareToPlay activates or ensures activation of the audio session. It does not deactivate it.

The code does not explicitly deactivate the playback session when the sound finishes.

stopMainGridSoundPlayback only does:

soundEffectPlayer?.stop()
soundEffectPlayer = nil

Main_ButtonBehavior.swift:1508-1511

3.4 Synchronous operation

prepareToPlay is synchronous. There is no asynchronous AVAudioPlayer prepareToPlay API in the installed SDK.

Removing it and relying on play() is not a reliable warning fix. Apple documents that play() performs the preparation automatically, so the blocking work could merely move to player.play() on the main thread.

3.5 Why it runs on the main thread

6. Threading and MainActor analysis

6.1 Project isolation

The target uses default MainActor isolation.

SpeechRecognitionManager is additionally explicitly declared @MainActor:

SR_Manager.swift:197-198

This ensures its published state and audio-engine lifecycle are serialized with UI state.

6.2 UI state that must remain MainActor-isolated

The following should remain MainActor-bound:

• @Published recognition results and displayState
• SwiftUI @State such as isSpkRecEnabled
• Alerts
• soundEffectPlayer storage
• Speech-recognition LED and display changes
• Timer/widget observable state
• Recognition session identifiers if the manager remains MainActor-owned

6.3 Work that need not inherently be on MainActor

These operations do not update UI directly:

• AVAudioSession setCategory
• AVAudioSession activation/deactivation
• AVAudioPlayer construction
• AVAudioPlayer prepareToPlay
• File decoding and buffer preparation

They can potentially execute elsewhere, but they must be serialized relative to one another and relative to audio-engine startup/shutdown.

6.4 Audio-engine operations requiring ordered handling

These should not be casually dispatched independently:

• Setting the category to .record
• Activating the recording session
• Installing/removing the input tap
• AVAudioEngine prepare/start/stop
• Ending/cancelling recognition
• Deactivating the session
• Switching to .playback
• Preparing or starting an AVAudioPlayer

Moving only one call to DispatchQueue.global().async could allow playback configuration to race with recognition startup or shutdown.

6.5 Task behavior

Task { } does not mean “background thread.”

Tasks created in MainScreen or SpeechRecognitionManager inherit MainActor. Awaiting an async activation temporarily suspends the task, but later statements resume under the same actor isolation.

8. Speech synthesis and playback interactions

8.1 Speech synthesis while recognition is enabled

speakMainGridText contains:

guard !isSpkRecEnabled else {
return

}

Main_ButtonBehavior.swift:670-673

This deliberately prevents speech synthesis while recognition is enabled. It reduces feedback loops and avoids directly changing the session to playback during active recognition.

This applies to .spk and other uses of speakMainGridText.

8.2 Sound playback while recognition is enabled

playMainGridSound has no equivalent guard.

A sound command can therefore call activateAudioSessionForSpeechPlayback while speech recognition has configured the session as:

.record / measurement

If the session remains active, line 303 switches it to:

.playback / spokenAudio

Apple documents that changing category or mode while active causes an immediate change. This may disrupt AVAudioEngine input or trigger recognition errors.

The source does not explicitly coordinate this transition with SpeechRecognitionManager.

8.3 Ambient sound while recognition is enabled

Ambient playback uses the same playback-session callback and likewise has no visible recognition guard.

It can therefore compete with speech recognition.

8.4 Restoration after speech and sound

Speech recognition reestablishes .record/.measurement whenever it restarts.

Playback code does not explicitly restore a prior recording category after speech or sound completes.

No audio-player completion delegate restores the session.

No speech-synthesizer completion delegate restores the session.

If recognition is enabled, synthesis is prevented, but ordinary or ambient sound can still change the shared session.

8.5 Repeated audio commands

Every speech or sound start calls the playback activation helper again.

Sequential sound commands can:

• Repeat setCategory
• Repeat activation
• Prepare new players
• Replace soundEffectPlayer while previous playback may be active

The old player is generally released when soundEffectPlayer is replaced, but there is no explicit stop immediately before every replacement.

9. Whether the warnings are related

The best classification is:

C. Different operations sharing an underlying lifecycle problem.

Warning A is a synchronous category/mode/options change.

Warning B is synchronous AVAudioPlayer preparation and implicit session activation.

They are not two reports of the exact same statement.

They are connected because playMainGridSound executes both operations in sequence:

1. activateAudioSessionForSpeechPlayback
2. AVAudioPlayer.prepareToPlay

They also share these design conditions:

• Both run on MainActor.
• Both affect the shared AVAudioSession.
• Both may perform audio-service or hardware work.
• Multiple independent components manipulate the session.
• There is no common serialized audio-session coordinator.
• Playback and recognition configuration can overlap.

10.6 Deployment implications

The deployment target is iOS 17.6.

The asynchronous AVAudioSession activation/deactivation APIs cannot replace the legacy path unconditionally. The app must retain a fallback for iOS 17.6 through iOS 26.

For those systems, synchronous setActive must run in a controlled non-main execution context if main-thread blocking is to be eliminated.

11. Possible fixes and trade-offs

OPTION A: Use asynchronous AVAudioSession activation/deactivation

Applicable to:

• Explicit activation and deactivation
• iOS 27 and later

Already used in:

SR_Support.swift:305-308
SR_Manager.swift:316-320
SR_Manager.swift:450-454

Advantages:

• Does not block MainActor during activation/deactivation.
• Preserves an explicit completion point.
• Apple-provided implementation.
• Clear success/error reporting.

Limitations:

• Does not make setCategory asynchronous.
• Does not make AVAudioPlayer.prepareToPlay asynchronous.
• Does not cover the deployment target’s iOS 17.6-26 range.
• Does not by itself coordinate competing recognition and playback configuration.

Expected warning effect:

• Eliminates warnings caused specifically by synchronous setActive on iOS 27.
• Does not directly eliminate Warning A or Warning B.

OPTION B: Move blocking work to a serialized non-main execution context

Applicable to:

• setCategory
• iOS 17.6-26 setActive fallback
• AVAudioPlayer construction and prepareToPlay
• Potentially recognition session activation/deactivation

Advantages:

• Directly addresses main-thread blocking.
• Can preserve strict audio-operation ordering.
• Supports the deployment target.
• Can coordinate recording and playback category changes.

Risks:

• A random global queue is unsafe because operations may overlap or reorder.
• AVAudioEngine lifecycle and playback lifecycle must not race.
• SwiftUI and @Published state must return to MainActor.
• AVAudioPlayer ownership must be clearly transferred and not mutated concurrently.
• Adding a dedicated actor or serial executor is a larger change than moving one line.

Expected warning effect:

• Warning A should disappear when setCategory no longer executes on the main thread.
• Warning B should disappear when preparation no longer executes on the main thread.
• Runtime verification is required.

OPTION C: Reduce unnecessary activation and category changes

Possible checks include avoiding setCategory when category, mode, and options already match the desired playback configuration.

Advantages:

• Reduces repeated route changes.
• Reduces unnecessary audio-service calls.
• May reduce warning frequency.
• Helps sequential speech and sound commands.

Risks:

• Reading category state and deciding whether to change it must still be serialized.
• The first transition remains synchronous.
• Another component can change the shared session between the check and use.
• Skipping explicit activation before prepareToPlay may leave implicit activation on MainActor.
• Session “already active” state is not directly exposed as a simple reliable public Boolean.

Expected warning effect:

• May reduce occurrences.
• Cannot guarantee elimination.

OPTION D: Preserve existing behavior

Advantages:

• No lifecycle regressions.
• The warnings may correspond to brief pauses on many devices.
• Existing audio behavior remains known.

Risks:

• Main-thread blocking remains.
• First sound playback or route transitions may visibly pause.
• Sound playback can still compete with active recognition.
• Future diagnostics may identify additional call sites, such as ambient sound and Settings preview.

Expected warning effect:

• None.

12. Recommended smallest safe fix

The safest solution is not a bare DispatchQueue.global().async wrapper.

12.1 Warning A recommendation

Exact file:

ESP32BLE/ESP32BLE/Scrns/Main_Screen/Speech Recognition/SR_Support.swift

Exact function:

activateAudioSessionForSpeechPlayback()

Offending statement:

SR_Support.swift:303
audioSession.setCategory(...)

Recommended restructuring:

• Move playback category configuration and activation into a dedicated serialized, non-main audio-session execution context.
• Keep setCategory followed by activation as one ordered operation.
• On iOS 27+, await the existing asynchronous activate API.
• On iOS 17.6-26, execute synchronous setActive(true) on the same serialized non-main context.
• Return success or an error rather than silently ignoring every failure.
• Update alerts or UI state on MainActor only after the audio operation completes.

Lifecycle requirements:

• Do not allow recognition’s .record configuration to interleave with playback’s .playback configuration.
• Decide explicitly whether active recognition should block, stop, or be restored after sound playback.
• Preserve the existing behavior for .spk, which currently does nothing while speech recognition is enabled.

Expected result:

• setCategory no longer blocks MainActor.
• Legacy setActive fallback no longer blocks MainActor.
• Audio-session transitions become ordered.

12.2 Warning B recommendation

Exact file:

ESP32BLE/ESP32BLE/Scrns/Main_Screen/Main_ButtonBehavior.swift

Exact function:

playMainGridSound(named:repeats:)

Offending statement:

Main_ButtonBehavior.swift:1498
player.prepareToPlay()

Recommended restructuring:

• Resolve the URL and perform UI validation on MainActor.
• Await serialized playback-session configuration.
• Construct and prepare AVAudioPlayer in a controlled non-main operation.
• Check the Bool returned by prepareToPlay.
• Return the prepared player to MainActor.
• On MainActor, start playback and assign soundEffectPlayer.
• Report errors through the existing alert state on MainActor.

Lifecycle requirements:

• Do not start playback until session activation completes.
• Prevent a stale preparation result from replacing a newer sound command if overlapping commands are possible.
• Ensure the player remains strongly retained.
• Avoid concurrent mutation of the same player from multiple isolation contexts.

Expected result:

• Buffer loading and hardware preparation no longer block MainActor.
• Existing playback state remains SwiftUI-safe.

13. Whether to split implementation into separate stages

Recommendation: two small implementation stages.

Stage A: Audio-session configuration and activation

Primary files/functions:

• SR_Support.swift
activateAudioSessionForSpeechPlayback()

• SR_Manager.swift
configureAudioSession()
finishRecognitionSession(shouldRestart:)

A shared serialized mechanism may be required if recognition and playback are to be made race-free. If the implementation is restricted to one file, it can remove the immediate Warning A but cannot completely coordinate ownership.

Stage B: AVAudioPlayer preparation

Primary file/function:

• Main_ButtonBehavior.swift
playMainGridSound(named:repeats:)

This stage should consume the ordered session-activation result from Stage A and move player preparation off MainActor.

Reasons to split:

• Warning A is session configuration.
• Warning B is player/hardware preparation.
• They have different APIs and error paths.
• Warning B should be built on top of the ordering established in Stage A.
• Separate stages make speech-recognition regressions easier to isolate.

Related ambient-sound and Settings-preview warnings should be separate follow-up work unless physically observed as part of the same reproduction.
