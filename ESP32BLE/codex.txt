ESP-HELP-001 — READ-ONLY HELP SYSTEM ARCHITECTURE PROBE

Scope: ESP32BLE iOS/iPadOS development project only.

No files, settings, packages, builds, runs, commits, backups, ESPMacHelper files, or firmware were modified.

A. EXECUTIVE SUMMARY

ESP has a custom full-screen Settings implementation, not NavigationStack, NavigationView, or a Settings sheet. Settings is conditionally overlaid by the root ContentView and returned from through a callback that sets isSettingsScreenPresented to false.

The smallest, safest Help architecture is:

• A single Help entry point in Settings.
• A self-contained Help sheet.
• A NavigationStack inside that sheet only.
• A SwiftUI topic list.
• A WKWebView wrapped by a new UIViewRepresentable for offline HTML topic pages.
• Bundled local HTML/CSS/images in one preserved Help resource directory.
• External PDF link opened through the existing UIApplication.shared.open mechanism.

This avoids changing the existing root screen switching, BLE state, Mac Helper state, import/export state, Settings document editor, or Soft Editor.

There is no existing WebKit, WKWebView, local HTML renderer, or bundled HTML content to reuse. The project does have several UIKit bridges using UIViewRepresentable, so that bridge pattern is already established, but none is suitable for reuse as a web renderer.

The app target supports iPhone and iPad with an iOS 17.6 deployment target. A WKWebView-based bridge is appropriate for that target. The newer native SwiftUI WebView API must not be the sole implementation if iOS 17.6 remains supported.

C. RECOMMENDED HELP BUTTON LOCATION

Recommendation:

Place one compact Help button in the Settings top toolbar, immediately after the existing main button.

Why this is preferred:

• It is consistently available in both iPhone and iPad Settings layouts.
• It is visible before the user reaches device, document, import/export, or file-management controls.
• It is clearly separate from BLE and Mac connection controls, so it can serve all Help topics rather than appearing to be only connection help.
• It avoids changing the existing connection panel, device list, file table, Soft Editor, and data-management controls.
• It is the least invasive location in the established Settings hierarchy.

Relevant toolbar source:

• Toolbar container: Set_Screen.swift:461-587.
• Existing main button: Set_Screen.swift:466-469.
• Import menu: Set_Screen.swift:497-515.
• Export menu: Set_Screen.swift:524-562.
• Table selector: Set_Screen.swift:569.
• Repair/new controls: Set_Screen.swift:574-583.

iPhone landscape assessment:

• The existing toolbar is dense and uses an HStack with fixed-width controls, menus, title control, spacers, and conditional iPad spacing.
• Source: Set_Screen.swift:461-587.
• A text-labeled “Help” button would create avoidable compression risk.
• A compact icon-only button with a clear accessibility label is the appropriate form.
• This must be tested on the smallest supported iPhone landscape width.

iPad assessment:

• The toolbar already inserts spacers around the title area on iPad.
• Source: Set_Screen.swift:484-492 and 516-519.
• A compact Help control should have materially lower layout risk on iPad.

Alternative considered:

• Adding Help inside SettingsAvailableDevicesPanel would avoid toolbar pressure, but it would associate general application help with connection controls and would appear in different visual positions on iPhone versus iPad.
• Not recommended.

E. RECOMMENDED HELP VIEWER ARCHITECTURE

Recommendation:

1. Keep Help state local to SettingsScreen.

• A local Boolean presentation state in Settings is sufficient.
• Do not add Help state to BLEKeyboardManager, MacConnectionManager, document persistence, or the root ContentView unless later requirements demand deep links.

2. Present a Help sheet from Settings.

• The sheet opens above Settings.
• Dismissing the sheet returns the user directly to the unchanged Settings screen.
• This isolates Help from the application’s custom root-level screen switching.

3. Put NavigationStack inside Help only.

• The Help sheet can contain a native SwiftUI topic list:
• Connect to Mac
• Connect to ESP32BLE
• Using ESP
• Troubleshooting
• Complete User Manual

• Tapping an offline topic pushes a detail view containing a local WKWebView.
• The system navigation back control returns to the topic list.
• The sheet’s Close/Done control returns to Settings.

This is intentionally limited to Help. It does not redesign Settings navigation.

4. Use WKWebView through a small UIViewRepresentable.

• Import WebKit only in the new Help renderer file.
• Load local content with WKWebView.loadFileURL(_:allowingReadAccessTo:).
• Grant read access to only the bundled Help directory, not the full application bundle.
• Apple documents that the read-access URL controls which additional local files WebKit may read. A directory access URL is appropriate when HTML relies on local CSS and images.

5. Keep Help content offline.

• The four short Help topics should be fully usable without network access.
• Do not fetch, download, or update those pages dynamically.

6. Handle PDF link separately.

• The Complete User Manual item should use an external HTTPS URL through UIApplication.shared.open.
• It should not be rendered inside the offline Help WKWebView by default.

iOS compatibility:

• Target deployment is iOS 17.6 for both target configurations.
• Source: ESP32BLE.xcodeproj/project.pbxproj:634 and 676.

• A UIKit WKWebView wrapped in UIViewRepresentable is compatible with that deployment target.

• Apple now provides a native SwiftUI WebView API in newer OS releases, but it must not be the only solution while iOS 17.6 support remains required.

Light/dark appearance:

• Use standard semantic CSS with:
• color-scheme: light dark
• @media (prefers-color-scheme: dark)
• system colors or paired light/dark CSS variables.

• Do not hard-code black backgrounds, white text, or fixed contrast assumptions.

Dynamic Type and readability:

• Use a viewport meta tag.
• Use relative CSS sizing such as rem/em rather than fixed pixel text.
• Use readable line height and an adaptable content width.
• WKWebView/HTML Dynamic Type behavior must be tested at larger accessibility sizes. HTML does not automatically gain all native SwiftUI text-style behavior.

Accessibility:

• Use semantic HTML:
• h1, h2, p, ul, ol, nav, main.
• Use meaningful link labels.
• Add alt text for instructional images.
• Maintain sufficient contrast in both appearances.
• Keep links and controls large enough for touch.
• Do not use image-only text for instructional content.
• Test VoiceOver heading navigation, link traversal, focus order, text selection, and larger text sizes.

Rotation and landscape:

• A sheet plus NavigationStack handles navigation independently of the custom Settings layout.
• WKWebView should be constrained to the Help detail view’s available size, not assigned fixed device dimensions.
• Relative HTML/CSS should reflow automatically as width changes.
• Test iPhone landscape and iPad split/rotation behavior.

Technical risks requiring device testing:

• Sheet appearance on compact iPhone landscape.
• Toolbar button fit on smallest supported iPhone landscape.
• WKWebView rendering of local CSS/images after app-store packaging.
• Relative local links across topic pages.
• Dynamic Type behavior at accessibility text sizes.
• Dark/light switching while Help is visible.
• VoiceOver focus after pushing/popping Help pages and dismissing the sheet.
• External PDF handling when Safari is unavailable, restricted, or offline.

Design notes:

• Keep index.html optional if SwiftUI provides the Help topic list. It can still be useful as a fallback landing page or for future web publication.
• Use relative paths:
• css/help.css
• images/example.png
• connect-mac.html

• Preserve the Help directory hierarchy in the app bundle.
• Add the Help directory as a resource in a way that copies its hierarchy rather than flattening files into the bundle root.
• Then locate index.html through Bundle.main with the Help subdirectory and grant WKWebView read access to that Help directory.

Why preserving the folder hierarchy matters:

• Relative image, CSS, and local HTML links depend on a stable directory structure.
• Flattened resources can break relative paths or require content changes that should not be necessary.

No existing HTML-resource convention was found, so this should be introduced as an isolated Help-only resource directory.

H. PDF MANUAL LINKING APPROACH

Confirmed existing external URL mechanism:

• The app already opens external URLs through UIApplication.shared.open.
• Source: Scrns/Main_Screen/Main_ButtonBehavior.swift:758-772 and 803-805.
• There are also async URL-open calls in the same file.
• Source: Main_ButtonBehavior.swift:1027-1030 and 1086.

Recommendation:

• The Complete User Manual Help item should open the future HTTPS PDF URL externally through UIApplication.shared.open.
• Safari/default browser handling is provided by iOS.
• No new application permission is needed merely to open a normal HTTPS URL.
• The existing Info.plist has no ATS exceptions; a standard HTTPS GitHub Pages URL should not require one.
• Source: ESP32BLE/Info.plist:1-13.

Offline behavior:

• The app can attempt to open the external URL, but cannot guarantee that the PDF is reachable.
• The Help UI should make the distinction explicit:
“Complete User Manual — opens online PDF”
and provide a short offline/unavailable explanation if opening fails or the document cannot load.

• Final behavior must be tested with:
• Airplane mode.
• No DNS.
• Captive portal.
• GitHub Pages unavailable.
• Safari restrictions or device-management restrictions.

No final PDF URL was invented.

I. COMPATIBILITY AND REGRESSION RISKS

BLE discovery and connection:

• Risk is low if Help is an isolated Settings sheet with no BLE state changes.
• Do not create, reset, or observe BLE discovery state from Help.
• Relevant current connection UI:
• SettingsAvailableDevicesPanel.
• Source: Set_AvailableDevices.swift:88-151 and 237-287.

Mac Helper discovery and pairing:

• Risk is low if Help only displays static content.
• Do not alter MacConnectionManager state or pairing operations.
• Existing pairing UI:
• Source: Set_AvailableDevices.swift:166-235.

Settings navigation:

• Main risk: adding Help to the root ContentView’s custom screen-state system would couple Help to existing main/settings transitions.
• Isolation approach: keep Help as a Settings-owned sheet.

Settings toolbar:

• Highest layout risk is iPhone landscape because the existing toolbar is already dense.
• Use one compact icon button only; test all supported iPhone widths/orientations.

Files, import/export, backup, restore:

• Help must not use the Settings document directory, file picker state, archive state, import state, or export state.
• It should use only bundled app resources.
• Existing toolbar contains import/export and full-backup actions:
• Source: Set_Screen.swift:497-562.

Soft Editor and Command Info:

• Keep Help independent from smartCommandDescription, Soft Editor accessory state, Smart Editor text fields, and command insertion state.
• This is essential because Command Info depends on selected editor action and insertion state.

iPad layout:

• The current iPad Settings layout is a split HStack, not standard split-view navigation.
• A self-contained Help sheet avoids changing its document table and editor sizing.
• Source: Set_Screen.swift:405-419.

iPhone landscape:

• Help content itself should reflow, but the entry button and sheet presentation require real-device testing.
• Existing iPhone Settings layout is a custom HStack with fixed device-panel width and a calculated document-table width.
• Source: Set_Screen.swift:429-459.

iOS 17.6:

• Keep implementation to SwiftUI, UIKit, WebKit APIs available on iOS 17.6.
• Do not require newer native SwiftUI WebView APIs as the only renderer.
• Target configuration:
• ESP32BLE.xcodeproj/project.pbxproj:634 and 676.

L. USER DECISIONS NEEDED

No decision is needed to begin the future Stage 1 implementation, assuming the recommended compact toolbar Help button and Settings-owned Help sheet are acceptable.

Decisions needed before later stages:

1. Help presentation style:
• Recommended: a dismissible Help sheet containing its own NavigationStack.
• Alternative: another full custom root screen.
• The sheet is substantially safer because it avoids altering existing custom root navigation.

2. Offline content policy:
• Recommended: English-only bundled HTML for initial public release.
• Decide later whether Help content will be localized with the app.

3. PDF handoff policy:
• Recommended: open the hosted PDF externally in Safari/default browser.
• Decide whether a future version should offer in-app browser viewing instead.

4. Final manual URL:
• Required before Stage 4.
• The URL should be final, HTTPS, public, and stable before it is embedded in a release.
