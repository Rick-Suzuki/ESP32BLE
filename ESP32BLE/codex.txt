C. CURRENT SAVE BEHAVIOUR

commitSlotEditing() is in Main_DocumentActions.swift􀰓.

It always:
1. Resolves the editable anchor index.
2. Calculates current span.
3. Calls updateFunctionKeySlot(editableIndex, normalizedSlotEditorTextForCommit(editingSlotText)).
4. Reapplies span continuation markers if the button is multi-cell.

updateFunctionKeySlot is supplied by ContentView as updateSelectedDocumentSlot, wired at ContentView.swift􀰓.

updateSelectedDocumentSlot(...) at ContentView.swift􀰓:
1. Normalizes the line.
2. Updates functionKeySlotLines.
3. Calls persistSlotLines(updatedLines).

persistSlotLines(...) at ContentView.swift􀰓 writes the selected document file and reapplies loaded slot lines.

So yes: close currently invokes Save, and Save currently persists even when no user edit occurred.

G. ROOT CAUSE

The message appears without editing because every close path calls saveSlotEditing() unconditionally.

saveSlotEditing() always:
1. Commits the current editor text.
2. Persists through updateFunctionKeySlot.
3. Sets renameAlertMessage = "btn has been\nsaved to file".

There is no current check for “was anything edited during this editor session?”

H. RECOMMENDED MINIMAL FIX

Smallest safe future approach:

1. Add a session flag in MainScreen, for example:
@State private var didModifyCurrentSlotEditorSession = false

2. Initialize it to false in beginSlotEditing(at:), after loading the selected button.

3. Set it to true only from genuine editing actions, not from initial sync or focus/inspection.

Best places to set it:
• In user-action button handlers before they mutate drafts/text.
• In text-field binding setters when the new value differs due to user input.
• In smart editor bindings that represent actual user edits.
• In visibility/color/SF Symbol/paste/helper insert handlers.

4. Do not clear the flag if the user changes a value back to the original. That satisfies Case C.

5. On close, still consider calling commitSlotEditing() if persistence/normalization is required, but display the save message only if the session flag is true.

Safest minimal behavior:
• Keep close calling save/commit to avoid disrupting existing persistence/normalization.
• Gate only the confirmation message initially.

Cleaner later behavior:
• Split saveSlotEditing() into “commit” and “show saved message” variants, or add a parameter such as showConfirmation.

I. RISKS

Do not disturb:
• Existing close buttons.
• Existing save button.
• Long-press editor opening in normal and edit modes.
• Popup Edit opening.
• Smart editor immediate persistence paths.
• Multi-cell span preservation in commitSlotEditing().
• cancelSlotEditing() cleanup.
• Existing popup/toast overlay behavior.

Main risk:
If a future dirty flag is set by initial sync, the false save message will remain. The flag must be initialized after loading and not set by syncDraftsFromCombinedText() during editor appearance.
