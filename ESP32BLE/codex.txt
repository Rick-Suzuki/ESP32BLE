3. City resolution is local and offline.

It uses:

TimeZone(identifier:)
TimeZone.knownTimeZoneIdentifiers

There is no CLGeocoder, MapKit, CoreLocation, URLSession, bundled city database, or remote API in the widget resolver.

4. The parser treats every token after a date/time command as one city/location label.

Examples:

.clock London
cityLabel = "London"


.clock London, UK
cityLabel = "London, UK"


.clock Europe/London
cityLabel = "Europe/London"


Spaces are preserved by joining the remaining tokens with a single space. Commas are not specially parsed or removed.

5. Invalid locations silently fall back to the device time zone.

For example, .clock Atlantis produces a plausible device-local time rather than an error.

6. Ambiguity is not detected.

The resolver selects the first matching IANA identifier. It cannot report multiple matches.

7. Most widgets correctly use the parsed city time zone, including .min. Fractional-hour and fractional-quarter-hour zones work when a valid named time-zone identifier or resolvable identifier tail is supplied.

8. Two important inconsistencies exist:

• .date parses a city but rendering ignores the descriptor’s cityLabel.
• .dow parses a city but rendering ignores the descriptor’s cityLabel.

These two widgets instead consult the button’s alternate/right-hand text as a possible time-zone name.

9. Widgets do not share one timer.

Each rendered widget creates its own TimelineView. Calendar widgets update every 60 seconds; clock/second/minute/hour update every second.

10. There is no city-resolution cache or stored resolved IANA identifier.

The raw command remains part of the button/document data. Resolution is repeated from local Foundation data during formatting.

4. CITY PARAMETER SYNTAX
==================================================

CONFIRMED FROM SOURCE

Grammar at the widget descriptor parser:

command := widgetName [whitespace locationText]
locationText := every remaining whitespace-separated token, rejoined with spaces

Implementation:
Main_ButtonBehavior.swift:1228-1234
Main_ButtonBehavior.swift:1241-1321

Examples:

.clock London
Accepted syntactically.
Location passed to resolver: "London".

.clock Tokyo
Accepted syntactically.
Location passed to resolver: "Tokyo".

.clock London, UK
Accepted syntactically.
Location passed to resolver: "London, UK".
It is not country-qualified parsing; the comma remains literal, so resolution is expected to fail.

.clock Europe/London
Accepted syntactically.
TimeZone(identifier: "Europe/London") is attempted directly and should resolve.

.ord London
Not currently recognized because .ord is not implemented.

.day London
Currently accepted and uses "London" as cityLabel.

Spaces:
Multiple whitespace runs are collapsed when the tokens are rejoined.

Commas:
No special meaning. They remain part of the lookup query.

Colon plus whitespace:
At the outer document parser, a colon followed by whitespace separates command/action components:
ContentView.swift:2663-2695

Therefore a location containing ": " cannot remain intact as one widget command.

Multiple command parameters:
Date/time commands do not have separately typed parameters. Every token after the command becomes one location label.

Supported lookup forms:

• Exact identifiers accepted by TimeZone(identifier:).
• Exact normalized full entries from TimeZone.knownTimeZoneIdentifiers.
• Exact normalized final path components of known IANA identifiers.
• A redundant suffix match against “/query”.

Normalization only:

• Lowercases.
• Replaces underscores with spaces.
• Trims leading/trailing whitespace.

Implementation:
Main_ButtonLabelView.swift:715-741

City names:
Only work if the normalized city name equals the final component of a known time-zone identifier.

Examples likely to resolve structurally:

Tokyo -> Asia/Tokyo
London -> Europe/London
New York -> America/New_York
Los Angeles -> America/Los_Angeles

City/airport codes:
There is no input lookup table for codes such as LON, TYO, HND, NYC, or LAX.

The manual code dictionary at Main_ButtonLabelView.swift:670-678 is output/display-label code, not city-to-time-zone input resolution.

Country-qualified names:
No explicit support.

“London, UK” is not transformed to Europe/London.

Region-qualified names:
IANA form is supported, such as Europe/London.

Human form such as “London, England” is not structurally parsed.

Numeric offsets:
There is no explicit numeric-offset grammar or TimeZone(secondsFromGMT:) usage.

A string only works if TimeZone(identifier:) itself accepts that exact representation on the running OS. This was not executed during the read-only probe.

6. CITY-TO-TIME-ZONE RESOLUTION
==================================================

CONFIRMED FROM SOURCE

Primary resolver:

widgetTimeZone(for:)
Main_ButtonLabelView.swift:715-734

A duplicate property resolver exists at:
Main_ButtonLabelView.swift:503-522

Resolution sequence:

1. If cityLabel is nil, return nil.
2. Try TimeZone(identifier: cityLabel).
3. Normalize the input.
4. Iterate TimeZone.knownTimeZoneIdentifiers.
5. Select the first identifier whose:
   • normalized full identifier equals the query, or
   • normalized final path component equals the query, or
   • normalized identifier ends in “/query”.
6. Create TimeZone from the selected identifier.
7. Return nil if nothing matched.

Technology:

• Foundation TimeZone: yes.
• Foundation Calendar: used by the ordinal calculation.
• CLGeocoder: no.
• MapKit: no.
• CoreLocation: no.
• Bundled city database: no.
• Remote API: no.
• Hard-coded input lookup table: no.
• Hard-coded output city-code table: yes, but only in widgetDateCityCode at lines 670-678.

Lookup output:
A Foundation TimeZone.

Caching:
None.

Persistence:
No resolved identifier is persisted.

Failure handling:
Returns nil, followed by silent fallback to TimeZone.current.

Ambiguity handling:
None. first(where:) selects the first match.

DST:
Named Foundation time zones automatically carry their rule data, including daylight-saving transitions.

8. MINUTES AND SECONDS
==================================================

CONFIRMED FROM SOURCE

.min does use the specified city time zone:
Main_ButtonLabelView.swift:285-298
Main_ButtonLabelView.swift:556-562

The DateFormatter receives the resolved time zone and format "mm".

Therefore fractional offsets are represented correctly when the supplied location resolves to a valid named zone, including zones structurally equivalent to:

UTC+05:30
UTC+05:45
UTC+09:30

The minute may differ from the device’s minute exactly as required.

.sec also passes the resolved city time zone to DateFormatter.

At the same instant, ordinary civil time-zone rules do not change the seconds component, so this is normally redundant. It is nevertheless architecturally consistent with .hour and .min.

No city-specific calendar operation is required for seconds in the current implementation.

POSSIBLE RISK / REQUIRES TESTING

The supported input must resolve to a named identifier or identifier tail. The source does not explicitly support raw strings such as “UTC+05:45” through TimeZone(secondsFromGMT:).

widgetTimeZone(for: "Atlantis")

Result:

• No error.
• No empty value.
• No crash.
• No explicit UTC fallback.
• No previous-valid-city state.
• No default-city state.
• It normally displays device-local time.
• If the alternate/right button text happens to be a resolvable zone, .clock can use that instead.

For .hour, .min, .sec, .day, .month, and .year, invalid city text directly falls back to TimeZone.current.

For .date and .dow, the command city is ignored regardless of validity.

Invalid input is not distinguishable from:

• No city.
• A resolver limitation.
• An ambiguous input.
• A temporarily unavailable zone, although no network lookup exists.

Safest future error source:

Change resolution from TimeZone? into an explicit result carrying at least:

• localDefault
• resolved(TimeZone)
• unknown(input)
• ambiguous(input, candidates)

Then formatting can avoid silently applying TimeZone.current to an explicitly supplied but invalid city.

10. AMBIGUOUS CITY BEHAVIOR
==================================================

CONFIRMED FROM SOURCE

The resolver cannot detect ambiguity.

It uses:

TimeZone.knownTimeZoneIdentifiers.first { ... }

at:
Main_ButtonLabelView.swift:725-731

Consequences:

• Multiple candidates are never collected.
• The first matching identifier wins.
• No ambiguity error is available.
• Country qualification is not parsed.
• Region qualification is only supported when it is already a valid IANA identifier.
• Device region is not explicitly consulted.
• Locale.current affects displayed names, not candidate selection.

London examples:

Likely matches Europe/London because its final identifier component is London.

London, England
No transformation or country parsing exists; likely unresolved.

London, Ontario
No transformation exists; likely unresolved.

America/Toronto
Direct IANA identifier and should resolve, but this identifies the time zone rather than the city London, Ontario.

The resolver’s current model cannot safely represent arbitrary same-named cities.

13. MIDNIGHT, MONTH/YEAR BOUNDARIES, AND DST
==================================================

CONFIRMED FROM SOURCE

All widgets receive a Date representing an instant from their TimelineView context.

Correct city-local calendar derivation:

• .clock: yes
• .hour: yes
• .min: yes
• .sec: yes
• .day: yes
• .month: yes
• .year: yes
• .date: no, parsed command city is ignored
• .dow: no, parsed command city is ignored

Japan/London boundary example:

At an instant where Tokyo is October 18 and London is October 17:

• .day Tokyo can show 18th.
• .month Tokyo and .year Tokyo use Tokyo’s time zone.
• .date Tokyo may show the device’s date instead.
• .dow Tokyo may show the device’s weekday instead.

The same inconsistency applies across:

• Midnight.
• Month changes.
• New Year.
• International Date Line differences.

DST:

Named Foundation TimeZone values are used rather than fixed offsets.

Foundation DateFormatter and Calendar apply the zone’s DST rules for:

• Spring-forward transitions.
• Repeated autumn hours.
• Offset changes.
• Date changes around transitions.

No custom DST arithmetic was found.

POSSIBLE RISK / REQUIRES TESTING

• Each widget owns a separate TimelineView, so their context dates need not be byte-for-byte identical.
• Timeline schedules can be coalesced by the system.
• Calendar.current may use a non-Gregorian user calendar, while DateFormatter patterns have locale/calendar behaviors that should be verified under alternate calendar settings.

16. ERROR-PRESENTATION OPTIONS
==================================================

OPTION A — Error inside the widget

Visibility:
High in Button, Btn Text, and All modes.

Readability:
Good if compact, for example “Unknown city” with the input available in a smaller line or accessibility label.

Small-button compatibility:
Moderate. “Unknown city: Atlantis” may require aggressive scaling or truncation.

Gesture interference:
None.

Repeated-alert risk:
None.

iPhone/iPad consistency:
Strong.

Complexity:
Low to moderate. The formatter/resolver must return an explicit error state rather than TimeZone?.

Limitation:
Command mode currently bypasses widgetContent, so the raw command would still appear instead of the error.

Assessment:
Safest minimal presentation within the current architecture.


OPTION B — Alert/dialog

Visibility:
Very high.

Readability:
Excellent.

Small-button compatibility:
Excellent because the message is outside the button.

Gesture interference:
Requires defining when the alert appears.

Repeated-alert risk:
High. Timeline refreshes every second or minute; presenting from formatting/rendering would risk repeated alerts and state mutation during view updates.

iPhone/iPad consistency:
Alerts work on both, but presentation timing and competing alerts require care.

Complexity:
Moderate to high. The app already has shared alert state in Main_ButtonBehavior.swift:1606-1613 and 1662-1668, but date/time rendering has no error callback.

Assessment:
Not recommended as the default automatic response.


OPTION C — Compact indicator with tap for details

Visibility:
Moderate. A warning symbol is compact but may be missed.

Readability:
Good after interaction.

Small-button compatibility:
Strong.

Gesture interference:
Material risk. Date/time widgets are currently noninteractive:
Main_ButtonBehavior.swift:1729-1752

Making them tappable could conflict with button behavior, edit mode, or future actions.

Repeated-alert risk:
Low if details only appear after an explicit tap.

iPhone/iPad consistency:
Generally good, but popover versus sheet/alert behavior requires design.

Complexity:
Moderate to high.

Assessment:
Useful if detailed ambiguity/error information is required, but not the smallest change.


OPTION D — Inline compact fallback plus accessible detail

Example visible content:

⚠ Atlantis

or:

Unknown city

with an accessibility label/value containing:

Unknown city: Atlantis

Visibility:
Good.

Readability:
Better than squeezing the complete message into very small buttons.

Small-button compatibility:
Strong.

Gesture interference:
None.

Repeated-alert risk:
None.

iPhone/iPad consistency:
Strong.

Complexity:
Moderate.

Assessment:
Best overall direction. It is essentially a compact version of Option A and fits the current noninteractive widget architecture.


Recommended presentation

Use Option D/A:

• Never show a calculated fallback value for an explicitly invalid city.
• Render a compact inline error.
• Include the full city in accessibility text.
• Preserve the raw command in Command mode.
• Avoid automatic alerts from TimelineView rendering.
• Consider tap-for-details only later if ambiguity candidate selection becomes necessary.

20. REMAINING UNCERTAINTIES
==================================================

POSSIBLE RISK / REQUIRES TESTING

1. Exact TimeZone(identifier:) acceptance

The source passes raw strings directly to TimeZone(identifier:). The exact set of accepted aliases, abbreviations, and GMT-style strings is determined by Foundation and the installed OS data. It was not executed during this strictly read-only probe.

2. First-match ordering

Ambiguous matching depends on the ordering of TimeZone.knownTimeZoneIdentifiers. The source makes no stability guarantee of its own.

3. Timeline scheduling

Source confirms requested intervals, but actual delivery can be delayed or coalesced by SwiftUI and system power/background behavior.

4. Immediate city-edit propagation

The state path strongly suggests the descriptor is recreated when the document/button entry changes, but this was not confirmed by launching the app.

5. Alternate/right-text time-zone behavior

It is source-confirmed, but whether it is an intentional historical feature or an accidental coupling cannot be established from implementation alone.

6. Dead/support helpers

clockText(for:), dateWeekdayText(for:), dateHeaderText(for:cityLabel:), dowHeaderText(for:cityLabel:), and widgetDateCityCode(for:cityLabel:) appear disconnected from the active rendering calls inspected here. A future cleanup should not be combined with the command rename.

7. Documentation mismatch

.month renders a localized full month name, while its help says the display is “10”. This is unrelated to the ordinal rename but should be tracked separately.

8. Localization expectations

Ordinal suffixes are English-only. Any future localization policy must decide whether .ord is explicitly English or should use locale-aware ordinal formatting.

9. General city coverage

The resolver only knows IANA zone identifiers and their final components. It is not a comprehensive city resolver. Many valid city names will fail even though their time zone is known under a different representative city.

10. No automated coverage

No dedicated date/time widget unit or UI tests were found. All behavioral conclusions above are source-derived; runtime-sensitive items remain in the physical-device checklist.
