4. Missing-file detection

An error is classified as confirmed missing when either:

• Its NSError domain and code directly identify a missing file.
• An underlying NSError identifies a missing file.
• For another error, the parent directory can be successfully enumerated and the exact standardized document URL is absent.

The correction does not rely solely on fileExists(atPath:).

If the parent directory cannot be enumerated, absence is not considered proven and the original error remains a genuine failure.

5. Genuine filesystem errors

An error remains a genuine failure when:

• The document still appears in its parent directory.
• The parent directory cannot be inspected reliably.
• The error is not a recognized missing-file error.
• A read or atomic write fails for another reason.

Permission, corruption, and other I/O failures therefore continue to display the existing save-failure alert.

External-change conflict detection was not changed.

6. Unsaved editor protection

A confirmed missing file now follows two paths:

• If documentEditorText equals savedDocumentEditorText, the editor is clean. The old baseline is cleared and the existing .missing transition continues.
• If the values differ, the editor has unsaved changes. Its contents and baseline are preserved, the transition is blocked, and the existing “File Removed” warning is displayed.

The old renamed path is never recreated, and unsaved text is never written into the newly selected document.

7. Operational effects

Rename:
The stale old URL can now be recognized as missing even if its NSError is not one of the original Cocoa codes. A clean rename transition should no longer produce the generic read/save alert for that condition.

Duplicate:
Normal duplication behavior is unchanged. Genuine errors remain visible.

Delete:
Uses the same improved missing-file detection. Clean deleted documents can transition normally; unsaved editor contents are preserved and block the transition.

Automatic-save observers were not disabled or modified.

ContentView was not modified.

10. Remaining risks and uncertainties

Physical-device verification is still required.

The new diagnostics will identify the actual NSError domain and code if the problem persists.

There remains an unavoidable filesystem race between checking a path and subsequently reading or writing it. Read and write catches now apply the same missing-file classification, limiting that risk.

No claim is made that the physical-device bug is confirmed fixed until the duplicate-and-rename workflow has been tested on the affected device.
