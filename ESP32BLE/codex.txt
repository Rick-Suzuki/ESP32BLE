Confirmed mechanism:

1. The left side of a screen entry becomes sendTexts.
2. FunctionKeyEntry.primaryDisplayText joins sendTexts with colons.
3. Text after “::” becomes alternateDisplayText.
4. Both a missing right side and an explicitly empty right side produce alternateDisplayText == nil:
   • “.prev”
   • “.prev::”
5. effectiveAlternateDisplayText(for:) first preserves any nonempty explicit right text.
6. When explicit text is empty, it asks navigationCommandDefaultLabel(for:) for a fallback.
7. buttonTitle(for:) then applies the selected display mode:
   • Left: primaryDisplayText
   • Right: effective alternate text
   • Both: primary plus effective alternate
   • Last: last component of effective alternate
8. mainGridButtonLabel(...) passes those resolved strings to MainScreenButtonLabelView.
9. Ordinary textual buttons are finally rendered by textLabel(title: title) at Main_ButtonLabelView.swift line 160.

This mechanism is suitable for reuse. The missing part is a command-specific default-label resolver covering the requested commands rather than navigation alone.

Current behavior for all seven groups:

When no explicit right-hand text exists, navigationCommandDefaultLabel returns nil. buttonTitle(for:) therefore exits at lines 96–98 and displays the serialized command rather than providing distinct Left/Right/Both/Last content.

Explicit right-hand text is already supported universally through “::” and takes precedence.

Application representation:
The command stores a user-entered application name or URL scheme, not a bundle identifier.

Known names are mapped to schemes:
• Notes or Apple Notes → mobilenotes://
• Mail → message://
• Messages or iMessage → sms:
• FaceTime → facetime://
• Maps → maps://
• Music → music://
• Calendar → calshow://
• Phone → tel://

Unknown names are normalized into a lowercase URL scheme. If the argument contains a colon, it is interpreted directly as a URL.

Current default label:
The full command, such as “app Safari”.

Desired default:
The application name.

Ambiguity:
The source cannot always derive a human-readable application name. For example:
• “Apple Notes” and “Notes” resolve to the same app.
• “applenotes” is accepted but is not necessarily the desired visible spelling.
• A custom URL such as “myapp://open/page” has no reliable application display name.

Safest display rule:
Use the exact entered operand after “app ”, preserving capitalization and spaces. Do not attempt to derive a name from the resulting URL.

Explicit right-hand text:
Supported and especially useful for custom URLs.

C. SHARED IMPLEMENTATION OPPORTUNITIES

One shared command-default helper is appropriate.

Recommended structure:

• Keep resolvedAlternateDisplayText(for:) responsible only for real explicit right-hand text.
• Extend effectiveAlternateDisplayText(for:) so that, after confirming explicit text is empty, it asks one command-specific default resolver.
• Preserve navigationCommandDefaultLabel(for:) or call it from the new shared resolver.
• Make the new resolver return nil for unrelated commands.

Suggested command-specific outputs:

• .prev → prev
• .next → next
• .back → back
• .forw → forw
• home → home
• file <filename> → exact filename
• app <reference> → exact entered operand
• sc <name> → exact shortcut name
• shortcut <name> → exact shortcut name
• valid out <int> <int> → out
• valid pwm <int> <int> <int> → pwm
• cb <text> → cb

Only Main_ButtonBehavior.swift should require modification for default-label behavior.

ContentView.swift, command execution, stored screen data, and MainScreenButtonLabelView should not need modification.

D. SPECIAL CASES AND AMBIGUITIES

Command chains

parsedActionTokens(from:) separates left-hand commands on colons at ContentView.swift lines 91–111.

A shared default resolver should only generate an argument-derived default when the entry contains one applicable command. For a multi-command chain, selecting one command’s filename, shortcut name, or label could misrepresent the button’s actual actions.

Recommendation:
Require entry.sendTexts.count == 1 for these generated defaults unless a specific chain-display policy is later defined.

Colons inside arguments

Because colons delimit action chains, unrestricted operands containing colons can be split before command recognition.

HTTP and HTTPS receive a special parsing exception at ContentView.swift lines 2630–2637. File, shortcut, and clipboard commands do not.

The Open App parser accepts colon-containing URLs, but the screen-line parser may split such a command before it reaches targetAppURLForSendText. This is a pre-existing parsing limitation, not a default-label issue.

Explicit right text

functionKeyEntry(from:) stores a nonempty right side as alternateDisplayText at ContentView.swift lines 2617–2627. effectiveAlternateDisplayText(for:) returns it before any fallback. This precedence can be preserved without special cases.

SF Symbols and emoji

SF Symbol and emoji detection intentionally use resolvedAlternateDisplayText rather than effectiveAlternateDisplayText:

• parsedSFSymbolDisplay(for:), Main_ButtonBehavior.swift lines 1679–1697
• parsedEmojiDisplay(for:), lines 1699–1715

Therefore, generated textual defaults will not accidentally become SF Symbol or emoji specifications. This separation should be retained.

Colour prefixes

resolvedAlternateDisplayText(for:) strips a right-side hexadecimal colour component at Main_ButtonBehavior.swift lines 139–153. The fallback should be applied after this resolution, as navigation currently does.

Dynamic widgets

The requested commands do not enter the widget renderer. No changes are needed to MainScreenButtonLabelView’s widget branch. The excluded clock, date, random, stopwatch, stop, and timer commands can remain untouched.

HOME mismatch

Confirmed source behavior is “home”, while help content advertises “.home”. This should be treated as a separate command-syntax task. A display-only change should not make “.home” appear supported.
