2. New CC parser

Added MIDIControlChangeCommand containing:

• controller: UInt8
• value: UInt8
• channelOverride: UInt8?

Added MIDIControlChangeParser.parse(_:).

Supported forms:

.cc <controller> <value>

.cc <controller> <value> <channel>

The parser:

• Uses the existing whitespace-splitting convention.
• Accepts leading, trailing, and repeated whitespace.
• Requires exact lowercase .cc.
• Validates controller and value as 0...127.
• Validates optional channel as 1...16.
• Rejects missing, extra, negative, non-numeric, and out-of-range arguments.
• Does not clamp values.

Named and numeric MIDI note parsing was not changed.

3. Channel resolution

MIDIChannelSettings now provides a shared resolver accepting:

channelOverride: UInt8?

defaultChannel: Int

Resolution order is:

1. Valid explicit override.
2. Valid device-local default.
3. Fallback channel 1.

The existing MIDICommand resolver delegates to this shared implementation, preserving current .midi behavior.

4. Classification and malformed-command suppression

Main_ButtonBehavior now includes:

• A single-command CC adapter.
• Exact .cc command classification.
• Centralized parsing through MIDIControlChangeParser.
• Early suppression of every .cc-classified entry.

A valid .cc command is handled and returns before ordinary button processing.

A malformed .cc command also returns immediately and cannot trigger:

• Keyboard output.
• BLE output.
• Speech.
• Navigation.
• Widget processing.
• File operations.
• Network MIDI transmission.

Entries containing .cc mixed with other commands are classified as CC-related but fail the exactly-one-command adapter, so the entire activation is safely suppressed.

Existing .midi classification and suppression were not altered.

5. Main Screen behavior

CC uses the existing ordinary SwiftUI Button path.

Each successful activation:

• Checks that button execution is enabled.
• Requires Mac network output mode.
• Requires a send-capable authenticated Mac connection.
• Resolves the effective channel.
• Requests one authenticated CC transmission.
• Returns without ordinary command processing.

Button release does nothing.

No changes were made to:

• Main_GridSection.swift
• MIDITouchCaptureView
• MIDI touch-down or release handling
• Touch cancellation
• Button geometry or rendering

Main_Screen passes its current AppStorage MIDI default channel through the existing sendLine closure. MainGridSection’s closure type was unchanged.

6. Network message construction

ESP32BLE constructs:

MIDI:CC:<controller>:<value>:<channel>

Examples:

MIDI:CC:64:127:1

MIDI:CC:64:0:1

MIDI:CC:1:100:2

Transmission uses the existing:

MacConnectionManager.sendAuthenticatedCommand

MacConnectionManager.swift was not modified.

Authentication, newline framing, connection management, and transport remain unchanged.

Repeated identical CC values are not deduplicated.

7. Helper parsing and validation

ParsedMIDICommand now includes:

controlChange(
controller: UInt8,

value: UInt8,

networkChannel: UInt8

)

MacNetworkServer accepts exactly five fields:

MIDI:CC:<controller>:<value>:<channel>

It independently validates:

• Controller 0...127.
• Value 0...127.
• Network channel 1...16.
• Exact uppercase wire tokens MIDI and CC.
• Exact field count.

Malformed MIDI-prefixed commands remain suppressed and cannot fall through into keyboard execution.

Existing Note On and Note Off parsing remains unchanged.

Successful submissions produce a standard diagnostic beginning with:

No new endpoint or output service was introduced.

9. MIDI-012 ownership

MIDI-012 ownership remains unchanged:

[NoteKey: [NoteOwner: Int]]

CC submission does not:

• Create NoteKey values.
• Modify activeNoteOwnerCounts.
• Increment or decrement note counts.
• Participate in Note Off.
• Participate in disconnect cleanup.
• Affect menu-test ownership.

Each CC is submitted once and forgotten.

14. Warnings and limitations

The Helper build reported one existing warning in MIDIOutputService.swift:

Comparing the non-optional MIDIEventListAdd result to nil always returns true.

That warning is in the pre-existing sendMessage implementation and was not introduced or changed by MIDI-013.

The command-line Xcode process also reported environmental CoreSimulator and file-type detection warnings. They did not prevent the macOS Helper build.

Controller state intentionally persists at the receiving synthesizer. CC64 is not automatically reset on release, disconnect, or screen changes.

Clients sending CC to the same MIDI channel share the receiver’s controller state.
