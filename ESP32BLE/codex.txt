C. What Repair actually does

Repair operates on one selected screen document only. It does not scan the Documents directory, rebuild indexes, restore backups, create directories, rename files, copy files, delete files, modify MIDI/BLE settings, or repair unrelated data.

It:

1. Requires Files mode and a selected screen file.
2. Saves current editor text first, using the normal conflict and missing-file safeguards.
3. Reads the editor text and normalizes line endings.
4. Limits the result to maxFunctionKeyCount lines.
5. Rebuilds the selected screen’s grid storage lines:
• Keeps ordinary button-anchor lines.
• Converts blank lines and _ placeholders to _.
• Removes orphaned @@wide and @@block continuation lines.
• Reconstructs valid continuation tokens for button shapes that fit the screen grid.
• Uses the screen’s .config.json grid dimensions when valid; otherwise uses legacy AppStorage grid dimensions; otherwise falls back to calculated grid dimensions.
6. Atomically overwrites the selected screen file with the reconstructed text if it differs.
7. Reloads that same screen into Settings and displays “Document repaired” or “Document checked.”

D. Files, directories, settings, or data modified

Modified:

• Only the currently selected screen document, in the app Documents directory.
• The in-memory Settings editor state for that same document.
• The loaded function-key state after reload.

Read, but not modified:

• The matching .config.json screen configuration, if present.
• The documentGridDimensionsData AppStorage value, as a fallback source of grid dimensions.

Not modified:

• Other screen files.
• Config files.
• Imported files.
• Images, sounds, PDFs, templates, backups.
• Selected-document preference, except that the already-selected document is reloaded.
• BLE, Mac Helper, MIDI, or general application settings.

E. Confirmed historical purpose

Confirmed source-history evidence:

• Repair was introduced in commit c6fdd0e, dated 2026-05-19, titled “repair document added.”
• The initial commit added Repair together with stored per-document grid dimensions and continuation-token reconstruction.
• Grid-size and larger-button work occurred immediately before it.

The commit message does not state a user-facing problem. The code establishes that its purpose was to repair malformed screen-grid storage, especially the @@wide and @@block continuation markers used by multi-cell buttons.

F. Current relevance

Still potentially useful, but only in rare cases:

• A hand-edited or externally damaged .screen file has missing, stale, or orphaned multi-cell continuation markers.
• A legacy/imported screen has inconsistent button-grid storage.
• A screen has malformed blank/continuation lines and must be normalized into a loadable grid layout.

It is not needed for:

• Fresh installations.
• Ordinary screen editing.
• Normal app restarts.
• Normal import/export or full-backup restoration.
• Missing .config.json files.
• Ordinary loading of valid screens.

G. Automatic recovery comparison

Automatic recovery exists, but it is different:

• On launch, ContentView ensures at least one default screen file exists when no screen files are present: ContentView.swift:488-522.
• During document refresh, ContentView creates missing screen .config.json files from AppStorage/default data: ContentView.swift:524-563 and 1066-1087.
• When a screen loads, ContentView normalizes its lines in memory for display, but does not rewrite the document merely because it contains malformed continuation markers: ContentView.swift:694-715 and 811-824.
• Normal editor persistence writes only intentional user edits: ContentView.swift:875-904.

Therefore, Repair is the only code path that rewrites an existing screen specifically to reconstruct its stored button-layout markers.

H. Data safety risks

Repair can overwrite the selected screen document. The write itself is atomic, but the previous content is not retained by the app.

Specific risks:

• No confirmation is requested.
• No backup or undo is created.
• Lines after maxFunctionKeyCount are discarded.
• Orphaned or malformed continuation markers are replaced with _.
• A malformed larger-button layout can be reduced to individual 1×1 buttons.
• A user who intentionally stored unusual blank/continuation-line data can lose that exact formatting.

The normal save path protects against an external-file conflict or missing file before writing: Set_Screen.swift:2040-2124. If the on-disk document changed externally, Repair either reloads it and asks the user to check it, or prevents a conflicting write.

I. Repeat safety

For stable grid dimensions, Repair is effectively idempotent: after its reconstructed output is saved, a second run should report “Document checked.”

It is not reversible within the app, because it does not preserve the pre-repair content.

J. User-visible feedback and error handling

Feedback:

• “Select a text file to repair” when no selected document is available.
• “Document repaired” when text changed.
• “Document checked” when no change was required.
• “The file changed outside ESP and was reloaded. Check it before repairing.”

The feedback is a custom modal overlay with an OK button: Set_Screen.swift:1032-1073.

There is no progress UI, no confirmation dialog, and no repair-specific error message for conflict, missing-file, or failed-save cases. Those cases rely on the normal document-save alerts or silently stop within repairDocument’s final switch.

The work is synchronous in the toolbar button action. For normal screen sizes, this is likely brief; it is not dispatched to a background task.

L. Recommendation

RELOCATE.

Repair still has a legitimate narrow recovery purpose for malformed multi-cell screen layouts, so retiring the underlying mechanism would be speculative. However, it is destructive enough to be poorly suited to an always-visible, unexplained top-toolbar control for a public App Store user.

M. Smallest safe future change

Move only the existing Repair entry point out of the top toolbar into a clearly labelled advanced/recovery area. Preserve the current implementation initially.

Before exposing it publicly in another location, add a user explanation and confirmation that the selected screen will be normalized and overwritten without an automatic backup. That would be a separate scoped change.

N. Remaining uncertainties
