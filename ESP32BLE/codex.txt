3. Baseline capture

After loadFunctionKeys(from:) successfully reads a screen, ContentView now retains:

• loadedScreenBaselineURL: the exact URL that was loaded.
• loadedScreenBaselineText: the exact unmodified text read from disk.

The baseline is captured only after a successful String(contentsOf:) operation.

If loading fails:

• The baseline URL is cleared.
• The baseline text is cleared.
• No empty or stale text becomes a valid baseline.

Loading another screen replaces both baseline values.

4. URL association

Before saving, saveMainScreenText(_:) requires:

• A valid loaded baseline URL.
• A valid loaded baseline text.
• The baseline URL’s filename to match selectedDocumentName.

The cached document list is not used to establish the baseline or determine whether the loaded file still exists.

5. Disk comparison

Before writing, saveMainScreenText(_:) now:

• Verifies that the baseline exists and belongs to the selected screen.
• Checks the exact baseline URL with FileManager.fileExists.
• Reads the current file contents directly from disk.
• Compares the disk text with the proposed output and loaded baseline.
• Writes only when disk still matches the baseline.

Modification dates are not used.

6. Save-result handling

The private MainScreenSaveResult distinguishes:

• saved
• unchanged
• conflict
• missing
• failed

Disk unchanged:

• Proposed text is written.
• The exact successfully written text becomes the new baseline.
• Normal subsequent edits continue working.

Disk already equals proposed text:

• No write occurs.
• The verified disk text becomes the baseline.
• The requested slot state is applied.
• The operation succeeds without a false conflict.

Disk changed externally:

• No write occurs.
• The external file is preserved.
• The baseline is not replaced with stale local text.
• The operation returns false.

Disk deleted:

• The file is not recreated.
• No write occurs.
• The operation returns false.

Read or write failure:

• The operation returns false.
• The baseline is not updated.

7. Rejected-edit behavior

persistSlotLines(_:) continues to apply new slot lines only after a saved or synchronized result.

For conflict, missing, or failure:

• The proposed slot lines are not applied to ContentView.
• The previously displayed screen state remains visible.
• The disk file remains untouched.
• A warning clearly states that the attempted edit was not saved.

This uses the safe rollback behavior permitted by the specification. No external replacement is automatically loaded over the visible screen. Navigating away and returning will use the normal disk-loading path.

8. Caller-result corrections

Three existing wrappers previously discarded persistSlotLines(_:) failure:

• Grid resize always returned true.
• Tile movement returned its new anchor.
• Slot duplication always returned true.

They now propagate rejection:

• Resize returns false.
• Movement returns nil.
• Duplication returns false.

The existing restoration, undo, redo, cut, paste, delete, and direct slot-edit paths already receive the persistence Bool result through their existing callback structures.
