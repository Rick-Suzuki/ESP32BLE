B. Current Template selection state

The selected Template is stored in SettingsScreen as:

selectedTemplateURL: URL?

Single tap calls selectTemplateForDescription(_:), which:

• Assigns selectedTemplateURL.
• Loads the template configuration.
• Loads its description, no-description state, or unavailable state.
• Causes the description panel to update.

The state is already temporary and nonpersistent.

C. Current selected-row colour

In Set_Table.swift lines 786–810:

• Selection identity uses standardized URL equality:
selectedTemplateURL?.standardizedFileURL == templateURL.standardizedFileURL

• Selected text is bold:
.fontWeight(isSelected ? .bold : .regular)

• Selected text is currently green:
.foregroundStyle(isSelected ? Color.green : .white)

• The row background remains black in both states.

Therefore, the green/yellow change affects text colour only. It does not alter the row background, dimensions, separators, alignment, IDs, or scrolling.

D. Current gestures

The Template gesture is already exclusive:

• Lines 788–800 use TapGesture(count: 2).exclusively(before: TapGesture(count: 1)).

Single tap:

• Plays ButtonClickFeedback.
• Calls selectTemplate(templateURL).
• Does not install the template.
• Does not show a notification.

Double tap:

• Plays ButtonClickFeedback.
• Calls selectTemplate(templateURL).
• Calls applyTemplate(templateURL).
• Does not also execute the single-tap gesture branch.

Accessibility follows the same behavior:

• Default accessibility action selects.
• Named “Apply Template” action selects, then applies.

E. Installation and notification path

Double tap calls prepareTemplateApplication(_:), which:

• Validates the template and selected target screen.
• Saves the current screen if appropriate.
• Creates pendingTemplateApplication.
• Presents the existing confirmation alert.

After confirmation:

• applyPendingTemplate() calls the injected applyTemplate closure.
• ContentView applies the template to the selected screen.
• Settings reloads the selected document text.
• Settings displays “Template applied”.

The existing installation feedback is green because the Settings-level feedback overlay uses .foregroundStyle(.green) at Set_Screen.swift line 1701.

Single selection has no notification. Notification styling is independent of the Template row colour.

F. Smallest safe implementation

A single substitution in Set_Table.swift line 806 is sufficient:

Current:
.foregroundStyle(isSelected ? Color.green : .white)

Recommended:
.foregroundStyle(isSelected ? Color.yellow : .white)

This preserves:

• Existing selectedTemplateURL identity.
• Bold selected text.
• Exclusive gesture behavior.
• Description loading.
• Template application and confirmation.
• Accessibility selected trait.
• Row IDs, swipe-to-delete, layout, and scrolling.
• Existing notifications.

No new selection state is needed.

G. Selection lifecycle

Current behavior already matches a temporary selection model:

• Selecting another Template replaces selectedTemplateURL, so the prior row becomes white.
• Switching away from Templates and back in the same Settings session retains selection and description.
• Closing Settings destroys the SettingsScreen instance, so the @State selection is cleared on reopening.
• Installing a Template leaves the selected Template selected; this is current behavior and need not change for the colour-only correction.
• Deleting a selected Template calls refreshTemplateFiles(), which clears selection if that standardized URL no longer exists.
• Template refresh similarly clears an unavailable selected Template at Set_Screen.swift lines 2805–2813.

There is no Template rename path identified in the inspected code. If an external rename/removal is followed by template refresh, the existing unavailable-selection cleanup applies.
