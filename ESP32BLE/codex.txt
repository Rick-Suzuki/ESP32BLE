2. Space token normalization:

If token is "sp", it returns literal " ".
If token is already literal " ", it falls through and returns original sendText at line 1428.

Existing Mac Helper Space representation:

In this repo snapshot, I found no Mac Helper implementation/parser source. The workspace contains only the iOS sender side and logs/notes.

No occurrence of KEY:SPACE was found in the project.
The iOS sender currently emits KEY:RETURN, KEY:BACKSPACE, KEY:UP/DOWN/LEFT/RIGHT, KEY:F-number, and KEY:letter, but never KEY:SPACE.

So from available repo evidence:
• Existing iOS-side protocol style strongly suggests KEY:SPACE would be the natural representation.
• I cannot confirm the actual Mac Helper parser already supports KEY:SPACE because that parser is not present in this workspace.
• There is no evidence in this repo that KEY:SPACE is currently supported or emitted.

Smallest proposed fix, not implemented:

On the iOS sender side:
• Preserve literal single-space tokens in MacConnectionManager.macMessages(from:) instead of trimming them into empty.
• Convert a literal space token to KEY:SPACE in MacConnectionManager.macMessage(for:modifiers:) or equivalent conversion logic.

On the Mac Helper side, if not already supported:
• Add KEY:SPACE to the existing KEY parser/special-key mapping, alongside KEY:LEFT, KEY:RETURN, KEY:BACKSPACE, etc.
• It should map to the platform’s Space key event, not text framing or auth/network logic.

No networking, LF framing, authentication, Bluetooth, timing, function-key handling, UI, or refactor changes are implicated.

Other tokens with the same silent-drop problem:

From the iOS sender path, anything that reaches MacConnectionManager.macMessages(from:) as whitespace-only is silently dropped by the same condition:

• literal " "
• SP / sp after normalizedBluetoothSendText converts it to " "
• literal tab "\t", if it ever reaches this path as a token
• literal newline "\n" or other whitespace-only token, if it ever reaches this path as a token

Other Bluetooth-supported ASCII tokens do not appear to be silently dropped by the iOS Mac sender. Unknown tokens fall through to:
ContentView.swift:625
TEXT:<token>

Potential Mac-mode mismatches that are not silent drops:
• TAB token becomes TEXT:TAB, not KEY:TAB.
• ESC token becomes TEXT:ESC, not KEY:ESC.
• keypad tokens like kp0, kp1, kp/, kp*, kp-, kp+, kp. become TEXT:kp0 etc. without modifiers, or CTRL+KP0 style strings with modifiers.
• Whether those work depends on the Mac Helper parser, which is not present here.

Main conclusion:

The space is not lost in generation. It is lost in MacConnectionManager.macMessages(from:) at ContentView.swift:575-578 because whitespace trimming converts " " to "", and the empty-string guard skips it before any Mac command is generated. LEFT succeeds because it survives trimming and has an explicit KEY:LEFT mapping.
