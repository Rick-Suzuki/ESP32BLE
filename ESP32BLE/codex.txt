1. EXECUTIVE SUMMARY

CONFIRMED SOURCE FINDING:

The reported stale-editor behaviour is explained by the current source.

A successful replacement import:

1. Replaces Widgets.screen on disk.
2. Refreshes the cached file arrays.
3. Calls ContentView.loadFunctionKeys(from:) for the imported screen.
4. Reloads Main Screen state from the replacement file.
5. Leaves the Settings editor unchanged when the selected filename and file-list paths remain the same.

The Settings editor currently reloads in response to:

• Initial Settings task execution.
• documentFiles.map(.path) changing.
• selectedDocumentName changing.
• The Settings list mode changing.
• Explicit text-file selection.

A same-filename replacement changes the file contents but not its path or selected filename. Therefore, none of the relevant Settings editor observers is guaranteed to fire.

This explains why:

• Settings continues showing the old text.
• Main already contains the imported version.
• Selecting another screen and returning reloads the editor correctly.
• Returning to Main displays the imported version.

The smallest safe correction is in Set_Screen.swift: after a successful document import or replacement, explicitly reload the Settings editor when the successfully imported destination URL is the document currently loaded by the editor.

12. DIFFERENT-FILENAME IMPORT

CONFIRMED SOURCE BEHAVIOUR:

finishPendingImportSession(_:) stores the first successfully imported screen URL in session.firstImportedDocumentURL and calls loadFunctionKeys(firstImportedDocumentURL).

If Another.screen is imported while Widgets.screen is selected:

1. ContentView loads Another.screen.
2. selectedDocumentName changes from Widgets.screen to Another.screen.
3. The Settings selectedDocumentName observer runs.
4. It safely processes the old editor through saveCurrentDocumentText().
5. If the transition is permitted, loadSelectedDocumentText() loads Another.screen.

Thus, a different filename has an existing selection-change signal that a same-filename replacement lacks.

13. DIRTY EDITOR BEHAVIOUR

The editor uses immediate automatic saving:

.onChange(of: documentEditorText) {
guard !isLoadingDocumentText else { return }

saveCurrentDocumentText()

}

Lines 524–527.

Therefore, under normal successful operation, there is not a prolonged unsaved editor state: text changes immediately pass through the protected save function.

A genuinely locally modified but unsaved state can still exist when:

• A save fails.
• A disk conflict is detected.
• A blocked save result prevents the write.
• State changes occur around an import or alert transition.

Current replacement import does not ask saveCurrentDocumentText() to validate the editor before replacing the destination. The explicit Replace Existing action directly performs the import replacement.

After successful replacement, if the old editor remains visible:

• documentEditorText contains the pre-import text.
• savedDocumentEditorText contains the pre-import baseline.
• The disk contains the imported text.

The next protected save compares all three.

If the old editor has no local changes:

LOCAL == BASELINE
DISK != BASELINE

saveDocumentText(_:to:) reloads disk into the editor and returns .reloadedFromDisk.

Lines 1604–1609.

If the editor contains local changes:

LOCAL != BASELINE
DISK != BASELINE
DISK != LOCAL

saveDocumentText(_:to:) sets .conflict, presents File Changed Externally, and does not overwrite the import.

Lines 1612–1615.

Thus, current F2B protection prevents the stale editor from silently overwriting the imported version.

However, it does not proactively update the editor immediately after the explicit replacement.

RECOMMENDATION:

The import correction should not call saveDocumentText(_:to:) after replacement. That would treat an intentional replacement import as an external conflict when local text differs.

Instead, after successful explicit Replace Existing, the imported disk version should be deliberately loaded into the editor and installed as the new baseline. This is consistent with the stated rule that a successful explicit replacement import is authoritative.

15. MINIMUM SAFE CORRECTION

Recommended file:

ESP32BLE/ESP32BLE/Scrns/Set_Screen/Set_Screen.swift

No ContentView change is necessary.

Preferred correction point:

recordSuccessfulImport(...)
Lines 3013–3053

Why this is the safest small central point:

• It executes only after the file operation succeeds.
• It receives the actual destination targetURL.
• It knows the ImportedContentKind.
• It covers normal screen import and full-backup replacement.
• It does not run after an import failure.
• It avoids relying on selectedDocumentName changing.
• It avoids relying on the cached path list changing.

Recommended behaviour:

After recording a successful document import:

1. Check contentKind == .document.
2. Check that targetURL identifies the same file as loadedDocumentURL.
3. If so, call the existing loadSelectedDocumentText().
4. Let loadSelectedDocumentText() update:
   • documentEditorText
   • savedDocumentEditorText
   • loadedDocumentName
   • loadedDocumentURL
   • blockedDocumentSaveResult
5. Do not invoke the protected save path first.
6. Do not write editor contents to disk.

A small helper could make the intent explicit, for example:

reloadEditorAfterSuccessfulImportIfNeeded(at:)

The helper should:

• Compare standardized destination and loaded URLs, or otherwise use a reliable same-file comparison.
• Do nothing for images, sounds, PDFs, configurations, or unrelated screen files.
• Reload only after successful document installation.
• Use the existing loading logic and isLoadingDocumentText protection.

Alternative correction point:

importReplacingExistingFile(...)
Lines 3179–3231

Reloading there immediately after a successful document replacement would also fix the reported case. However, recordSuccessfulImport(...) is more central and also covers successful non-conflict imports that resolve to the currently loaded identity.

Important implementation detail:

The reload must be performed before any later observer can interpret the old editor buffer against the new disk contents. The loader updates the editor and baseline together under isLoadingDocumentText, preventing recursive autosave.

16. IMPORT FAILURE BEHAVIOUR

If replacement import fails:

• recordSuccessfulImport(...) is not called.
• recordImportFailure(...) records the failure.
• renameAlertMessage reports the problem.
• The proposed reload would not run.
• Existing editor text and baseline remain unchanged.

This satisfies the requirement that a failed import must not replace the visible editor contents.

The new uniquely named file does not equal loadedDocumentURL, so the current editor remains unchanged until the existing selection mechanism selects another screen.

20. REMAINING RISKS

CONFIRMED:

The normal screen-import replacement removes the destination before installing its replacement. A failed import after deletion could leave the destination absent. This is separate from the stale-editor issue.

RECOMMENDATION:

Do not broaden F2C.3 into an atomic-import rewrite. The editor refresh can be corrected independently and minimally.

Care is also required not to reload an unrelated selected editor merely because some other document was imported. The target destination must match the editor’s loaded URL.

A full-backup import can replace several files. The correction should evaluate each successfully imported document rather than assuming only session.firstImportedDocumentURL matters.

No source changes were made during this investigation.
