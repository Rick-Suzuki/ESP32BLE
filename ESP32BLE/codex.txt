MIDI-010A-FIX — READ-ONLY PARSING INVESTIGATION

1. Exact root cause

The observed behavior matches the previously compiled MIDI parser, not the current source in the working tree.

The rejecting condition in the previous implementation was:

components.count == 2

That implementation accepted only:

.midi <note>

It rejected:

.midi <note> <velocity>

When the parser rejected the three-component command, the grid created a normal button instead of MIDITouchView. Tapping that normal button called sendMainGridEntry(:), where isMIDICommandForGridEntry(:) deliberately suppressed anything beginning with “.midi”. Consequently, the command produced no ESP32BLE command log, sent nothing to ESPMacHelper, and played no note.

The current uncommitted source already changes the condition to:

components.count == 2 || components.count == 3

Therefore, the reported runtime behavior strongly indicates that the device is running a build made from the earlier exact-two-component implementation.

2. Complete parsing and routing path

Stored command loading:

ContentView.swift
normalizedSlotLines(from:) reads stored slot lines.
applySlotLines(_:) stores them and calls normalizedFunctionKeys(from:).
normalizedFunctionKeys(from:) calls functionKeyEntry(from:) for each slot.
functionKeyEntry(from:) separates action text from optional display metadata using “::”.
parsedSendTexts(from:) calls parsedActionTokens(from:) for MIDI commands.
parsedActionTokens(from:) splits on colons, not whitespace.

Therefore:

“.midi 60” becomes:
sendTexts = [“.midi 60”]

“.midi 60 100” becomes:
sendTexts = [“.midi 60 100”]

“.midi 60 30” becomes:
sendTexts = [“.midi 60 30”]

No command is rejected in ContentView.swift, and each command becomes a FunctionKeyEntry containing exactly one sendTexts element.

Grid construction:

Main_Screen.swift
mainGridSection(...) passes:

midiCommandForGridEntry
sendMIDINoteOnFromTouch
sendMIDINoteOffFromTouch

to MainScreenGridSection.

Main_GridSection.swift
gridButtonView(...) calls midiCommand(entry).

If parsing returns a note and velocity, it creates MIDITouchView. Its onDown closure captures midiCommand.velocity and calls:

onMIDITouchDown(note, midiCommand.velocity)

If parsing returns nil, execution falls through to the normal Button implementation. That button calls sendMainGridEntry(entry).

Normal-button MIDI suppression:

Main_ButtonBehavior.swift
sendMainGridEntry(:) first calls isMIDICommandForGridEntry(:).

That classifier recognizes any send text whose first whitespace-separated component is exactly “.midi”. It does not validate argument count.

If recognized, sendMainGridEntry(_:) returns immediately. This prevents malformed MIDI commands—and MIDI commands that failed the touch parser—from falling through to normal keyboard or text transmission.

This early return also occurs before the normal button-command logging block, explaining why rejected explicit-velocity commands do not appear in the ESP32BLE console.

4. Velocity-passing verification

The current source passes velocity correctly throughout the touch path.

midiCommandForGridEntry(_:) returns:

(note: Int, velocity: Int)

Main_GridSection.swift captures midiCommand.velocity in the MIDITouchView onDown closure:

onMIDITouchDown(note, midiCommand.velocity)

Main_Screen.swift connects onMIDITouchDown directly to:

sendMIDINoteOnFromTouch

sendMIDINoteOnFromTouch(_:velocity:) validates velocity in 1...127 and constructs:

MIDI:NOTE_ON:<note>:<velocity>:1

No incorrect optional handling or closure capture was found.

No velocity is stored inside MIDITouchView itself, but this is intentional: the surrounding closure captures the parsed velocity and supplies it when touch-down occurs.

6. Smallest recommended fix

The smallest source correction is to allow either two or three whitespace-separated components in the MIDI grid parser, parse the third component as velocity when present, and retain 100 as the default when omitted.

That correction is already present as an uncommitted change in the current ESP32BLE working tree.

No additional parsing, routing, gesture, touch, polyphony, Note Off, editor, template, backup/restore, or ESPMacHelper change is indicated.

To make the current source behavior reach the device, ESP32BLE must eventually be rebuilt and installed. No build was performed during this investigation, as requested.

The correction is limited to ESP32BLE. ESPMacHelper is not responsible for the command disappearing before the iOS console and touch callback.

7. Regression risks

The parser should continue requiring exactly one FunctionKeyEntry sendTexts element.

Valid notes must remain restricted to 0...127.

Explicit velocity must remain restricted to 1...127.

Missing, malformed, out-of-range, or extra arguments must continue returning nil.

The case-sensitive “.midi” classification must remain consistent between midiCommandForGridEntry(:) and isMIDICommandForGridEntry(:).

The suppression in sendMainGridEntry(_:) should remain. Removing it would risk sending malformed MIDI command text through the normal keyboard-output path.

The two-component form must continue defaulting to velocity 100.

No touch-handling change is required.
