A. WIDGET ARCHITECTURE SUMMARY

1. Screen-file parsing and stored representation

File:
ESP32BLE/ESP32BLE/Scrns/ContentView.swift

Important locations:

• FunctionKeyEntry: lines 67–82
• functionKeyEntry(from:): lines 2582–2628
• parsedSendTexts(from:): lines 2630–2644
• widget-command recognition list: lines 2646–2656
• parsedWidgetSendTexts(from:): lines 2658–2695

A screen line is stored literally in FunctionKeyEntry.rawLine.

The parser derives:

• sendTexts: commands/actions from the left side
• alternateDisplayText: visible text or symbol configuration from the right side
• buttonColorCode
• visibility flags

The format is effectively:

command or action :: alternate display text

If there is no “::”, the entire line becomes both rawLine and a single sendTexts entry.

Widget identifiers are not stored separately in the .screen file. They are reconstructed dynamically by inspecting sendTexts.

Consequences:

• Command names are stored literally.
• Renaming commands without aliases would break existing screens.
• Default labels are generated dynamically from rawLine/sendTexts.
• Adding an alias is safer than renaming an existing command.

Does the preview problem occur with explicit “file”?

• file spk.txt should preview if the file exists in Documents or the bundle and is UTF-8 readable.
• file aces2.jpg should preview if UIImage can decode it.
• file macshortcuts.pdf previews only if it is a one-page PDF that renders successfully.
• A multi-page PDF is a confirmed unsupported path in the current implementation.

If an explicitly commanded TXT or JPG still does not preview, device testing is required to inspect filename, location, case, file availability, or decoding.

Is automatic filename recognition safe?

Not as a blanket extension rule.

Reasons:

• Ordinary button text may legitimately end in .txt, .pdf, or .jpg.
• Legacy screen/navigation handling already gives .txt special historical meaning in parts of the code.
• Sound files are already recognized by extension without “file”.
• .rnd filename.txt uses .txt for a different widget.
• “spk filename.txt” has separate semantics.

Smallest safe future approach:

Do not interpret every extension automatically. If desired, use a narrow rule that requires both:

• a supported preview extension, and
• a successful lookup of an existing regular file,

while excluding known command contexts.

Even that should be tested carefully against ordinary button text.

Regression risk:
HIGH for blanket automatic recognition.
MEDIUM for existence-checked, context-aware recognition.

C. SHARED ROOT CAUSES

1. Widget rendering takes precedence over SF Symbol rendering

Main_ButtonLabelView.swift lines 127–144 checks widgetDescriptor first.

Consequences:

• stopwatch symbol name becomes visible text
• add symbol name becomes counter configuration/title
• minus symbol syntax including colon becomes title text
• power ignores symbol and ordinary text
• random/timer/ambient may have similar symbol/title inconsistencies

This is the main shared display cause.

2. Editor preview and actual button use different rendering paths

Editor:
Main_Screen.swift lines 4129–4297

Actual button:
Main_ButtonBehavior.swift lines 1518–1574
Main_ButtonLabelView.swift lines 53–390

The editor validates and renders SF Symbols directly.
The actual widget often treats the same right-side value as widget configuration or title.

This explains “correct preview but incorrect Main Screen” behavior.

3. Command definitions are duplicated

Widget recognition is duplicated in:

• ContentView.swift lines 2646–2656
• Main_ButtonBehavior.swift lines 1298–1307

Any alias must currently be added in both places and in the descriptor switch.

Risk: partial changes can make a command parse differently during screen loading and runtime recognition.

4. Help/editor command examples disagree with runtime syntax

Examples:

• Runtime requires .rnd; help inserts rnd.
• Runtime requires .add; help inserts add.
• Runtime requires .minus; help inserts minus.
• Runtime requires .power; help inserts power.
• Help advertises .prev/.next/.back/.forw, while runtime accepts only unprefixed versions.

This is a second shared root cause, separate from display rendering.

5. Colon has multiple meanings

Colon is used for:

• chained commands
• SF Symbol subtitle separation
• widget configuration/title separation
• display modes

A general colon-removal fix would be unsafe.
