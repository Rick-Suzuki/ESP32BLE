C. Main-grid call path

Normal button tap:

Main_GridSection.swift button action
→ sendLine(entry)
→ sendMainGridEntry(entry:defaultMIDIChannel:)
→ local sendBluetoothIfNeeded()
→ sendKeyboardOutputTokens(_:respectsButtonMode:)
→ ESPOutputProbe.printGeneratedItems(_:)
→ [ESP-OUTPUT]

Mac Helper mode then continues:

sendKeyboardOutputTokens
→ macConnection.sendSmartScriptKeyboardTokens(_:)
→ sendKeyboardMessages(_:)

→ [ESP-MAC-TX]

ESP32 mode then continues:

sendKeyboardOutputTokens
→ ble.sendLine(_:)
→ BLE outgoing queue.

Command chains

One originating button can produce multiple [ESP-OUTPUT] events:

• Multiple generated keyboard tokens in one output call.
• Separate modifier-plus-key command batches.
• Wait-chain command output after one or more delays.

A source snapshot passed alongside each output batch would reliably associate all generated events with the originating button.

F. BLE versus Mac Helper behavior

CONFIRMED

[ESP-OUTPUT] is shared by both output modes. It is emitted before the output-mode switch in sendKeyboardOutputTokens, at line 1196.

Therefore it logs generated keyboard items for:

• Mac Helper mode
• ESP32 BLE mode
• Even .none output mode, before the not-connected alert is shown

[ESP-MAC-TX] is Mac Helper transport-specific. It logs all framed Mac traffic, including authentication frames, and has no originating button metadata.

BLE does not use [ESP-MAC-TX].

G. Smallest safe implementation approach

Recommended approach, not implemented:

1. Add an optional immutable source diagnostic value to the shared output path, rather than global mutable “current button” state.

2. Pass that optional value into ESPOutputProbe.printGeneratedItems.

3. Form the value from the originating FunctionKeyEntry before asynchronous work begins:
• SF Symbol name from parsedSFSymbolDisplay(for:)?.name
• button text from parsedSFSymbolDisplay(for:)?.subtitle
• no metadata when the entry is not an SF Symbol button, or when no source entry exists.

4. Thread the optional source information through:
• direct main-grid activation
• speech-recognition activation
• wait-chain execution, using its existing sourceEntry
• timer completion, where an entry is already supplied

5. Leave editor Preview/Play, keyboard screen, modifier helper, and non-button sources without source-button metadata.

This avoids deriving display values from the command, avoids changing transport behavior, preserves existing output numbering, and avoids metadata being overwritten by another button while delayed tasks are running.

Do not use a shared mutable currentSourceButton property. Concurrent button presses and asynchronous wait chains could then label output from one button with another button’s SF Symbol/text.

H. Regression risks and tests

Manual regression areas:

• Normal main-grid SF Symbol button:
• Verify [ESP-OUTPUT] includes the expected SF name and subtitle.
• Verify command and [ESP-MAC-TX] payload are unchanged.

• Normal text-only button:
• Confirm a defined no-SF metadata format, such as omitted fields or explicit nil/empty fields.

• Speech-triggered SF Symbol button:
• Confirm source metadata identifies the matched button, not recognized text or command text.

• Two rapid button presses:
• Confirm each output event retains its own source metadata.

• Wait chain:
• Press one SF Symbol button containing .wait.
• Press another button before the delay expires.
• Confirm delayed output still identifies the original button.

• Multi-token command:
• Confirm every [ESP-OUTPUT] event from that button has consistent source metadata.

• Timer completion:
• Confirm its output metadata reflects the intended originating entry, or is deliberately omitted if it represents a separate generated action.

• Mac Helper and BLE modes:
• Confirm [ESP-OUTPUT] formatting is correct in both modes.
• Confirm [ESP-MAC-TX] remains unchanged.

• Keyboard screen, Preview/Play, modifier helper, MIDI:
• Confirm they retain their current output behavior and do not receive misleading button metadata.
