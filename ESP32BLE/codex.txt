1. ROOT CAUSE OR BEST-SUPPORTED HYPOTHESIS

Best-supported source hypothesis:

The G6 metadata itself appears to transfer correctly through repeated Undo/Redo. The likely disappearance path is the G6 Resize-specific restore validation in refreshMainGridActionMenuTargetAfterSnapshotRestore(preferredButtonAnchor:).

For Resize Undo/Redo, that helper now does this:

• Restores snapshot.
• Uses stored resize anchor.
• Requires that anchor to be a real button.
• If validation fails, calls dismissMainGridActionMenu().

That is the only Resize Undo/Redo path I found that can explicitly make the popup disappear.

Source-confirmed: there is no retry after this validation failure. If the stored anchor is temporarily or actually not considered a button at that moment, the popup is dismissed immediately.

Runtime confirmation needed: whether the intermittent case is caused by a genuinely invalid stored anchor, a state/render ordering issue, or a visible-count/grid-boundary edge case.

8. WHETHER STALE CALLBACKS CAN INTERFERE

Confirmed from source:
• A stale callback for a different index is ignored because refresh index must match rendered target index.
• A stale callback for the same index can be accepted because there is no refresh-generation check in refreshPendingActionMenuFrameIfPossible(...).
• That would more likely cause a stale frame than full disappearance.
• If guard validation fails inside the pending refresh callback, it cancels pending refresh but does not dismiss the popup.

The explicit disappearance still points more strongly to the validation branch in refreshMainGridActionMenuTargetAfterSnapshotRestore(...).

10. WHY THE POPUP DISAPPEARS

Best-supported explanation:

During repeated Resize Undo/Redo, refreshMainGridActionMenuTargetAfterSnapshotRestore(preferredButtonAnchor:) occasionally rejects the stored anchor and calls dismissMainGridActionMenu().

The exact rejection can be one of:
• stored anchor is outside visibleBoxCount
• stored anchor is outside functionKeys
• stored anchor is a continuation token
• stored anchor is blank/empty according to mainGridIndexContainsButton

The source does not prove which condition is hit at runtime. Because the button geometry is reported as correct after the operation, the likely issue is not document restoration; it is that the popup restore path treats any immediate validation miss as fatal and dismisses instead of preserving the current popup while awaiting/attempting a rendered-frame refresh.

Why single Undo/Redo usually works:
• The restored anchor is normally valid immediately, so the helper schedules refresh and the popup follows.

Why repeated operations expose it:
• Repeated Undo/Redo rapidly replaces pending refresh state and repeatedly validates anchors during state transitions. Any one validation miss causes an immediate permanent popup dismissal.

11. SMALLEST RECOMMENDED CORRECTION

Do not change popup geometry.

Recommended future fix:
• Modify refreshMainGridActionMenuTargetAfterSnapshotRestore(preferredButtonAnchor:).
• For Resize-preferred anchors, do not immediately call dismissMainGridActionMenu() on button-validation failure.
• Instead, preserve the current mainGridActionMenuTarget and either:
   • leave the popup open with the last valid frame while waiting for a real rendered frame, or
   • cancel only the pending resize refresh and keep the popup target unchanged.
• Only dismiss when the target is structurally impossible, such as document mismatch, edit mode off, or explicit user dismissal.

A slightly stronger version:
• Add a refresh generation token to pending frame refresh state so stale same-index callbacks cannot satisfy a newer refresh.
• This is probably secondary; it addresses stale frame risk more than disappearance.

The smallest source-targeted correction is to avoid fatal dismissal for Resize-specific validation misses that may be transient, while still requiring a real button before replacing the popup target frame.
