Current behavior

The current blocking notification uses:

@State private var isRestoreCompleteAlertPresented = false

The alert presents:

• Restore Complete
• Your backup has been restored successfully.
• OK

beginRestoreAllFiles() resets the state before every restore.

finishPendingImportSession(_:) sets the state only after:

• Pending import state is cleared.
• Temporary extraction cleanup is attempted.
• Template discovery is refreshed when applicable.
• General file collections are refreshed.
• Any imported screen or selected resource updates are completed.

The existing success conditions are:

• importMode is .allFiles.
• importedAnything is true, enforced by the preceding guard.
• failedFileCount is zero.
• skipFileNameKeys is empty.
• skipTemplatePairKeys is empty.
• renameAlertMessage is nil.

Consequently, the alert is suppressed for ordinary imports, cancellation, invalid ZIPs, failures, partial failures and restores that skipped any ordinary file or template pair.

Existing timed notification infrastructure

Settings already has a suitable nonblocking notification mechanism:

• templateFeedbackMessage stores the visible text.
• templateFeedbackTask owns the dismissal operation.
• showTemplateFeedback(_:) cancels the previous task.
• The new message is displayed immediately.
• A new Task waits for two seconds.
• The task checks cancellation before clearing the message.
• The overlay uses allowsHitTesting(false), so it does not block Settings interaction.

This currently displays “Template applied” and “Template saved”.

The existing cancellation behavior prevents an older timer from hiding a newer notification:

1. The previous task is cancelled.
2. The new message replaces the old message.
3. The cancelled task exits without clearing the new message.
4. A new two-second task controls the new message.

Recommended minimal implementation

Reuse the existing banner rather than creating a second timer system.

The smallest behavioral change would be:

• Remove isRestoreCompleteAlertPresented.
• Remove the Restore Complete .alert modifier.
• Remove its reset from beginRestoreAllFiles().
• Keep the existing restore success condition unchanged.
• At that condition, call:
showTemplateFeedback("Restore Complete")

For clearer naming, the private infrastructure could be generalized to:

• settingsFeedbackMessage
• settingsFeedbackTask
• showSettingsFeedback(_:)

That rename would also update the two existing template-feedback call sites, but would not change their behavior.

Keeping the existing template-oriented names would produce a smaller diff, while generalizing them would make the shared purpose clearer. Either is technically safe.

Position and layout

The existing overlay is attached to SettingsDocumentTableSection and aligned to its top.

It appears:

• Below the Settings toolbar.
• Inside the table area.
• Above table content.
• Without changing layout height.
• Without affecting safe-area or toolbar geometry.
• Without intercepting touches.

This is a suitable interpretation of “near the top of Settings” and already works with the current iPhone/iPad table layout.

If the desired location is instead centered across the entire Settings width, a new outer overlay would be required. That would be a larger layout change and is unnecessary unless device testing shows the table-area placement is unsuitable.

Risks and device checks

• Backup, restore and template messages would share one slot. A newer message would intentionally replace an older one.
• A two-second message can disappear while the user is not looking at the table area, but this is expected for nonblocking feedback.
• The existing overlay has no explicit transition or animation; none is required.
• The table refresh changes importRefreshID, but the feedback state belongs to SettingsScreen rather than the table, so the message can be shown after refresh.
• Manual checks are needed for iPhone landscape, iPad mini and larger iPads to confirm the table-top position remains clearly visible.

Current export flow

1. The user selects Create Full Backup.
2. prepareArchiveExport() calls saveCurrentDocumentText().
3. It verifies hasArchiveExportContent.
4. makeFullArchiveData() creates the ZIP bytes.
5. SettingsArchiveFileDocument stores those bytes.
6. isExportingArchive becomes true.
7. SwiftUI presents fileExporter.
8. SettingsArchiveFileDocument.fileWrapper(configuration:) supplies the ZIP bytes.
9. The system writes the document to the destination selected by the user.
10. The fileExporter completion closure receives Result<URL, Error>.
11. Failures currently set renameAlertMessage.
12. exportArchiveDocument is cleared after completion.

Exact successful-save point

The correct success point is:

archiveExportPresenter’s fileExporter completion closure, when result is .success.

Generating archiveData is not sufficient. At that stage the user has not selected a destination and may still cancel.

Recommended completion handling

Change the completion closure conceptually to:

• .success:
show the shared “Backup Complete” feedback.
• .failure:
preserve the existing renameAlertMessage behavior.
• Always:
clear exportArchiveDocument.

The existing FileDocument fileExporter overload documents that:

• Its completion callback receives success or failure.
• If the user cancels, the completion callback is not called.
• SwiftUI clears isPresented before invoking completion.

Therefore, presenting “Backup Complete” only from the .success case will not show it on cancellation. Apple fileExporter documentation

What success guarantees

A successful callback means the system export operation completed and produced the destination URL. It is the appropriate application-level point for saying the backup was saved.

It does not guarantee that an iCloud or third-party File Provider has completed every subsequent server upload or cross-device synchronization step. Those activities can continue after the coordinated local/provider write succeeds.

The message should therefore mean “the export was successfully handed to and completed by the selected destination provider,” not “the cloud service has fully synchronized it everywhere.”

Recommended shared mechanism

Use the same feedback state and task for:

• Template saved
• Template applied
• Restore Complete
• Backup Complete

The existing task-cancellation logic already ensures that an older dismissal cannot erase a newer message.

No ZIP generation, filename, destination, file type or provider behavior needs to change.

Potential limitation

The current cancellation overload does not execute the completion closure on user cancellation. Consequently, exportArchiveDocument may remain populated after cancellation under the current implementation.

That is a separate cleanup concern and does not cause a false Backup Complete notification. It does not need to be changed for the requested notification behavior.

ESP-BACKUP-002-C — iOS 17 Move wording

Current export configuration

The Full Backup exporter uses one SwiftUI path on all supported iPhones and iPads:

.fileExporter(
isPresented: $isExportingArchive,

document: exportArchiveDocument,

contentType: archiveExportType,

defaultFilename: archiveExportDefaultFilename()

)

Configuration details:

• Document type: SettingsArchiveFileDocument conforming to FileDocument.
• Document payload: regular-file FileWrapper containing ZIP bytes.
• Content type: UTType(filenameExtension: "zip") ?? .data.
• Writable type: the same ZIP type.
• Filename: ESP_yyMMdd_HHmmss.zip.
• File dialog option: .displayFileExtensions.
• No platform-specific iOS 17 branch.
• No UIDocumentPickerViewController is used for Full Backup.
• Current deployment target: iOS 17.6.
• Current SDK: iPhoneOS 27.0.
• Supported devices: iPhone and iPad.

Does ESP specify “Move”?

No.

The source contains no “Move” or “Save” confirmation-button title for the exporter.

The only related file-dialog modifier is:

.fileDialogBrowserOptions(.displayFileExtensions)

That controls extension visibility, not confirmation wording.

Who supplies the wording?

The displayed confirmation title is supplied by Apple’s native Files/document-picker interface.

Apple’s UIKit documentation describes exporting a local document as selecting a destination where the picker either moves or copies the document. This underlying transfer terminology makes “Move” plausible for an export implementation that stages a local file before publishing it. UIDocumentPickerViewController documentation

However, the SwiftUI API does not document that iOS 17 must display “Move”, nor does it promise a particular confirmation-button title.

Could FileDocument or ZIP configuration cause it?

No source evidence indicates that the ZIP content type or default filename selects the word “Move”.

The FileDocument exporter necessarily supplies a FileWrapper which SwiftUI may stage as a temporary local document before invoking the system destination picker. It is plausible that iOS 17 exposes the underlying move-style wording for that implementation while newer systems present the more user-friendly “Save”.

That explanation is an inference from the framework architecture, not a documented Apple guarantee.

Is this a documented iOS 17 difference?

No official documentation was found stating that iOS 17 always labels SwiftUI fileExporter confirmation as “Move”.

The observation is confirmed on the reported iPad Pro, but it must be treated as an OS/device/provider-specific presentation behavior rather than a universal iOS 17 rule.

Can SwiftUI change the label on iOS?

Apple provides fileDialogConfirmationLabel(_:), but its documentation explicitly describes it as a macOS customization.

It is not a supported iOS mechanism for forcing the Files confirmation title to “Save”. Apple fileDialogConfirmationLabel documentation

Therefore, adding:

.fileDialogConfirmationLabel("Save")

would not be a supported iPhone/iPad correction.

Would UIKit change the wording?

UIKit offers:

UIDocumentPickerViewController(
forExporting: urls,

asCopy: true

)

The asCopy value changes whether the supplied local document is copied rather than moved. Apple UIKit initializer documentation

This might influence the system wording, but Apple does not document the exact button title. It therefore cannot guarantee “Save” on iOS 17.

Moving to UIKit would also require:

• Creating and managing a temporary ZIP URL.
• Presenting a UIViewControllerRepresentable.
• Implementing picker delegate handling.
• Distinguishing success and cancellation.
• Cleaning temporary files safely.
• Preserving Files and File Provider behavior.
• Testing iCloud Drive and third-party providers.
• Replacing a currently successful FileDocument workflow.

That is not a small wording-only correction.

Verified findings

• ESP does not set the Move label.
• There is one SwiftUI exporter path for iOS 17 and newer.
• The Full Backup is exported as a ZIP FileDocument.
• The export succeeds on the affected iPad.
• Apple controls the native iOS Files UI.
• The documented confirmation-label customization is macOS-only.
• No supported iOS property guarantees a “Save” label.
• The deployment target includes iOS 17.6.

Uncertainties

• Whether the label difference comes specifically from iOS 17, that iPad’s exact point release, or its selected Files provider.
• Whether the wording changes between On My iPad, iCloud Drive and a third-party provider.
• Whether the same OS/device displays a different title when exporting another FileDocument type.
• Whether a UIKit asCopy exporter would display Save, Copy or another system-selected title.

Recommended action

Retain the native SwiftUI fileExporter.

“Move” is cosmetically undesirable, but the operation is successful and there is no documented, small iOS API for replacing the label.

Replacing the exporter would add substantial lifecycle and provider risk for an unguaranteed wording change.

Smallest additional diagnostic

On the affected iOS 17 iPad Pro, export the same backup to:

• On My iPad
• iCloud Drive
• Any installed third-party File Provider

Record whether the label changes by destination.

Then repeat one destination on a newer iPadOS device.

This will distinguish an OS-wide presentation difference from provider-specific behavior without changing application code.

Final recommendation

Implement 002-A and 002-B together as one small Settings-only phase:

1. Generalize or reuse the existing timed feedback state.
2. Remove the Restore Complete Boolean and blocking alert.
3. Preserve the current restore success condition.
4. Show “Restore Complete” through the shared two-second feedback helper.
5. In fileExporter’s .success case, show “Backup Complete”.
6. Preserve the current failure handler.
7. Leave cancellation without feedback.
8. Keep the existing cancellation-safe task replacement behavior.
9. Do not alter ZIP creation, restore logic or file-provider integration.

Keep 002-C separate and make no exporter change unless further device testing identifies a reproducible provider-independent issue and Apple exposes a supported iOS control.

No files were modified. No formatter, export, restore, backup, project change or device test was performed.
