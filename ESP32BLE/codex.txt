6. Saving and file-operation dependencies

The displayed-title system is also part of filename editing, so it is not purely decorative.

currentTitleDisplayName is used for:

• The visible title.
• Initializing documentNameDraft on Settings appearance.
• Initializing the draft when title editing begins.
• Resetting the draft after loading editor contents.
• Resetting the draft after rename completion.
• Cancelling filename editing.

canEditCurrentTitle is category-dependent:

• Screens: active screen can be renamed.
• Images: selected image can be renamed.
• Sounds: selected sound can be renamed.
• PDFs: selected PDF can be renamed.
• Text: disabled.
• Plates: disabled.
• All Files: disabled.

commitNameEdit() is also category-dependent:

• Screens calls renameDocument.
• Images calls renameSelectedImage.
• Sounds calls renameSelectedSound.
• PDFs calls renameSelectedPDF.

Consequently, changing currentTitleDisplayName globally without considering title editing could make the control display the active screen while still renaming an image, sound, or PDF. That would be misleading and potentially unsafe.

Editor saving does not use currentTitleDisplayName or documentNameDraft.

Conflict-aware saving uses:

• loadedDocumentName
• loadedDocumentURL
• savedDocumentEditorText
• documentEditorText

saveCurrentDocumentText() resolves through fileURLForLoadedDocumentName() and verifies the loaded name and URL match. These values should remain untouched.

Other dependencies:

• Screen URL resolution uses selectedDocumentName and selectedDocumentFileURL.
• Save as Template uses the active selectedDocumentName and selectedDocumentFileURL.
• Apply Template uses selectedDocumentName as the expected target.
• Main reload uses ContentView’s selectedDocumentName and selectedDocumentURL().
• Screen rename uses ContentView.renameSelectedDocument.
• Screen deletion uses ContentView.deleteDocument and selects a fallback when deleting the active screen.
• Navigation history is owned by ContentView.
• Import/export logic has its own category and selected-file rules.
• Table highlighting uses category-specific selection state.

None of those authoritative values should be changed to solve this display issue.

7. Root cause

The root cause is currentTitleDisplayName in Set_Screen.swift, approximately lines 2466–2483.

It deliberately derives the top title from listMode:

switch listMode {
case .files:
return selectedDocumentDisplayName

case .text:
return selectedTextDisplayName

case .images:
return selectedImageDisplayName

case .sounds:
return selectedSoundDisplayName

case .pdfs:
return selectedPDFDisplayName

case .templates:
return "Templates"

case .all:
return "all files"

}

The top control therefore represents the selected item in the current category rather than the active screen.

The new Plates selection did not corrupt or replace selectedDocumentName. It merely made the existing category-dependent title behaviour more visible.

Set_Table.swift is not responsible for rendering the top filename.

8. Recommended minimal fix

The smallest safe correction belongs only in:

ESP32BLE/ESP32BLE/Scrns/Set_Screen/Set_Screen.swift

Recommended approach:

1. Add an explicitly named active-screen display property, or reuse selectedDocumentDisplayName directly:

private var activeScreenDisplayName: String {
selectedDocumentDisplayName

}

2. Use activeScreenDisplayName for the non-editing top label in both branches of settingsTitleControl(availableWidth:):

• Text(activeScreenDisplayName)
• SettingsUIKitVisualButton(title: activeScreenDisplayName, ...)

3. Do not change:

• selectedDocumentName
• loadedDocumentName
• loadedDocumentURL
• Category selection state
• Editor state
• Template selection
• ContentView callbacks
• Screen history

Important rename consideration:

The current top control is also the category-specific rename entry point. Merely changing its visible label while retaining image/sound/PDF rename behaviour would create a mismatch: the control would show “home” but could rename an image or sound when tapped.

The safest coherent implementation is therefore to make the top control semantically active-screen-only:

• Display activeScreenDisplayName in every category.
• Initialize documentNameDraft from activeScreenDisplayName.
• Make title editing target renameDocument, the active screen, regardless of category.
• Base title editability on selectedDocumentFileURL rather than the current category.

This preserves the active-screen source of truth and prevents a displayed active-screen name from invoking an unrelated asset rename.

However, the current top control appears to be the existing UI for renaming images, sounds, and PDFs. Converting it to active-screen-only would remove that category-specific rename entry point unless those rename actions exist elsewhere. No alternative rename control was found during this probe.

Therefore there are two implementation choices:

Minimal visual-only change:

• Show selectedDocumentDisplayName in the non-editing title.
• Keep existing category-specific rename state and functions.
• Smallest code change and preserves file operations.
• Risk: tapping the title in Images, Sounds, or PDFs temporarily changes the field to the category item and renames that item. The control’s display and action are semantically inconsistent.

Coherent active-screen-only change:

• Make display, draft, editability, and commit action all use the active screen.
• Safest interpretation of “the top filename always displays the active screen.”
• Requires deciding what happens to the existing image/sound/PDF rename access.

Recommendation:

Use the coherent active-screen-only version, but confirm whether category-specific image, sound, and PDF renaming may stop using this top control. If those rename workflows must remain available, they need a separate category-specific rename entry point; that is no longer a display-only fix.

No ContentView or Set_Table changes are needed because selectedDocumentName is already reliably available in Settings.

9. Regression risks

Changing the active screen while Settings is open:

• selectedDocumentName updates through ContentView.
• The corrected title will automatically update.
• The Settings editor already reloads through onChange(of: selectedDocumentName).

Returning from Settings to Main:

• No special handling is needed.
• selectedDocumentName remains authoritative.

Applying a template:

• Active filename remains unchanged.
• Corrected title remains unchanged.
• Main and Settings editor reload the replaced contents.

Saving a template:

• Uses selectedDocumentName and selectedDocumentFileURL.
• The title correction should not affect it.

Renaming the active screen:

• ContentView updates selectedDocumentName after successful rename.
• Corrected title should update automatically.
• Care is required not to disconnect documentNameDraft from the intended rename target.

Deleting the active screen:

• ContentView selects and loads its fallback screen.
• selectedDocumentName changes to that fallback.
• Corrected title should update automatically.

Creating or importing a screen:

• If the operation selects the new screen, selectedDocumentName provides the new title.
• If it merely adds a file, the title should remain unchanged.

Switching Settings categories:

• The corrected title remains derived from selectedDocumentName.
• Category-specific table selections and editor loading remain independent.

Refreshing file lists:

• The title remains stable unless refresh causes ContentView to replace a missing active screen with a fallback.

Screen single tap:

• Title remains unchanged.

Screen double tap:

• Title intentionally changes because the actual active screen changes.

Template browsing:

• Title remains unchanged.

Text, image, sound, PDF, Markdown, and All Files browsing:

• Title remains unchanged.

Primary risk:

• The top control currently combines display and category-specific rename behaviour. The eventual fix must keep its displayed identity and rename target consistent.

10. Implementation phase assessment

The visual correction can be implemented in one very small phase affecting only Set_Screen.swift.

A fully coherent correction can also remain one small phase if the top title is authorized to become active-screen-only for both display and rename.

If image, sound, and PDF rename access must remain exactly as it is, a product decision or separate rename control is required before implementation. That broader solution should not be guessed.
