2. New deletion helper

Added deleteTemplateDocument(at:fileManager:) in TemplateDocument.swift.

The helper:

• Accepts only .template URLs.
• Validates the containing directory.
• Requires the template to exist as a regular file.
• Uses templateConfigURL(forTemplateDocumentURL:) for its sidecar.
• Accepts a missing sidecar.
• Rejects a sidecar that exists but is not a regular file.
• Cannot target .screen or normal .config.json files.

Deletion sequence:

1. Creates a unique hidden staging directory beside the template.
2. Moves the template into staging.
3. Moves the sidecar when present.
4. Restores the template if sidecar staging fails.
5. Removes the staging directory only after all applicable files are staged.
6. Reports success only after final cleanup completes.

TemplateDeletionError distinguishes:

• Invalid template URL.
• Invalid parent directory.
• Missing template.
• Non-regular template or sidecar.
• Staging preparation failure.
• Staging failure with successful restoration.
• Critical rollback failure.
• Final cleanup failure.

Rollback never overwrites an existing destination. A rollback collision produces a critical rollback error.

If final cleanup fails, the recoverable staged files remain in the hidden staging directory and the operation reports failure.

3. Settings callback and reconciliation

Added deleteTemplate(_:) in Set_Screen.swift.

It:

• Calls deleteTemplateDocument(at:).
• Never calls the Screens deletion function.
• Refreshes template discovery after success.
• Clears the selected template and description through existing refresh reconciliation when the deleted template disappears.
• Preserves the Plates category.
• Does not modify selectedDocumentName, the Settings editor, Main Screen contents, or navigation history.

On failure it:

• Refreshes template discovery to reflect the actual filesystem state.
• Clears stale selection when necessary.
• Presents the existing native Settings error alert.
• Uses “Critical Template Deletion Error” for rollback failure.
• Never reports success after staging or cleanup failure.

7. Limitations and remaining risks

• Moving two files cannot form one atomic filesystem transaction.
• A critical filesystem failure can prevent rollback; this is reported distinctly.
• A final cleanup failure can leave recoverable files inside the hidden staging directory.
• No persistent recovery journal was introduced.
• Native List gesture arbitration and VoiceOver action ordering require device testing.
• No tests touched actual user templates.
