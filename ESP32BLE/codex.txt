1. EXECUTIVE SUMMARY

CONFIRMED SOURCE FINDINGS

Problem A — possible data loss:

The source contains a genuine stale-data overwrite risk.

A loaded screen is retained in memory in two places:

• ContentView.functionKeySlotLines
• SettingsScreen.documentEditorText

Neither representation records the file’s modification date, size, identity, hash, or original contents for conflict detection.

Several operations write these in-memory values directly over the selected .screen file without first checking whether the disk file changed externally.

The most significant risk is SettingsScreen:

• It loads the entire screen into documentEditorText.
• It saves on every documentEditorText change.
• It also saves unconditionally when the selected screen changes.
• It saves unconditionally when the Settings list mode changes.
• It saves before creating, repairing, or exporting.
• These saves do not compare documentEditorText with savedDocumentEditorText.
• They do not compare the current disk file with the version originally loaded.

Therefore, after iTunes replaces widgets.screen, a later Settings action can write the old editor contents back over that replacement.

ContentView’s grid-edit operations have the same conflict weakness. Moving, duplicating, editing, restoring, or resizing a button writes the cached functionKeySlotLines over the disk file without checking for an external replacement.

However, no source evidence shows that backgrounding or swiping the app away directly saves a .screen file. The only scenePhase handler performs keep-awake maintenance when the app becomes active.

Consequently:

• A stale overwrite is source-confirmed as possible.
• A termination-triggered save is not supported by the source.
• The exact interaction that caused the reported overwrite still requires device testing.

Problem B — file discovery:

The failure to show English.screen until restart is directly explained by the source.

The available screen list is cached in:

• ContentView.documentFiles
• ContentView.documentDirectorySnapshot

The Documents directory is scanned at startup and after application-controlled file operations. It is not rescanned when:

• The app enters the foreground.
• The Settings screen opens.
• The file-selection UI appears.
• iTunes adds or replaces a file externally.

On restart, the startup task scans Documents again, which makes English.screen appear.

10. OTHER FILE TYPES

.txt files

The Settings text editor uses the same documentEditorText and saveDocumentText mechanism.

Therefore, externally changed .txt files have a similar stale-editor overwrite risk if they are currently loaded in Settings.

Images, sounds, and PDFs

These are listed from the same cached documentDirectorySnapshot, so externally added files can remain invisible until a refresh.

They are not generally loaded as editable text and then automatically rewritten. Consequently, the specific stale-text overwrite mechanism does not apply to them.

They remain subject to explicit rename, delete, import, and replacement operations.

11. CONFIRMED ROOT CAUSES

CONFIRMED SOURCE FINDING 1

The app has no external-change detection before overwriting a loaded .screen file.

CONFIRMED SOURCE FINDING 2

SettingsScreen performs unconditional saves from cached editor contents on selected-file and list-mode transitions.

CONFIRMED SOURCE FINDING 3

Main Screen grid edits persist a complete cached slot array without verifying that the disk file is still the version originally loaded.

CONFIRMED SOURCE FINDING 4

There is no dirty-state guard in saveCurrentDocumentText(). savedDocumentEditorText exists but is not used to prevent unnecessary writes.

CONFIRMED SOURCE FINDING 5

The screen list and full Documents snapshot are cached and are not refreshed on foreground activation or external directory changes.

CONFIRMED SOURCE FINDING 6

There is no background or termination screen-save handler in the inspected source.

12. HYPOTHESES REQUIRING DEVICE TESTING

The most likely application-level explanations are:

• Settings was visible or mounted with old documentEditorText, and a list-mode or selected-screen transition triggered saveCurrentDocumentText().
• An editor state update triggered the documentEditorText onChange save.
• Returning from Settings invoked saveSelectedDocumentAndReload().
• A Main Screen edit, move, duplicate, resize, or undo/restore operation persisted stale functionKeySlotLines.

A pure sequence of:

• External replacement.
• No user or state-changing action.
• Background.
• Swipe-away termination.

does not contain a source-confirmed application save trigger.

Device testing is needed to determine whether:

• A particular Settings state change occurs implicitly during backgrounding.
• iTunes/Finder reports the replacement before it is fully committed.
• Another interaction occurred between replacement and termination.
• The running build differs from the inspected source.

13. SMALLEST RECOMMENDED FIX

Priority 1: Stop unnecessary Settings writes

The smallest immediate risk reduction is in:

ESP32BLE/ESP32BLE/Scrns/Set_Screen/Set_Screen.swift

Function:
saveDocumentText(_:to:), lines 1428–1436

Before writing, require the proposed text to differ from savedDocumentEditorText.

This would stop unchanged list-mode and selected-file transitions from rewriting the same cached text.

Advantage:

• Very small change.
• Eliminates many unconditional stale writes.
• Preserves actual in-app edits.

Limitation:

• If the user edits old cached contents after an external replacement, the text is dirty and would still overwrite the external file.
• It does not protect ContentView grid edits.

Priority 2: Add real conflict detection

When a screen or text file is loaded, retain a baseline representing that disk version. The safest minimal baseline is the loaded file contents, since the source already reads them.

Before any screen write:

• Read the current disk contents.
• Compare them with the baseline loaded into memory.
• If disk differs and the in-memory text is unchanged, reload from disk instead of writing.
• If both disk and memory changed, stop and present a conflict choice rather than silently overwriting.

A content comparison is safer than modification date alone because:

• Replacement utilities can preserve timestamps.
• Timestamp resolution can miss rapid changes.
• Atomic replacement can change file identity.

At minimum, both write funnels should be protected:

• ContentView.persistSlotLines(_:), lines 755–775.
• SettingsScreen.saveDocumentText(_:to:), lines 1428–1436.

saveSelectedDocumentAndReload(_:) should use the same protection or funnel through the protected Settings save path.

Priority 3: Refresh external files on foreground

Extend the existing scenePhase active branch in:

ESP32BLE/ESP32BLE/Scrns/ContentView.swift
lines 382–386

to call refreshDocumentFiles().

After refreshing:

• If the selected screen still exists and has changed externally while local state is clean, reload it.
• If the selected screen was deleted externally, select a valid fallback.
• If local state is dirty and the disk changed, do not silently reload or overwrite; surface a conflict.

Calling refreshDocumentFiles() alone fixes discovery of English.screen but does not update the displayed contents of an externally replaced widgets.screen.

Priority 4: Refresh when opening Settings

Calling refreshDocumentFiles() from showSettingsScreen(), lines 2773–2781, would ensure the file list is current before the editor opens.

This is useful as a secondary refresh point, but it should not replace foreground refresh.

FINAL CONCLUSION

Problem B has a definite source-level cause: the Documents directory is not refreshed after external changes.

Problem A has a definite source-level vulnerability: cached screen contents are written without dirty-state or external-change checks.

The source does not support the narrower conclusion that app termination itself performs the overwrite. The most credible application-side overwrite points are the unconditional Settings saves and full cached-grid writes that can occur before termination.
