B. Confirmed Settings initialization sequence

The initial Settings presentation is active from launch:

• ContentView initializes isSettingsScreenPresented as true at line 215.
• ContentView therefore creates SettingsScreen at lines 325–329.
• SettingsScreen initializes previewImageURL as nil at line 383.
• SettingsScreen onAppear calls restorePreviewFromAppliedBackground() at lines 401–403.
• That function calls selectPreviewImage(selectedImageURL) at lines 1538–1540.
• selectedImageURL depends on availableImageURLs.
• availableImageURLs depends on documentDirectorySnapshot, not ContentView.backgroundImageFiles.
• documentDirectorySnapshot begins empty at ContentView line 203.

C4-P corrected ContentView.backgroundImageFiles ordering, which fixes main-screen/per-screen background restoration. It does not guarantee that Settings’ separate documentDirectorySnapshot has been populated when Settings onAppear executes.

Later, ensureDefaultFunctionKeysFile() refreshes document files, causing documentDirectorySnapshot to become populated. At that point selectedImageURL can correctly resolve the applied image, so the IMAGE row becomes GREEN. However, Settings does not retry restorePreviewFromAppliedBackground() when the snapshot becomes available.

This exactly matches the observed state:

• Applied image row: GREEN, because selectedImageURL now resolves.
• previewImageURL: nil, because it was initialized/restored before image URLs existed and never restored again.
• BLACK row: YELLOW, because nil is a preview-only BLACK state while a different image is applied.
• Large preview: BLACK, because it renders previewImageURL, which remains nil.

C. Document snapshot interaction

The Settings observer is:

• Lines 407–412 in Set_Screen.swift.

Its current behavior is cleanup only:

• If previewImageURL is nonnil and no longer exists in availableImageURLs, it clears previewImageURL to nil.
• If previewImageURL is already nil, it does nothing.
• It never retries restorePreviewFromAppliedBackground().

Therefore, after the snapshot changes from empty to populated:

• A valid applied image becomes resolvable as selectedImageURL.
• The table correctly marks it GREEN.
• The preview remains nil/BLACK.
• No current callback repairs that initial preview state.

The snapshot cleanup observer does not itself clear a valid image preview after the image collection has populated. Its role is valid for deletion or external removal.

D. Applied-background resolution

selectedImageURL, in Set_ImgSelectionSupport.swift lines 20–37, resolves in this order:

1. Persisted complete path, if it is present in availableImageURLs.
2. Persisted filename, case-insensitively.
3. Persisted one-based image index.
4. nil/BLACK if none resolve.

Because availableImageURLs derives from Settings’ documentDirectorySnapshot, selectedImageURL is temporarily nil while that snapshot is empty, even though the persisted image selection and ContentView’s own background collection may already be valid.

Image sorting is consistent alphabetical filename sorting. There is no evidence that sorting or path identity causes this particular BLACK preview result.

F. Selected-document interaction

The selectedDocumentName observer at lines 404–406 unconditionally sets previewImageURL to nil.

This can also contribute during startup if selectedDocumentName changes after Settings has appeared. It likewise does not call restorePreviewFromAppliedBackground() afterward.

The empty document snapshot alone is sufficient to explain the observed result. The selected-document handler is an additional initialization-order risk because it can clear a correctly restored preview without a subsequent restore call.

G. Confirmed cause

Confirmed source cause:

• Settings preview restoration depends on documentDirectorySnapshot.
• The initial Settings view can restore before that snapshot contains files.
• selectedImageURL consequently resolves to nil.
• previewImageURL becomes nil/BLACK.
• Snapshot population later enables the applied row to become GREEN.
• No handler restores previewImageURL after that point.

This explains the exact GREEN applied-image / YELLOW BLACK / BLACK preview combination observed after relaunch.

H. Main-screen rendering remains independently unproven

The green Settings row proves that Settings can now resolve the stored applied selection after document snapshot population.

It does not prove that the main-screen UIImage was decoded and rendered successfully. ContentView intentionally clears loadedBackgroundImage while Settings is visible, at lines 669–676.

Physical verification should therefore include:

• Return to the main screen after relaunch.

• Then reopen Settings and confirm the same image is both GREEN and previewed.

I. Smallest safe correction recommendation

Only Set_Screen.swift needs to change.

Recommended approach:

• Treat preview restoration as pending only during Settings initialization and after a selected-document change.
• Restore preview from selectedImageURL once documentDirectorySnapshot becomes available.
• Do not use a blanket rule such as “if previewImageURL is nil, restore it,” because that would incorrectly overwrite an intentional user BLACK preview during a Settings session.

A minimal state-aware approach would be:

1. Mark initial preview restoration as pending when Settings appears.
2. Mark it pending when selectedDocumentName changes.
3. On documentDirectorySnapshot change:
• If restoration is pending, call restorePreviewFromAppliedBackground() after the snapshot is available, then clear the pending flag.
• Otherwise retain the current deletion cleanup behavior only.
4. User actions through Reset, Random, Previous, Next, IMAGE table single-tap, and BLACK row single-tap must clear or bypass the pending-initialization condition so intentional preview-only selection is never overwritten.

This preserves:

• Valid initial applied-image preview restoration.
• Intentional BLACK preview.
• C4-D preview synchronization.
• Snapshot cleanup after deletion or external file removal.
• Existing applied/preview GREEN/YELLOW/WHITE rules.

No timer, polling, retry delay, persistent state, or changes to C4-P/C4-D are needed.

J. iPhone and iPad behavior

Both platforms use the same SettingsScreen state, lifecycle handlers, availableImageURLs computation, and preview panel.

There is no platform-specific preview restoration branch. The issue and correction should apply consistently to iPhone and iPad.

K. Potential regressions to protect against

• Do not restore over a user-selected BLACK preview after Reset.
• Do not restore over an intentionally previewed physical image after a normal file refresh.
• Preserve C4-D behavior when deletion changes the applied or previewed image.
• Preserve snapshot cleanup when the currently previewed physical image is deleted externally.
• Preserve the preview-only versus applied-background distinction.
• Preserve immediate Settings reopening behavior within a running application.
• Do not alter C4-P startup ordering.
