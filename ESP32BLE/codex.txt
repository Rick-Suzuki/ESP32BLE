MIDI-LATENCY-001
END-TO-END MIDI LATENCY INVESTIGATION

SUMMARY

No intentional 50–60 ms delay was found in the MIDI-specific touch, parsing, transmission, or CoreMIDI code.

Note On starts directly from UIKit touchesBegan. It does not wait for touch release, a SwiftUI Button, a gesture recognizer, a timer, a debounce, or keyboard timing.

However, three plausible avoidable latency sources exist:

1. ESP32BLE performs synchronous diagnostic formatting and printing before calling Network.framework send.
2. ESPMacHelper hops received data from its Network.framework queue to the main actor, then performs logging, timestamp formatting, published UI-state updates, command-history insertion, and activity-indicator work before submitting MIDI.
3. The connection uses default TCP parameters and does not explicitly disable Nagle’s algorithm for these small messages.

These are credible contributors to variable latency, particularly while running under Xcode or when either application’s main thread is busy. Static inspection cannot establish whether they account for the subjectively estimated 50–60 ms.

2. iPad touch detection

Relevant file:

ESP32BLE/Scrns/Main_Screen/Main_GridSection.swift

A valid MIDI entry creates MIDITouchView directly. The visible button label has hit testing disabled, and the transparent UIKit MIDITouchCaptureView receives the touch.

Note On is triggered by:

MIDITouchCaptureView.touchesBegan(_:with:)

The exact touch-time operations are:

Guard against a duplicate active touch.
Take the first UITouch.
Read the already-configured note.
Save the active touch and note.
Print the MIDI touch-down diagnostic.
Invoke onDown immediately.

There is no wait for touchesEnded.

There is no movement threshold before Note On. Movement is examined only after Note On in touchesMoved, where leaving the view cancels the active note.

There is no SwiftUI Button action in the valid MIDI path.

The ordinary Button branch exists only when midiCommand(entry) returns nil. A valid MIDI command takes the MIDITouchView branch instead.

The TapGesture and double-tap recognition at Main_GridSection.swift lines 404–429 belong to ordinary sound buttons, not MIDI buttons.

The LongPressGesture belongs to grid-edit mode. MIDI touch capture is created only when grid-edit mode is disabled.

No timer, Task.sleep, debounce, animation, asyncAfter, or explicit dispatch occurs between touchesBegan and the MIDI callback.

The synchronous touch-down print occurs before onDown:

print("🐞 [MIDI-TOUCH] DOWN note=...")
onDown?(note)

Console output can become comparatively expensive when attached to Xcode, although the actual cost was not measured.

3. MIDI parsing and routing

Relevant files:

ESP32BLE/Scrns/MIDI/MIDICommandParser.swift
ESP32BLE/Scrns/Main_Screen/Main_ButtonBehavior.swift
ESP32BLE/Scrns/Main_Screen/Main_GridSection.swift
ESP32BLE/Scrns/Main_Screen/Main_Screen.swift

MIDICommandParser performs only synchronous string splitting and integer validation.

The parser is called by midiCommandForGridEntry(_:) while SwiftUI constructs/evaluates gridButtonView. It is not called from touchesBegan.

The rendered MIDITouchView already contains:

The parsed note.
A closure capturing the parsed velocity.

Consequently, touch-down does not reparse the command.

The recently added channel override and default-channel resolver are not used in the current transmission path. They introduce no touch-time work.

Main_Screen.swift directly connects:

onMIDITouchDown: sendMIDINoteOnFromTouch

sendMIDINoteOnFromTouch performs only synchronous guards and string interpolation before calling the network manager.

The command does not pass through:

sendMainGridEntry
Ordinary keyboard handling
Bluetooth token processing
Keyboard timing
Wait-chain processing
Speech processing
Audio playback
Button-click feedback

Keyboard timing settings therefore do not affect MIDI Note On.

4. ESP32BLE network transmission

Relevant file:

ESP32BLE/Scrns/MacConnectionManager.swift

MacConnectionManager is @MainActor. The touch callback and transmission preparation therefore run on the main actor.

sendAuthenticatedCommand performs:

A canSend guard.
A direct call to send(_:)
A direct call to sendFramedMessage(_:requiresAuthentication:)

Authentication does not add per-note cryptographic work. The connection has already been authenticated; the method only checks the authenticated state.

sendFramedMessage then:

Appends a newline delimiter.
Checks the connection and authentication state.
UTF-8 encodes the short command.
Formats and prints a detailed payload diagnostic.
Calls NWConnection.send.

NWConnection.send is asynchronous. The code does not wait for its completion before returning. Its completion handler handles errors only.

Important critical-path diagnostic work:

ESPMacTransportProbe.printPayload(data) runs before NWConnection.send.

That function:

Maps every byte to a decimal string.
Joins all byte strings.
Walks the data again to create an escaped payload.
Prints the complete formatted diagnostic.

The MIDI message is small, so the pure computation should ordinarily be small. The synchronous console output is less predictable, especially during debugging.

5. TCP behavior

Both ESP32BLE and ESPMacHelper use:

NWParameters.tcp

Neither side explicitly configures:

NWProtocolTCP.Options.noDelay

Apple documents noDelay as the option that disables Nagle’s algorithm.

The current code therefore does not explicitly request latency-oriented handling for small TCP writes.

This is a plausible investigation target because MIDI messages are very small and sent individually. TCP packet coalescing and delayed acknowledgments can sometimes produce latency patterns in the tens-of-milliseconds range.

Static inspection cannot determine:

The effective default behavior chosen by Network.framework.
Whether Nagle is actually delaying these particular packets.
Whether Wi-Fi scheduling dominates instead.
Whether the reported delay is present on every Note On or only under certain packet sequences.

This should be measured before changing TCP configuration.

There is no application-level send queue, batching timer, debounce, or deliberate delay in ESP32BLE.

6. ESPMacHelper network reception

Relevant file:

ESPMacHelper/ESPMacHelper/MacNetworkServer.swift

The NWConnection runs on a private serial DispatchQueue named:

MacNetworkServer

The receive callback does not parse or execute the message directly on that queue. When data arrives, it schedules:

Task { @MainActor in
self.processReceivedData(...)

}

This introduces a main-actor scheduling hop before MIDI processing.

If the Helper’s main actor is busy rendering UI, processing logs, or doing unrelated work, the MIDI message waits for main-actor availability.

The receive call is rearmed immediately on the Network.framework callback queue, so no receive timer exists.

The buffer processing is synchronous:

Append received data.
Search for the newline delimiter.
Extract the frame.
Decode UTF-8.
Call processCompleteCommand.

No artificial delay exists in framing.

The command is complete as soon as the newline arrives. It does not wait for additional bytes after finding that delimiter.

7. ESPMacHelper work before MIDI submission

processCompleteCommand performs substantial non-MIDI work before handleCommand:

Capture Date and DispatchTime.
Print the received message.
Check authenticated client state.
Allocate a command-probe sequence number.
Format and print a RECEIVED probe.
Print the raw message.
Assign the @Published lastReceived property.
Build a display representation.
Format a timestamp with DateFormatter.
Insert a ReceivedCommand at the beginning of an @Published history array.
Trim that array if necessary.
Update the @Published activity-indicator state.
Schedule an asyncAfter operation to clear the indicator.
Format and print an EXECUTE START probe.
Finally call handleCommand.

The 0.5-second activity-indicator duration does not delay Note On. Its asyncAfter block runs later.

The act of scheduling that block and changing published UI state occurs before Note On, however.

The command history is limited to 50 entries, so array insertion is not large, but it still performs allocation, formatting, observation invalidation, and potential SwiftUI update scheduling on the main actor.

The multiple synchronous print calls are also on the pre-MIDI critical path.

This is the largest concentration of avoidable application work found between network receipt and CoreMIDI submission.

8. Helper MIDI parsing

handleCommand trims the message and tries parseMIDICommand first.

For valid MIDI input:

It does not query Accessibility permission.
It does not execute keyboard parsing.
It does not execute text handling.
It does not use key-down or inter-key delays.
It directly calls MIDIOutputService.

The two keyboard-delay constants in MacNetworkServer are both zero and are unrelated to valid MIDI commands.

MIDI parsing consists only of:

Splitting on colons.
Checking field count and fixed strings.
Parsing UInt8 values.
Validating note and velocity.
Validating the current fixed channel 1 field.

This work is synchronous and negligible compared with scheduling, logging, or network transport.

9. MIDIOutputService and CoreMIDI

Relevant file:

ESPMacHelper/ESPMacHelper/MIDIOutputService.swift

MIDIOutputService is @MainActor.

startNetworkNote creates a NoteKey and calls startNote.

startNote:

Looks up current note owners.
Checks duplicate ownership.
Builds a MIDI 1.0 Universal MIDI Packet Note On.
Calls sendMessage.
Records ownership after successful submission.

There are no timers, tasks, sleeps, dispatches, or debounces in the network Note On path.

sendMessage:

Checks that the virtual source exists.
Initializes a MIDIEventList.
Adds one event using MIDIEventListAdd.
Uses timestamp 0.
Calls MIDIReceivedEventList immediately.

No future timestamp is supplied. The application does not deliberately schedule the event for later delivery.

MIDIReceivedEventList distributes incoming events from the virtual source to connected CoreMIDI clients. Logic Pro is downstream from this call.

The MIDI Note On log occurs after successful CoreMIDI submission, so that specific print does not delay the Note On submission.

11. Most likely software contributors

Highest priority:

Mac Helper main-actor hop and pre-execution work.

All incoming data is moved to the main actor, and several logging and UI-history operations occur before handleCommand. This can introduce variable latency when the main thread is occupied.

Second priority:

TCP small-message behavior.

Neither connection explicitly enables TCP noDelay. This is a plausible source of tens-of-milliseconds delay but is not proven by inspection.

Third priority:

Synchronous diagnostics before sending and before executing.

ESP32BLE performs detailed payload logging before NWConnection.send.
MIDITouchCaptureView prints before invoking onDown.
ESPMacHelper performs several prints before CoreMIDI submission.

Debug-console attachment can amplify these costs.

Lower priority:

Command parsing, integer conversion, ownership dictionaries, and MIDIEventList construction.

These are small synchronous operations with no waiting mechanism.

12. Touchscreen versus physical keyboard

A USB MIDI keyboard has a fundamentally shorter transport path:

CoreMIDI

The iPad path includes:

Touchscreen scan and event delivery
UIKit main-run-loop delivery
Application processing
Wi-Fi

Mac receive scheduling

CoreMIDI

Even with perfect application code, the iPad/Wi-Fi path should be expected to have more latency and jitter than direct USB MIDI.

This does not prove that the entire perceived difference is unavoidable. It means the comparison includes both software-path differences and physical-interface differences.

13. Recommended next investigation

Before changing behavior, measure distinct boundaries in a release-style run:

Touch event received on iPad.
Immediately before NWConnection.send.
Mac receive callback arrival before the main-actor hop.
Start of main-actor processing.
Immediately before MIDIReceivedEventList.
Logic Pro or CoreMIDI receipt.

The existing Helper command probes measure only portions of the Mac-side path and perform logging that can itself perturb timing.

Useful controlled comparisons would be:

Run without Xcode consoles attached.
Compare Debug and Release builds.
Temporarily disable existing diagnostics in a dedicated approved experiment.
Compare Wi-Fi conditions and proximity.
Compare repeated isolated Note Ons against rapid Note On/Note Off sequences.
Measure whether delay is constant or occurs in clusters.
Measure the private Network queue to main-actor wait separately.
Test TCP noDelay as an isolated later experiment.

No optimization should be selected solely from the subjective 50–60 ms estimate.

14. Overall conclusion

The MIDI touch implementation is already using the earliest normal UIKit touch callback and does not wait for gesture recognition or release.

The iPad sends immediately after synchronous guards and diagnostics.

CoreMIDI submission is immediate and uses no future timestamp.

The main avoidable architectural concern is that ESPMacHelper moves incoming network data to the main actor and performs diagnostic and UI bookkeeping before submitting MIDI.

Default TCP small-packet behavior and synchronous console logging are additional plausible contributors.

There is not enough evidence from static inspection to assign a measured latency to any one stage or confirm the reported 50–60 ms.
