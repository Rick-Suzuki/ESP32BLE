B. Background persistence storage and writers

The three shared AppStorage keys are:

• selectedBackgroundImageIndex, default 0
• selectedBackgroundImageName, default empty
• selectedBackgroundImagePath, default empty

Settings and ContentView use the same UserDefaults keys.

The primary Settings writer is persistSelectedImage(_:), in Set_ImgSelectionSupport.swift lines 63–72:

• Physical image: stores its full path, basename, and one-based sorted index.
• BLACK/nil: stores index 0, empty name, and empty path.

Known background-state writers include:

• Settings manual application through applySettingsBackground(_:).
• IMAGE table double-tap through the same Settings application path.
• Preview-panel tap through the same Settings application path.
• C4-D deletion fallback through persistSelectedImage(predecessorURL).
• Main-screen background controls through their own persistence helper.
• ContentView restoration and normalization paths.

C. Manual IMAGE application path

Both manual Settings application routes are correct by source inspection.

IMAGE double tap:

• Set_Table.swift invokes handleImageBackgroundSelection(imageURL).
• Set_Screen.swift injects applySettingsBackground(imageURL).
• applySettingsBackground(_:) calls persistSelectedImage(imageURL).
• It synchronizes previewImageURL to the applied URL.
• It triggers the existing changed-BG feedback.

Large preview single tap:

• The preview panel call site invokes applySettingsBackground(previewImageURL).
• It uses previewImageURL, not the decoded image.
• It therefore persists the same full path, name, and index through persistSelectedImage(_:).

Conclusion: manual application should persist correctly at the Settings layer. There is no source evidence that either Settings application path writes BLACK for a valid image.

D. Current C4-D deletion path

C4-D is present in the current deleteImage(_:) implementation.

It correctly:

• Captures availableImageURLs before deletion.
• Finds the deleted image using complete URL-path equality.
• Chooses the preceding original image, or nil/BLACK for the first image.
• Captures whether the deleted image was applied and/or previewed.
• Deletes the file and refreshes the document snapshot.
• Validates that the predecessor still exists after refresh.
• Uses persistSelectedImage(validatedPredecessorURL) when the deleted image was applied.
• Synchronizes the Settings preview to that same predecessor.
• Changes only the preview when the deleted image was preview-only.
• Leaves both applied and preview state unchanged for unrelated deletion.

The predecessor index is recalculated after refresh inside persistSelectedImage(_:), using the refreshed sorted collection. Therefore C4-D does not appear to write a stale post-deletion index.

E. Confirmed cause of the BLACK reset after app restart

The source establishes a startup ordering problem in ContentView.

Current sequence:

1. ContentView’s .task begins.
2. ensureDefaultFunctionKeysFile() runs.
3. It refreshes document files and selects/loads the current screen.
4. loadFunctionKeys(from:) calls restoreBackgroundImageSelection(for:).
5. Only after this completes does the outer startup task call refreshBackgroundImageFiles().

At step 4, backgroundImageFiles is still initially empty.

restoreBackgroundImageSelection(for:) restores the image using the saved screen configuration’s backgroundImageName. It searches backgroundImageFiles for that name. Since that collection is empty at this point, the lookup fails and lines approximately 1352–1358 explicitly write:

• selectedBackgroundImageIndex = 0
• selectedBackgroundImagePath = ""
• selectedBackgroundImageName = ""
• loadedBackgroundImage = nil

This permanently changes the shared AppStorage selection to BLACK before the background image collection is populated.

The later refreshBackgroundImageFiles() loads the images, but does not retry restoration of the saved screen background.

This is a confirmed source-order cause, not merely a timing hypothesis. It explains both cases:

• Manual application: the screen configuration retains the image name, but startup clears the active AppStorage selection before the image list is ready.
• C4-D predecessor application: the predecessor name is saved through the normal persistence/ContentView observer path, but the same premature startup restore subsequently clears the active selection to BLACK.

F. Absolute path and identity findings

Image URLs are built from the application Documents directory. Those URLs and their absolute paths are stable across ordinary app relaunches on the same installation.

Settings resolves a persisted selection in this order:

1. Stored full path.
2. Stored filename.
3. Stored one-based sorted index.

ContentView screen configuration persists only the portable filename, not the full path or index. That is appropriate for the screen configuration, but requires the image collection to be available before restoration.

A genuinely missing, renamed, or deleted image should safely resolve to BLACK. A valid existing image currently fails only because restoration occurs before image discovery.

G. Can the three stored values diverge?

Yes, briefly. persistSelectedImage(_:) writes path, then name, then index. AppStorage observers can react to individual changes. The normal final state is coherent, and this is not the confirmed restart cause.

More importantly, ContentView’s restoration failure explicitly overwrites all three values with the BLACK representation. That is the observed persistent failure.

Case 5 — Close and reopen Settings without terminating ESP
• Settings restores preview from selectedImageURL.
• This should work while the app remains alive, because image collections have already loaded.

Case 6 — Background collection initially empty but image exists
• Current behavior incorrectly treats the valid name as missing and persists BLACK.
• Required behavior: defer resolution until the collection is available, without overwriting valid stored state.

I. Smallest safe correction recommendation

Correct the existing ContentView startup/restoration ordering, rather than altering C4-D, adding storage, adding delays, or changing Settings application code.

Smallest likely correction:

• Ensure refreshBackgroundImageFiles() completes before the first restoreBackgroundImageSelection(for:) call that occurs during initial screen loading.

A narrowly scoped equivalent is to make restoreBackgroundImageSelection(for:) refresh/obtain the background image collection before deciding that a nonempty saved background name is invalid.

Important preservation rule:

• A nonempty saved image name must not be converted to BLACK merely because backgroundImageFiles is temporarily empty during startup.
• BLACK should still be persisted only for an actually empty saved name or a confirmed missing image after the collection is available.

The preferred correction is startup ordering because it preserves the existing restoration implementation and avoids an additional retry/state mechanism.

J. C4-D assessment

C4-D’s predecessor selection is not the source of the restart BLACK reset.

Its predecessor calculation, post-delete validation, full-path comparisons, persisted replacement, and preview synchronization are consistent with the requested behavior. The restart defect occurs later in ContentView startup restoration.
