J. TOP-EDGE CONSTRAINTS

If the Resize popup is near the top edge, a message above it could extend off-screen.

Existing data available:
• menuPosition
• menuSize
• safeAreaInsets
• availableHeight
• gridTopY
• resolvedGridHeight

Potential safe approach:
• Prefer above-popup placement.
• If the message would exceed the safe/top boundary, clamp the message Y into the visible overlay area.
• If clamping would overlap the popup, consider placing it just below the popup only for that edge case.

This should be implemented as message placement only. The Resize popup itself should remain fixed.

N. RECOMMENDED IMPLEMENTATION

Smallest safe change set, preferably one controlled Codex implementation:

1. Add a non-mutating resize availability helper.

Safest option:
Reuse updatedSlotLinesForPopupResize(...) against the current slot-line snapshot and interpret outcomes:
• .success = enabled
• .sameSize = enabled
• .notEnoughSpace = disabled
• .spaceOccupied = disabled
• .invalidSource = disabled

This avoids duplicating validation.

2. Pass availability into MainGridResizeActionMenu.

Keep the fixed rows array and all positions unchanged.

3. Update shapeButton to accept isEnabled.

Use greyed-out styling and .disabled(!isEnabled) matching the main popup.

4. Preserve current-size behavior.

Current size should be enabled. Tapping it can remain a no-op unless future requirements say otherwise.

5. Add resize-local error message state if invalid options remain tappable somewhere.

If invalid options become disabled, user cannot tap them, so error messages may only be needed for race conditions where validation changes after the view renders.

6. For the future “message above popup” requirement, add a local overlay near menuPosition.

This should be separate from the top-centre operation message system.

7. Consider refreshing the popup target from rendered frames after successful resize.

This is not required for disabling options, but it would align Resize with Test 5I-B’s Cut/Paste correction and avoid synthetic final frames.

Recommended split:
• Stage 1: fixed-position disabled resize options.
• Stage 2: resize-local above-popup message.
• Stage 3, if needed: rendered-frame refresh after successful resize.

O. RISKS

Main risks:
• Accidentally changing the 146×146 popup layout.
• Treating .sameSize as disabled even though requirement says current size remains enabled.
• Duplicating validation and drifting from actual resize mutation rules.
• Showing resize errors in the top-centre operation toast instead of above the Resize popup.
• Placing an above-popup message off-screen near the top edge.
• Introducing platform-specific positioning tweaks that disturb completed iPad/iPhone popup geometry.
• Leaving successful resize anchored to a synthetic frame if future visual testing reveals stale positioning.

Frozen geometry does not need to change for option disabling.
