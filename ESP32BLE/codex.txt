2. New functions and responsibilities

TemplateDocument.swift:

• TemplateApplicationResult
Returns the applied ScreenConfig, template contents, and unchanged target URL.

• TemplateApplicationError
Provides distinguishable errors for validation, preparation, replacement, rollback, and critical rollback failure.

• applyTemplateDocument(...)
Validates, prepares, replaces, verifies, and—if necessary—rolls back the target screen and configuration.

• replacePreparedTemplateFile(...)
Performs each prepared per-file replacement.

• restoreTemplateApplicationTarget(...)
Restores the exact original screen bytes and original configuration state.

ContentView.swift:

• applyTemplateToSelectedDocument(...)
Reconfirms the selected screen, invokes the filesystem engine, reloads the same screen, and synchronizes legacy configuration values.

• synchronizeLegacyConfigurationValues(...)
Updates the existing per-document font-size and grid-dimension stores, background opacity, and font refresh token.

3. Validation rules

The engine validates:

• Source has the .template extension.
• Source exists and is a regular file.
• Source is readable and valid UTF-8.
• Template configuration sidecar exists and decodes successfully.
• Effective button count uses ContentView’s existing normalizedSlotLines parser.
• Button count does not exceed maxFunctionKeyCount.
• Grid rows and columns are positive.
• Grid multiplication does not overflow.
• Grid capacity accommodates the effective button count.
• Grid capacity does not exceed the supported maximum.
• Target is a .screen document.
• Target filename matches the expected selected filename.
• Selected screen has not changed.
• Target exists, is regular, and contains valid UTF-8.
• Original target screen and optional configuration bytes can be preserved.
• Target files have not changed during replacement preparation.

Invalid template configurations are never replaced with defaults.

4. File replacement sequence

• Reads and validates the template and its configuration.
• Snapshots the exact target screen bytes.
• Snapshots the exact target configuration bytes when present.
• Records when the target configuration did not previously exist.
• Encodes only TemplateConfiguration.screenConfig; template description metadata is excluded.
• Creates two unique temporary payload files in the target directory.
• Reads back and verifies both prepared payloads.
• Reconfirms the selected screen immediately before replacement.
• Confirms the target still matches its snapshots.
• Replaces the screen file.
• Replaces or creates the target configuration sidecar.
• Reads back and verifies both final files.
• Removes remaining temporary files.

The operation does not claim that the two replacements form a single atomic filesystem transaction.

5. Rollback behaviour

If replacement or final verification fails:

• The exact original screen bytes are restored.
• The exact original configuration bytes are restored when one existed.
• A newly created configuration is removed when the target originally had no sidecar.
• Restored bytes are verified.

A successfully restored failure reports replacementFailedAndRolledBack. A failed or incomplete restoration reports rollbackFailed separately, including both underlying errors.

6. Active-screen reload handling

After successful replacement:

• The existing loadFunctionKeys(from:) path reloads the same target URL.
• The selected filename remains unchanged.
• No history-recording screen-selection method is called.
• Navigation history is not modified.
• No template application occurs automatically.

7. Legacy configuration synchronization

After successful replacement, ContentView synchronizes:

• Per-document font size.
• Per-document grid dimensions.
• Main grid background opacity.
• Font-size refresh token.

Existing loadFunctionKeys behaviour continues restoring background-image compatibility state. Legacy values are not modified before the filesystem replacement succeeds.

9. Tests performed

Isolated tests used temporary directories outside the user’s Documents directory. They verified:

No real screen or template documents were modified. No device testing was performed.

10. Remaining risks and limitations

• A process termination between the two per-file replacements cannot be automatically recovered because this deliberately does not introduce a persistent transaction journal.
• The rollback failure path is implemented and compiled, but a forced low-level filesystem rollback failure was not injected during testing.
• Settings editor state and its save baseline are intentionally not refreshed in this phase.
• Actual interaction and reload behaviour still require device testing after the UI connection is added.
