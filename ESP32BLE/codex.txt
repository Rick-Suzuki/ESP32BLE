2. Plates row interaction

• Template rows are now plain-style Buttons.
• A single tap preserves existing click feedback and row appearance.
• The row sends only the template URL through a dedicated selectTemplate callback.
• It does not use the ordinary clipboard/file-selection handler.
• No double-tap, clipboard, swipe, preview, or immediate application behavior was added.
• Existing Screens row behavior was unchanged.

3. Confirmation state and presentation

Settings now captures:

• Template URL.
• Complete template filename.
• Expected target screen filename.
• Trimmed optional description.

A native SwiftUI alert displays:

• “Apply Template?”
• Template filename.
• Target filename.
• Optional description when nonempty.
• Replacement warning.
• Cancel action.
• Destructive Apply action.

Cancel does not invoke the template engine.

4. Pending editor-save handling

Before showing confirmation, Settings:

• Verifies the template is still a regular file.
• Loads and validates its configuration.
• Resolves and validates the selected target screen.
• Calls the existing conflict-aware saveCurrentDocumentText().
• Aborts for conflict, missing file, or save failure.
• Uses the existing native save-error presentation.

Unsaved editor content is therefore not silently discarded.

5. Application callback integration

ContentView passes applyTemplateToSelectedDocument(...) into Settings.

Apply:

• Reconfirms the selected filename.
• Calls the existing 001C-A engine.
• Does not write either target file directly.
• Does not call the history-recording screen-selection path.
• Leaves replacement validation, verification, and rollback to the existing engine.

6. Settings editor refresh

After successful application, Settings calls loadSelectedDocumentText().

This refreshes:

• Editor text.
• Saved-text baseline.
• Loaded document URL and filename.

This prevents stale pre-template editor content from overwriting the newly applied screen or causing a false external-change conflict.

7. Success and error feedback

• Success displays “Template applied” for two seconds inside the Settings table area.
• Ordinary failures use “Template Could Not Be Applied”.
• Template-loading failures use “Template Could Not Be Opened”.
• Critical rollback failures use the distinct title “Critical Template Error”.
• Success is shown only after the engine returns successfully and the editor reload begins.

The SwiftUI guidance informed the use of native Button and alert controls, private view-owned state, and a separate confirmation presentation branch.
