MIDI-010B — MIDI CHANNELS
READ-ONLY ARCHITECTURE REPORT

1. Current parser and proposed architecture

Current ESP32BLE parsing is in:

ESP32BLE/Scrns/Main_Screen/Main_ButtonBehavior.swift
midiCommandForGridEntry(_:)

It currently:

Accepts exactly one sendTexts entry.
Splits that entry on whitespace.
Accepts two or three components.
Requires the first component to be exactly “.midi”.
Validates note as 0...127.
Validates explicit velocity as 1...127.
Defaults omitted velocity to 100.
Returns a tuple containing note and velocity.

Current accepted forms:

.midi 60
.midi 60 50

The proposed four-component form requires expanding the accepted count to 2...4:

.midi <note>
.midi <note> <velocity>
.midi <note> <velocity> <channel>

Under this syntax, “.midi 60 3” remains velocity 3, not channel 3. A channel override cannot be specified without also specifying velocity. This avoids ambiguity and preserves existing command behavior.

Recommended parsed representation:

struct MIDICommand {
let note: UInt8

let velocity: UInt8

let channelOverride: UInt8?

}

The parser should preserve the user-facing channel as 1...16. It should not convert to CoreMIDI’s zero-based channel during ESP32BLE command parsing.

A separate resolved representation is recommended:

struct ResolvedMIDINoteCommand {
let note: UInt8

let velocity: UInt8

let channel: UInt8

}

Here, channel is still the wire/display value 1...16.

Resolution would be conceptually:

effectiveChannel = channelOverride ?? defaultMIDIChannel

The default must be defensively clamped or validated as 1...16 before use.

The wire command should remain one-based:

MIDI:NOTE_ON:<note>:<velocity>:<channel>
MIDI:NOTE_OFF:<note>:<channel>

Dedicated parser recommendation:

Yes. This is the appropriate point to move parsing into a dedicated MIDICommandParser.swift file.

The parser has already grown beyond a note-only helper. Adding channels and the anticipated named-note, Control Change, Program Change, and toggle features inside Main_ButtonBehavior.swift would mix syntax policy with UI execution and network behavior.

A dedicated parser should:

Own whitespace normalization.
Own exact argument-count validation.
Own numeric range validation.
Return structured command data.
Have no SwiftUI dependency.
Have no network dependency.
Have no CoreMIDI dependency.
Keep one-based display/wire channels separate from zero-based CoreMIDI channels.
Be directly unit-testable.

A reasonable initial API would be conceptually:

MIDICommandParser.parse(_ text: String) -> MIDICommand?

The parser should parse only the currently authorized Note command. Future command types can later be represented by an enum without changing the button-routing code repeatedly.

Named-note conversion should eventually occur in this ESP32BLE parser. ESPMacHelper should continue receiving numeric note, velocity, and channel fields only.

2. Recommended Settings location and persistence

ESP32BLE already uses @AppStorage extensively for device-local preferences.

Examples include:

speechRecognitionAutoOffMinutes
keyboardTimingOnMs
keyboardTimingOffMs
keepScreenAwake
outputMode
settingsStatusBarVisible
textToSpeechRate

This is backed by UserDefaults and is independent of .screen documents.

Recommended persistence:

@AppStorage("midiDefaultChannel") private var midiDefaultChannel = 1

The value should be constrained to 1...16 by the Settings control and validated again when resolved for transmission. The initial default should be 1.

The setting must not be added to:

ScreenDocument
TemplateDocument
Screen configuration JSON
Document backup/restore models
.screen serialization

Recommended UI location:

The most coherent location is the Connection area in Settings, near the Mac output controls in SettingsAvailableDevicesPanel.

MIDI output is currently available only through the Mac connection, so the setting belongs with the Mac transport configuration rather than keyboard timing, screen layout, image settings, or per-document controls.

It can be shown when Mac output is selected, or remain visible but clearly labeled as a Mac MIDI preference. Showing it for Mac output only is the cleaner arrangement.

The relevant view is:

ESP32BLE/Scrns/Set_Screen/Btm_Area/Set_AvailableDevices.swift
SettingsAvailableDevicesPanel

Smallest persistence/data-flow approach:

SettingsAvailableDevicesPanel reads and writes midiDefaultChannel using @AppStorage.
MainScreen reads the same key using @AppStorage.

Because both wrappers observe the same UserDefaults key, changing the value in Settings propagates to MainScreen without storing it in ContentView or passing a binding through SettingsScreen and SettingsBottomControlsSection.

For stronger key consistency, the storage key and valid range should be centralized in the new MIDI parser/model file rather than duplicated as string literals.

3. Required ESP32BLE modifications

A. Add the dedicated parser/model

Create MIDICommandParser.swift containing:

MIDICommand
ResolvedMIDINoteCommand or an equivalent note identity
MIDICommandParser
The default-channel storage key
The valid note, velocity, and channel ranges
A resolver from optional override to effective channel

B. Replace tuple parsing

Main_ButtonBehavior.swift currently returns:

(note: Int, velocity: Int)

It should return a structured command containing:

note
velocity
optional channel override

The effective channel should be resolved from the override and the current device-local default before the touch begins.

C. Send channel in Note On

sendMIDINoteOnFromTouch currently accepts note and velocity and always transmits channel 1.

It must accept the resolved channel and transmit:

MIDI:NOTE_ON:<note>:<velocity>:<channel>

All three values should remain defensively validated.

D. Send channel in Note Off

sendMIDINoteOffFromTouch currently accepts only note and always transmits channel 1.

It must receive both the original note and original channel and transmit:

MIDI:NOTE_OFF:<note>:<channel>

It must not read the current Settings value while releasing a held note.

E. Preserve the channel in the touch identity

Main_GridSection.swift currently stores only:

activeNote

The active touch must instead preserve at least:

note
channel

Velocity is needed only for Note On. Note Off needs the exact note/channel identity established by Note On.

F. Add Settings persistence and UI

SettingsAvailableDevicesPanel should expose an integer selector constrained to 1...16 and persisted with @AppStorage.

MainScreen should observe the same device-local preference.

No ContentView, screen-document, template, archive, editor, or backup changes are required if @AppStorage is used directly in the Settings panel and MainScreen.

4. Required ESPMacHelper modifications

Production Helper files inspected:

ESPMacHelper/ESPMacHelper/MacNetworkServer.swift
ESPMacHelper/ESPMacHelper/MIDIOutputService.swift

MacNetworkServer.swift currently parses these exact wire forms:

MIDI:NOTE_ON:<note>:<velocity>:1
MIDI:NOTE_OFF:<note>:1

The parser explicitly requires the final component to equal “1”.

ParsedMIDICommand currently drops channel information:

case noteOn(note: UInt8, velocity: UInt8)
case noteOff(UInt8)

handleCommand then hard-codes CoreMIDI channel 0:

startNetworkNote(... channel: 0 ...)
stopNetworkNote(... channel: 0 ...)

Required changes in MacNetworkServer.swift:

Parse wire channel as an integer.
Validate wire channel as 1...16.
Include the channel in both ParsedMIDICommand cases.
Convert to zero-based CoreMIDI channel by subtracting one.
Pass the resulting 0...15 value to MIDIOutputService.

Conceptually:

wireChannel: 1...16
coreMIDIChannel = wireChannel - 1

MIDIOutputService.swift already accepts a zero-based channel in:

startNetworkNote(note:velocity:channel:clientID:)
stopNetworkNote(note:channel:clientID:)

It already passes that channel to:

MIDI1UPNoteOn
MIDI1UPNoteOff

Therefore, no functional production change is required in MIDIOutputService.swift for basic 16-channel support.

The Helper’s menu test note can remain on its existing channel 1, represented internally as channel 0.

5. Note On/Note Off channel-preservation strategy

Current iOS touch identity:

MIDITouchCaptureView stores activeNote only.

Current callbacks:

onDown(Int)
onUp(Int)

That is insufficient once the channel can vary.

Recommended touch identity:

struct MIDINoteIdentity: Hashable {
let note: UInt8

let channel: UInt8

}

Recommended flow:

The button command is parsed.
The effective channel is resolved using the button override or current default.
MIDITouchView receives a fully resolved command.
touchesBegan records the resolved note/channel identity as the active identity.
Note On uses that identity and the parsed velocity.
touchesEnded sends Note Off using the stored active identity.
touchesCancelled sends Note Off using the same stored active identity.
cancelActiveTouch() sends Note Off using the same stored active identity.

The active identity must be captured at touch-down time. Note Off must not recompute the channel from:

The current Settings value.
The latest SwiftUI render.
The current button command.
A newly supplied closure’s captured default channel.

This guarantees:

Changing the default channel while a note is held does not redirect its Note Off.
Touch cancellation releases the original channel.
A button with an explicit override releases on that override.
A button without an override releases on the default that was effective when the touch began.

The safest callback shape is to pass the stored identity as an argument:

onDown(ResolvedMIDINoteCommand)
onUp(MIDINoteIdentity)

That is safer than relying on closures that capture the channel because SwiftUI can update the representable and replace those closures while a touch is active.

6. Same-note/different-channel ownership findings

MIDIOutputService already defines:

NoteKey(note, channel)

Its active-note dictionary is keyed by NoteKey:

activeNoteOwners: [NoteKey: Set<NoteOwner>]

Therefore:

Note 60 on channel 1 and note 60 on channel 3 are independent keys.
A Note Off for note 60/channel 1 does not release note 60/channel 3.
Disconnect cleanup finds every NoteKey owned by the disconnecting client, including notes on different channels.
MIDI panic/shutdown iterates all active NoteKeys and emits Note Off on each key’s stored channel.
Two different ESP32BLE clients can share the same note/channel safely; the actual Note Off is emitted only after the final owning client releases it.
Two buttons from the same client can play the same note on different channels independently because their NoteKeys differ by channel.

One existing ownership limitation should be preserved and tested:

NoteOwner is keyed only by network client ID, not by individual touch or button.

If the same ESP32BLE client holds the same note on the same channel from two different buttons, both presses map to the same owner and NoteKey. The second press does not add another independent ownership count, and the first release can stop the shared note.

That limitation already exists and is not introduced by channels. Same-note/different-channel operation is independent and should work correctly once the Helper passes the parsed channel through.

7. Automated testing recommendations

ESP32BLE parser tests:

“.midi 60” parses as note 60, velocity 100, no channel override.
“.midi 60 50” parses as note 60, velocity 50, no channel override.
“.midi 60 50 3” parses as note 60, velocity 50, channel override 3.
“.midi 60 100 16” parses as channel override 16.
Default resolution uses channel 1 initially.
Changing the default resolves an override-free command to the new value.
An explicit override ignores the default.
Leading, trailing, and repeated whitespace are handled consistently.
Tabs between arguments are handled consistently.
Notes 0 and 127 are accepted.
Notes -1 and 128 are rejected.
Velocities 1 and 127 are accepted.
Velocities 0 and 128 are rejected.
Channels 1 and 16 are accepted.
Channels 0 and 17 are rejected.
Missing arguments are rejected.
Non-numeric arguments are rejected.
Extra arguments are rejected.
“.MIDI” remains rejected if case sensitivity is intentionally retained.
“.midi 60 3” remains velocity 3 with no channel override.

ESP32BLE touch-state tests:

Touch-down stores the resolved channel.
Changing the default while held does not change the release channel.
Normal touch end uses the original channel.
Move-out cancellation uses the original channel.
System cancellation uses the original channel.
View dismantling uses the original channel.
Two buttons using the same note on different channels generate distinct Note On and Note Off pairs.
Multiple different notes remain independent.

ESPMacHelper parser tests:

NOTE_ON accepts wire channels 1 and 16.
NOTE_OFF accepts wire channels 1 and 16.
Wire channel 1 becomes CoreMIDI channel 0.
Wire channel 16 becomes CoreMIDI channel 15.
Channels 0 and 17 are rejected.
Malformed and extra fields are rejected.
Invalid MIDI commands do not fall through to keyboard or text execution.

MIDIOutputService ownership tests:

Same note on different channels creates separate NoteKeys.
Same note/channel from two clients remains active until both clients release it.
Disconnect releases every channel owned by that client.
Disconnecting one client does not release a shared key still owned by another client.
Panic/shutdown emits Note Off using every NoteKey’s stored channel.
Same client, same note, different channels remains independent.

Use the Swift Testing framework for pure parser and ownership tests.

8. Smallest safe implementation sequence

Step 1:
Add the ESP32BLE MIDI command model and centralized parser, preserving all current note and velocity behavior.

Step 2:
Add parser tests for current syntax before enabling channels.

Step 3:
Extend parsing to the optional fourth channel argument and add boundary/malformed-input tests.

Step 4:
Add the device-local @AppStorage default channel with initial value 1 and the Settings control.

Step 5:
Resolve the effective channel before touch-down and carry note/channel as the active touch identity.

Step 6:
Update ESP32BLE Note On and Note Off wire commands to include that resolved channel.

Step 7:
Extend MacNetworkServer’s parsed MIDI command to retain the wire channel, validate 1...16, convert it to 0...15, and pass it to MIDIOutputService.

Step 8:
Add Helper parser and ownership tests.

Step 9:
Perform integration testing for held notes, cancellation, simultaneous channels, disconnect cleanup, and panic.

This order keeps the existing channel-1 behavior working at each stage and isolates parser changes from touch-lifetime changes.
