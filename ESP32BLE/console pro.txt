============================================================
PURPOSE
============================================================

ESP -> ESPMacHelper networking is functionally complete and physically
tested.

ESPMacHelper has macOS Accessibility permission and can inject keyboard
events.

At present, however, the connection is plain TCP and any client capable
of reaching the service and sending correctly formatted commands could
potentially execute keyboard commands.

Implement V1 pairing and authentication.

PRIMARY UX GOAL:

NORMAL USE:
    zero user interaction

PAIRING:
    one deliberate action on Mac to temporarily allow pairing
    one pairing action on ESP
    NO code/password typing

AFTER PAIRING:
    automatic authentication on every connection

UNKNOWN / UNAUTHENTICATED CLIENT:
    MUST NEVER reach keyboard command execution

============================================================
SECURITY MODEL
============================================================

Use:

- strong random long-term credential per ESP installation
- persistent random ESP installation/device identifier
- persistent random Mac Helper installation identifier
- Keychain storage for long-term secrets
- challenge/response authentication
- HMAC-SHA256 using CryptoKit
- fresh cryptographically secure random nonce for every authentication
  session

DO NOT use:

- IP address as identity
- Bonjour service name as security identity
- six-digit permanent password
- hard-coded universal secret
- IDFV as authentication credential
- runtime clientID as persistent identity
- plaintext transmission of the long-term secret during normal
  authentication

The long-term secret MAY be transferred during the deliberately enabled
initial pairing exchange, because V1 pairing is explicitly authorized by
physical interaction at the Mac.

Normal reconnections MUST NOT transmit that long-term secret.

============================================================
IMPORTANT SECURITY LIMITATION
============================================================

V1 continues to use the existing plain TCP transport.

Therefore the implementation must NOT claim to provide encrypted network
traffic.

The purpose of V1 is:

- authenticate previously paired ESP installations
- reject arbitrary unauthenticated command senders
- prevent captured old authentication responses from being replayed by
  using a fresh challenge nonce

Do not unnecessarily convert the existing transport to TLS in this task.

Keep the scope controlled.

============================================================
IDENTITIES
============================================================

ESP:

On first need, generate a cryptographically random persistent installation
UUID/identifier.

Store it persistently.

Prefer Keychain persistence so it survives normal app relaunches and is
not merely temporary SwiftUI state.

Mac Helper:

On first need, generate its own persistent installation identifier.

Store persistently.

The identifiers are identities, NOT secrets.

Each paired ESP installation receives its OWN independent long-term random
secret.

Do NOT use one universal secret for every ESP.

Do NOT store long-term secrets in UserDefaults.

============================================================
PROTOCOL NAMESPACE
============================================================

The existing LF-delimited framing MUST remain unchanged.

Authentication/pairing messages must use the SAME existing LF framing:

MESSAGE\n

Introduce a clearly separate reserved protocol namespace so authentication
messages cannot be confused with normal commands.

For example:

AUTH:...
PAIR:...

Exact field layout may be chosen cleanly during implementation, but:

- document it in code
- keep parsing strict
- reject malformed security messages
- do not pass AUTH/PAIR messages into handleCommand
- do not allow unknown unauthenticated messages to reach handleCommand

Do not alter existing CMD/TEXT/KEY message semantics.

============================================================
MAC -> ESP RECEIVE PATH
============================================================

The inspection found ESP currently sends to Mac but does not currently
have a Mac-network receive loop.

Add the smallest robust receive implementation to MacConnectionManager.

Requirements:

- per-connection receive buffer
- LF-delimited framing
- handle partial messages across receive callbacks
- handle multiple messages in one receive callback
- UTF-8 decoding
- restart receive after processing
- clean buffer on disconnect/restart
- do NOT interfere with ESP -> Mac sending

Use the same framing principle already proven on Mac Helper.

Do NOT assume one TCP receive == one protocol message.

============================================================
PAIRING HANDSHAKE
============================================================

Implement a simple cryptographically strong pairing exchange.

The exact wire field representation can be chosen by Codex, but the
security properties MUST be:

1. Mac pairing mode must be enabled.

2. ESP explicitly requests pairing.

3. ESP sends its persistent installation ID.

4. Mac generates a fresh strong random long-term secret specifically for
   that ESP installation.

5. Mac stores that ESP ID + secret in Keychain.

6. Mac sends:
   - Mac Helper persistent identity
   - new long-term secret
   back to ESP as part of the authorized pairing exchange.

7. ESP stores:
   - Mac Helper identity
   - long-term secret
   in Keychain.

8. Pairing mode immediately closes after successful pairing.

9. ESP should then authenticate normally using the newly stored
   credential.

Do NOT subsequently transmit the long-term secret during ordinary
authentication.

============================================================
NORMAL AUTHENTICATION HANDSHAKE
============================================================

Every new TCP connection begins UNAUTHENTICATED.

Being TCP-connected is NOT equivalent to being authenticated.

Mac:

On a new connection becoming ready, generate a fresh cryptographically
secure random nonce/challenge.

Send a framed authentication challenge to ESP.

Conceptually:

AUTH:CHALLENGE:<helperID>:<nonce>

ESP:

Upon receiving the challenge:

- determine whether helperID matches its paired Helper
- retrieve its stored credential
- calculate HMAC-SHA256 using the stored secret
- include ESP installation ID in the authenticated material
- return a response

Conceptually:

AUTH:RESPONSE:<espID>:<hmac>

The HMAC input MUST bind at minimum:

- protocol/version context
- Helper identity
- ESP identity
- fresh nonce

Do NOT HMAC only the nonce without identities/context.

Mac:

Look up the paired credential for espID.

Calculate expected HMAC independently.

Compare received and expected authentication tags safely.

If valid:

client session becomes authenticated

Mac sends:

AUTH:OK

ESP then marks the Mac connection authenticated.

Only AFTER AUTH:OK may ESP normal command sending become enabled.

If invalid or unknown:

send AUTH:FAILED if appropriate
and/or close/reject the connection.

Never execute a normal command from that unauthenticated session.

============================================================
REPLAY PROTECTION
============================================================

Generate a NEW cryptographically secure challenge nonce for EVERY TCP
connection/authentication attempt.

Never reuse an old challenge.

A captured AUTH:RESPONSE from an old connection must not authenticate a
future connection.

============================================================
MAC PER-CLIENT SESSION STATE
============================================================

Add explicit per-client authentication/session state alongside the
existing:

connections[clientID]
receiveBuffers[clientID]

For example conceptually:

clientSessions[clientID]

Each client must independently track at least:

- authentication state
- current challenge nonce

Do not use one global authenticated Bool.

Multiple ESP iPads must remain independently supported.

When removeConnection() runs, remove that client's security/session state
as well.

When stop() clears clients, clear session state as well.

============================================================
CRITICAL MAC COMMAND GATE
============================================================

This is the most important security requirement.

In:

processCompleteCommand(_:clientID:)

or immediately adjacent to it:

AUTH and PAIR protocol frames may be handled by the security protocol.

NORMAL COMMANDS MUST NOT proceed to:

handleCommand(_:clientID:)

unless that clientID is authenticated.

Conceptually:

complete LF frame
       |
       +---- AUTH / PAIR ----> security protocol
       |
       +---- normal command
                  |
            authenticated?
              /       \
            NO         YES
            |           |
          DROP       handleCommand


Unauthenticated normal commands should be rejected/dropped and may be
diagnostically logged.
They MUST NOT:
- enter keyboard execution
- post CGEvents
============================================================
ESP COMMAND GATE
Currently:
canSend == status == .connected
is NOT sufficient.
Separate:
TCP connection readiness
from:
authentication readiness
Normal:
sendKeyboardTokens(_:)
must return false / refuse normal command transmission until the current
Mac connection is authenticated.
Do NOT queue old keyboard commands during authentication.
Dropping/refusing them is safer and consistent with the current behavior
when disconnected.
Security protocol messages need an internal send path that is allowed
before normal authentication.
Do NOT accidentally block AUTH/PAIR messages with the normal command gate.

One thing I've deliberately specified is that **pairing itself remains over plain TCP**. That's convenient and considerably better than what we have now, but it means this V1 isn't claiming confidentiality against an attacker actively sniffing the LAN *during that short pairing window*. Normal authentication afterward doesn't resend the secret. That limitation is worth keeping explicit rather than pretending HMAC magically encrypts TCP.
