Apple’s AVAudioPlayer documentation states that:

• prepareToPlay() performs setup including audio-session activation.
• Letting a sound finish or calling stop() undoes that setup.
• play() implicitly calls prepareToPlay() if the player is no longer prepared.

This makes the completed-player play() at line 5103 the strongest remaining main-thread activation candidate.

E. Audio-session coordinator interactions

• AudioSessionOperationCoordinator is an actor and serializes its public operations.

G. Possible warning sources, ranked

1. High confidence: completed-player restart on MainActor.

At natural completion, Repeat calls startPreparedSoundPreview, which directly calls play() on the completed player. Apple documents that completion undoes preparation and play() implicitly prepares an unprepared player. That implicit preparation can activate AVAudioSession on MainActor.

This path matches the observed Repeat correlation and remains after Stage 8B.21 moved explicit preparation off-main.

2. Medium confidence: manual Play after natural completion.

The same startPreparedSoundPreview path is used when the user presses Play after a completed track. It has the same implicit-preparation risk, even with Repeat OFF.

3. Lower confidence: audio-session state changing between background preparation and main-actor play.

A newly prepared player should not need implicit preparation when play() follows immediately. However, speech recording, interruptions, or another audio subsystem could change session state in between. Source inspection does not establish that this is occurring.

4. Lower confidence: MainActor stop() during player replacement.

stop() is called on MainActor at line 5225. Apple documents that stop undoes preparation, but source inspection does not prove it is the direct source of the reported activation/deactivation warning.

5. Low confidence: explicit coordinator activation/deactivation.

Those calls are either iOS 27+ asynchronous APIs or older-iOS calls dispatched onto the blocking queue. Settings does not invoke them directly. They remain possible sources elsewhere in the app, but the supplied Repeat evidence does not point to them.

H. Can the warning be attributed to Repeat with certainty?

No.

Repeat does not directly activate the audio session. It only exposes the completed-player restart path more frequently. The strongest supported conclusion is that Repeat causes the existing completed-player play() path to run repeatedly, and that play() may implicitly prepare/activate on MainActor after completion.

A runtime backtrace is still required to attribute the exact warning to a particular AVFoundation call with certainty.

I. Smallest recommended correction

Do not change it in this probe.

The smallest safe implementation would be to alter only the completed-track branch of startPreparedSoundPreview():

• When hasSoundPreviewCompleted is true, do not reset currentTime and call play() directly.
• Instead, reuse prepareSoundPreview for the currently selected URL with shouldStartPlayback: true.
• Let the existing asynchronous coordinator preparation complete, install the new prepared player on MainActor, then call play() only after installation.

That single shared branch covers both:

• Repeat’s natural-completion restart.
• Manual Play after a completed track.

It preserves Repeat priority, Auto Start behavior, UUID protection, the single Settings-owned player model, and the Stage 8B.21 request-generation safeguards. It also avoids adding session ownership or changing session category/mode policy.

For definitive confirmation before changing behavior, set symbolic breakpoints on:

• -[AVAudioPlayer prepareToPlay]
• -[AVAudioSession setActive:withOptions:error:]
• -[AVAudioSession setActive:error:]

Capture the backtrace when the warning occurs during a Repeat completion. If temporary source diagnostics are preferred, place one timestamped 🐞 print immediately before line 5103 identifying whether the start is a normal start, resume, or completed-track restart. Do not add continuous logging.

J. Risks and older-iOS considerations

• Repreparing a repeating track introduces a small asynchronous gap between iterations; this is the expected tradeoff for avoiding main-thread preparation.
• If the selected file is deleted or becomes unreadable after completion, repeat should fail safely rather than starting another file.
• The proposed correction reuses the existing coordinator fallback, so iOS 17.x remains supported without requiring iOS 27 APIs.
• Do not modify the coordinator’s existing recording/session policy; speech-recognition ordering remains protected by its serialized gate.
• A cancelled queued preparation can still finish its queue work, but current request-ID and selected-URL checks prevent it from installing, retaining a delegate, or starting obsolete playback.
