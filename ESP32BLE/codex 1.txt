1. WKWebView creation sites

Set_Screen.swift:6725–6758 creates a WKWebView for every non-preloaded HTML page via makeUIView → makeWebView. Each has a new WKWebViewConfiguration and Coordinator. The page wrapper’s .id changes on every page transition (6223–6230), so each page gets a new SwiftUI representable and normally a new WKWebView. Pages are not loaded into one shared view.

2. Ownership and retention

Normal page WebViews are owned by their UIKit/SwiftUI representable lifecycle; no source collection, cache, or global owner retains old page views. No explicit dismantleUIView exists, so release is ARC/UIKit-driven after replacement. Source does not prove deallocation timing.

3. Preloaded WebView lifecycle

ESPHelpView owns PreloadedFirstPage as @State (5727–5744). Contents appearance invokes preloadIfNeeded, which creates only connect-mac.html once per Help presentation (6834–6853). Page 1 reuses that exact instance (6343–6353, 6725–6728). It remains retained while Help is open, including after Home. Closing releases the Help view’s state; reopening creates a new owner. Source shows no duplicate Page 1 WebView while preload succeeds.

4. Navigation/Home/Close

Using ESP and Troubleshooting pages each create a new WebView per page. Home removes navigation destinations but does not intentionally retain normal views. Close clears path and state (5814–5818). No Help-specific accumulation is confirmed.

5. WebKit configuration

Each normal page creates a default configuration (6740), with a document-start device-family script. No explicit WKProcessPool, WKWebsiteDataStore, or WKUIDelegate exists. loadFileURL grants access only to bundled Help (6811–6826). Coordinator restricts main-frame navigation (6877–6895).

6. Console warnings

Multiple WebContent PIDs are plausibly consistent with separate page WebViews and WebKit process management, but do not prove a leak. Sandbox/context/RBS/GPU idle messages are likely system-level WebKit behavior or insufficient evidence; source does not link them to an ESP fault.

7. Risks

Confirmed: repeated page navigation recreates and reloads normal WebViews. Unsupported: growing retained WebViews or process leak. Preloading reduces only Connect to Mac Page 1 initialization delay.

8. Recommended diagnostic

Add temporary 🐞 identifiers in makeWebView, Coordinator deinit, PreloadedFirstPage deinit, and navigation start/finish. On iPad Air M2, record creation/deallocation counts across page transitions and repeated open/close cycles.
