B. GRID CONSTRUCTION

The grid is eager, not lazy.

MainScreenGridSection creates:

• Array(functionKeys.prefix(visibleBoxCount).enumerated()) at line 257.
• A ZStack child for every visible position through ForEach at line 268.
• An EmptyView for continuation tokens, but each position still enters the ForEach.
• A full button hierarchy for non-continuation positions, including labels, backgrounds, borders, gestures, and for MIDI buttons, a UIKit touch-capture view.

For a 20 × 37 configuration, 740 position records are enumerated. Empty ordinary positions use a relatively small label branch, but they are still SwiftUI nodes. Populated MIDI positions are materially more expensive because they include MIDINoteButton, MIDITouchView, and, on iPad, temporary geometry probes.

Identity is id: .offset. This is stable for a fixed grid slot, which is appropriate while a grid remains unchanged. During a resize, occupied entries can be remapped to different offsets by ContentView, so SwiftUI correctly treats changed slots as changed content.

Grid calculations are repeated for each MainScreenGridSection body evaluation:

• Cell width and height.
• Button origin and resolved span size.
• buttonShape for each visible non-continuation position.
• renderedButtonGridVisualHeight performs another pass and calls buttonShape again.

These operations are linear in visible positions. buttonShape has a small fixed candidate set, so this is not an N-squared algorithm, but its cost grows directly with grid size.

C. SINGLE MIDI BUTTON UPDATE PATH

Momentary MIDI Note path:

1. MIDITouchCaptureView receives touchesBegan.
2. It calls beginMIDIActivation through MIDITouchView.
3. MainScreen.beginMIDIActivation validates the document, slot, command text, session, and output availability.
4. MainMIDIActivationRegistry.begin sends the MIDI Note On first; only an accepted send creates and stores a UUID token.
5. Adding the token changes the registry’s private activations dictionary.
6. The pressed button reads activeToken(for: context), receives a non-nil token, and displays the green border.
7. On touch end/cancellation/exit, MIDITouchCaptureView calls endMIDIActivation.
8. MainMIDIActivationRegistry.release removes that token and sends the required Note Off or CC release command.
9. The active border disappears when activeToken becomes nil.

Toggle and CC behavior retain their existing specialized paths. Note-Off uses local isNoteOffPressed state for transient visual feedback and reconciles matching active notes.

D. INVALIDATION SCOPE

The activation registry is @Observable, but activeToken(for:) reads the single activations dictionary.

Every MIDI button’s active-token query is made while MainScreenGridSection constructs its body. Therefore, a mutation of activations can invalidate the grid section’s observed dependency, potentially causing its body to re-evaluate and recreate all visible grid descriptions, including unrelated buttons.

This is source-supported potential broad invalidation. It does not prove that every button is laid out, rasterized, or physically redrawn after every press:

• Body re-evaluation: potentially broad.
• Layout: SwiftUI may reuse unchanged layout results; source inspection cannot quantify it.
• Rendering: SwiftUI can retain unchanged rendered output; it is not correct to claim all 740 buttons are redrawn.
• MIDI transmission: remains limited to the pressed button’s validated command and required release.

The active-token lookup also linearly searches active activations. Normally that collection is small, so this is not the practical primary cost; the broad observed dictionary dependency is more significant.

E. ONCHANGE WARNING

The exact warning source cannot be proven from the warning text alone. SwiftUI reports only the observed type, String, not the view or property name.

The strongest source-supported candidate is the Soft Editor’s bidirectional synchronization:

• editingSlotText onChange can call syncDraftsFromCombinedText.
• That method changes actionDraft and rightDraft.
• Their onChange handlers call syncCombinedTextFromDrafts.
• That method can change editingSlotText again.

There are equality checks and an asynchronous reset of isSyncingDraftsFromCombinedText, but this remains a cyclic String-observer graph. It is the only inspected Main Screen String onChange path that writes one of the other observed Strings and can write back to the original observed String.

The Main Screen’s selectedDocumentName, selectedDocumentDisplayName, and renameAlertMessage handlers mutate other state but do not write their observed String back. The counter and timer configurationText handlers write local numeric/string display state, not configurationText.

Conclusion:
• If the warning occurs while the Soft Editor is presented, this loop is the most likely source.
• If Test D reproduces it with no slot editor open, source inspection alone is insufficient to identify the exact handler. The next diagnostic stage should add one temporary timestamped print at the entrance of only the four Soft Editor sync observers, including a frame counter and current values. No grid-wide logging is needed.

Therefore, the diagnostics do not directly explain:
“onChange(of: String) action tried to update multiple times per frame.”

They do add real layout-observation overhead on iPad MIDI buttons. At large grids with many populated MIDI buttons, they can increase main-thread layout work and console activity. They should remain untouched as requested until the planned cleanup.

G. GRID RESIZING

Each row/column action calls applyGridDimensions.

The resize sequence is:

1. Validate proposed dimensions and maximum position count.
2. ContentView.resizeSelectedDocumentGrid remaps occupied slot lines into the new grid.
3. persistSlotLines synchronously serializes and writes the screen document.
4. applySlotLines reparses lines and replaces the entire functionKeys array.
5. MainScreen updates visibleGridDimensions and visibleBoxCount.
6. Grid configuration is persisted separately through saveGridDimensions.
7. SwiftUI reconstructs the visible grid for the new dimensions.
8. MainScreen observes functionKeys.map(.rawLine), resets MIDI activations, and observes definedFunctionKeyCount to ensure capacity.

A rapid row/column sequence can therefore perform repeated whole-grid remaps, synchronous file writes, parse/replacement of functionKeys, state updates, and view reconstruction. This is a much more plausible reason for warning volume and interaction pressure than pressing one MIDI button.

H. GESTURE TIMEOUTS

There is no source evidence that the reported system gesture-gate timeout is caused by a MIDI protocol error or the String onChange warning.

Relevant source conditions:

• MIDI uses UIKit touch capture, not the ordinary SwiftUI Button gesture path.
• Slider movement scans registered MIDI touch views to locate a target; this is linear in active MIDI capture views during a slide.
• Resizing performs synchronous remapping, parsing, persistence, and eager grid reconstruction on the main actor.
• Large populated MIDI grids can contain many UIKit touch views and temporary measurement views.

These facts make main-thread pressure during rapid resizing plausible. They do not establish a direct cause for Apple’s system gesture timeout messages.

I. PERFORMANCE RISKS

Highest practical importance:

1. Eager construction of every visible position.
   • Cost grows with grid position count.
   • 740 positions are all enumerated and participate in the ZStack.

2. Whole-grid activation dependency.
   • A one-button MIDI press can invalidate the MainScreenGridSection because every active-token lookup observes the same dictionary.

3. Resizing writes and replaces whole grid data synchronously.
   • Each dimension change remaps slots, persists a document, reparses entries, and reconstructs the grid.

4. Temporary MIDI geometry probes.
   • iPad-only, but multiply GeometryReader and CGRect observation work for each populated MIDI button.

5. Per-button image tasks.
   • MainScreenButtonLabelView has a task keyed by image request, including button size. A resize can restart image work for image-backed buttons.

The same code paths serve 4 × 4, 6 × 8, 10 × 10, and 20 × 37. The difference is the number of materialized positions and populated-content hierarchies; no benchmark timing can be inferred from source.

J. MINIMAL CORRECTIONS

No change is justified from source inspection alone for the MIDI activation registry. A per-button observation redesign could reduce broad invalidation, but it carries meaningful risk to simultaneous touches, toggles, holds, slides, cancellation, and note ownership. It should be considered only after a focused measurement confirms press latency or excessive re-evaluation.

One narrow correction is justified if the warning is reproduced with the Soft Editor visible:

• Make the editor synchronization one-directional per user event, or consolidate actionDraft/rightDraft/combined text into one source of truth.
• The correction should avoid any onChange handler writing another String that then writes back to the original String in the same update cycle.
• Preserve current normalization, hidden-state metadata, and editor behavior.

Do not debounce grid persistence or replace the eager absolute-position grid with LazyVGrid without separate design validation; either could alter current grid geometry, persistence timing, slot remapping, or spanning buttons.
