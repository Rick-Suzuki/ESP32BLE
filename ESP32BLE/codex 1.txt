1. Confirmed Screen-specific bottleneck

The strongest confirmed issue is in the Screen table’s green-state check:

• Set_Table.swift:610 calls isLoadedDocument(fileURL) for every Screen row.
• Set_Screen.swift:2363 supplies that closure as:
selectedDocumentFileURL?.path == $0.path
• Set_Screen.swift:3524 calculates selectedDocumentFileURL by rebuilding availableDocumentURLs.
• Set_Screen.swift:3594–3600 rebuilds that collection by checking resource values for every directory entry, filtering, then sorting.

Therefore, every Screen-row render can rescan and sort the whole document snapshot. A Screen selection invalidates the Screen rows because their yellow/green/bold styling depends on selectedScreenSelectionPath, so rapid navigation can cause repeated main-thread directory-metadata filtering and sorting before SwiftUI reaches PlainDocumentEditor.updateUIView.

Text and Markdown do not do this per row:

• Text row: Set_Table.swift:683–684 compares selectedTextSelectionPath and loadedDocumentURL directly.
• Markdown row: Set_Table.swift:731–732 uses the same direct comparison pattern.

This is the meaningful Screen-versus-Text difference found in the active source.

Thus, normal navigation preserves the green active Screen and does not trigger Main Screen configuration loading.

3. Screen versus Text rendering differences

Screen rows are more expensive than Text rows in two ways:

• Each Screen row performs the expensive isLoadedDocument closure described above.
• Each Screen row also contains a two-tap exclusive gesture plus duplicate and delete swipe-action branches: Set_Table.swift:639–679.

Text rows use a direct Boolean calculation and a normal Button: Set_Table.swift:682–727.

The unique per-row directory rebuild is the most likely substantial source of the measured difference. It is structurally O(number of Screen rows × document snapshot work) for a Screen-table refresh, whereas Text uses direct URL/path comparisons.

4. Editor lifecycle

The editor itself remains shared and inexpensive:

• SettingsEditorSectionView: Set_TxtEditor.swift:386–420.
• PlainDocumentEditor.updateUIView: Set_TxtEditor.swift:65–116.

The recorded 1–4 ms UIKit work is consistent with this code. PlainDocumentEditor is not recreated by Screen navigation; it receives the changed text through the same binding used by Text and Markdown.

The delay occurs before updateUIView because SwiftUI must first process the invalidated Settings/table hierarchy. The Screen-row active-state computation is on that path.

5. Observers and warnings

Two String-based observers are relevant:

• Set_Screen.swift:820–823 observes documentEditorText. During a navigation assignment, it normally receives the new text after previewScreenDocument has completed. Its loading guard may no longer be true by then, so it can call saveCurrentDocumentText(). This behavior is shared by Screen, Text, and Markdown and does not explain the Screen-only difference.
• Set_Screen.swift:830–832 observes settingsModeEditResetKey. A Screen selection changes that computed String, then cancelNameEditing() writes title/focus-related state at Set_Screen.swift:3940–3944. Text and Markdown selections also change this key, so it is a possible contributor to transaction churn but is not Screen-specific.

The source does not contain a direct onChange(of: Optional<UUID>) in the Settings navigation path. The closest matching mechanism is:

• Set_Table.swift:191–202: task(id: documentNavigationRequest?.id).

Stage 6C.6 bypasses creation of that request for Screen navigation at Set_Screen.swift:2209–2213. Therefore it should not be the continuing cause during the enabled Screen-scroll isolation test. The warning cannot be conclusively attributed from its generic SwiftUI console text alone.

8. Recommended smallest production correction after the A/B result

Pass a precomputed active Screen path or active Screen URL into SettingsDocumentTableSection once, rather than passing the per-row isLoadedDocument closure.

Then documentRow should compare the current row directly with that already-resolved value. It should use the documentFiles collection already passed to the table, rather than recomputing availableDocumentURLs per row.

Likely implementation files:

• Set_Screen.swift: documentTableSection around lines 2326–2365.
• Set_Table.swift: documentRow around lines 609–615.

This retains yellow preview versus green active Screen behavior, existing row gestures, saving safeguards, and selection semantics.
