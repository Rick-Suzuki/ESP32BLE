B. Current Documents path construction

SR_Substitutions.swift obtains the directory using:

FileManager.default.urls(
for: .documentDirectory,

in: .userDomainMask

).first

It then appends:

SpeechSubstitutions.txt

The same URL construction is used for:

• Existence checks
• File creation
• File reading

There is no cached file URL.

The absolute sandbox path naturally differs between simulator, iPhone, and iPad, but the source uses the correct platform-provided Documents directory in all cases. No path mismatch was found.

C. Current default contents and generation

The current Swift default string is:

// Speech Recognition Substitutions
up<TAB>app
get her<TAB>github
middy<TAB>midi
you tube<TAB>youtube

The source uses Swift "\t" escapes, which produce actual tab characters at runtime.

The file is generated from the Swift string in SR_Substitutions.swift. It is not copied from an Xcode bundle resource.

The file is written as UTF-8 using:

write(to:atomically:encoding:)

with atomic writing enabled.

The multiline Swift literal uses LF-style line separation. Exact filesystem line endings would require runtime inspection, but no CRLF conversion is present in the source.

The requested layout is not currently present.

D. Current file-creation lifecycle

SpeechSubstitutions.load(normalize:) performs this sequence:

1. Obtain the Documents directory.
2. Append SpeechSubstitutions.txt.
3. Check file existence.
4. If missing, write defaultContents atomically.
5. Read the file as UTF-8.
6. Parse valid substitution rules.

However, this function is not called during application startup.

The only current call is from handleSpeechRecognitionToggle() when speech recognition is switched ON.

There is:

• No startup call from MainScreen.onAppear.
• No startup call from ContentView.task.
• No app-launch call from ESP32BLEApp.swift.
• No cached initialization flag.
• No cached file URL.

The parent Documents directory is not explicitly created. Normally the application Documents directory already exists. If the directory URL is unavailable or the write fails, the function returns an empty rule list.

E. Current speech ON/OFF and reload lifecycle

When speech is switched ON:

• Editing-state blocking is checked first.
• If not blocked, SpeechSubstitutions.load(normalize:) is called.
• The file is checked and created if missing.
• Rules are loaded into speechSubstitutionRules.
• Speech recognition is enabled.

When speech is switched OFF:

• The automatic-off task is cancelled.
• Recognition is disabled.
• The substitution file is not accessed.

Switching speech OFF and then ON causes a fresh file check and reload.

Automatic recognition-session restarts inside SR_Manager.swift do not call handleSpeechRecognitionToggle(). They restart recognition only and reuse the currently cached rules.

Therefore, editing the file while the app is running requires speech OFF followed by speech ON to reload it.

F. Confirmed reason the file is not recreated

Confirmed source behavior:

The file is not recreated on application startup because no startup path calls SpeechSubstitutions.load(normalize:).

MainScreen initializes:

isSpkRecEnabled = false

and does not load the substitution file in its startup lifecycle.

Therefore, if the user deletes the file while speech is disabled and then restarts ESP, the file remains absent until speech recognition is explicitly switched ON.

This explains the reported behavior if speech was not toggled ON after restarting ESP.

No stale URL or once-per-process creation flag was found.

If the file was deleted and speech was explicitly switched ON after restart, the source indicates that recreation should be attempted. Failure in that situation cannot be confirmed from static source alone. Possible runtime causes would include:

• The toggle handler was not reached.
• The file was deleted from a different location.
• Documents-directory access failed.
• File writing failed.
• The file was created but was not visible through the method used to inspect Documents.

The current implementation silently hides all such errors.

G. Smallest safe correction

Recommended design:

1. Add a small idempotent file-existence helper in SR_Substitutions.swift.
2. Have it use the same Documents URL and filename as load(normalize:).
3. Create the default file only when it does not exist.
4. Call that helper from an existing application-startup lifecycle hook.
5. Keep the existing load(normalize:) call when speech is switched ON so rules are still freshly reloaded.
6. Replace only defaultContents with the requested layout.

The safest localized startup locations are:

• MainScreen.onAppear, if MainScreen is guaranteed to exist at startup.
• The existing ContentView startup .task, which is already used for application initialization.

A dedicated ensure-file-exists helper is preferable to loading and parsing rules at startup because startup only needs to guarantee file existence. Speech activation can continue to perform the actual rule loading.

H. Recommended default file text

The requested content should be:

// Speech Recognition Substitutions
// put your recognized word on the left
// and your substitute word on the right
// separated by tabs
//
// recognized word<TAB>substitute word

up<TAB>app
get her<TAB>github
middy<TAB>midi
you tube<TAB>youtube

Each <TAB> above must be an actual tab character.

There are six consecutive comment lines before the blank line, including the column-header comment. The file should contain a blank line before the substitution entries.

In the Swift source, tabs should be represented as \t, for example:

"up\tapp"

The displayed file must contain actual tab characters, not the literal characters backslash and t.

Existing user-created files must never be replaced or reformatted.

I. Parser compatibility

The current parser already accepts the proposed layout.

Verified behavior:

• Blank lines are ignored.
• Comment lines are ignored after surrounding whitespace is trimmed.
• Comment lines with leading tabs are ignored.
• Leading tabs are removed.
• Trailing tabs are removed.
• Multiple separator tabs are treated as one separator.
• Spaces inside phrases such as get her and you tube are preserved.
• Surrounding whitespace around each field is trimmed.
• Lines without a separator are rejected.
• Lines with more than two nonempty tab-separated fields are rejected.
• Empty source or replacement fields are rejected.
• Duplicate normalized source phrases are ignored after the first valid occurrence.
• Parsing operates in memory and does not rewrite the source file.

No parser change is necessary for the proposed default layout.

J. Error handling and diagnostics

Current failures are silent.

The following conditions return an empty rule list without diagnostic output:

• Documents directory unavailable.
• Default-file creation failure.
• File read failure.
• UTF-8 decoding failure.

No current diagnostics report:

• The resolved file path.
• Whether the file existed.
• Whether creation was attempted.
• Creation errors.
• Read errors.
• Number of loaded rules.

Recommended future diagnostics, if needed, would be minimal print statements beginning with 🐞, such as:

• File path and existence status.
• Creation failure and error description.
• Read/decode failure and error description.
• Number of valid rules loaded.

No diagnostics should print file contents or be emitted for every recognition callback.
