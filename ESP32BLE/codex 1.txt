5. Confirmed cause of the excessive editor width

Confirmed cause: the editor and Delete button do not share a measured layout constraint.

The editor uses an independently reconstructed width:
• Four assumed 72-point buttons.
• Three assumed 8-point gaps.

The actual bottom row instead contains:
• One intrinsic-width Help control.
• Three 72-point controls.
• Three 8-point gaps.
• A parent-relative max-width frame.

This overestimates the visible row’s trailing edge, making the white editor viewport wider than Delete.

The negative leading padding is a separate placement adjustment. It does not establish a shared trailing coordinate with Delete.

6. Viewport versus image content

The excessive visible width is the editor viewport/border, not the aspect-fill image.

Evidence:
• The editor’s white border is rendered by the Rectangle stroke in Set_ImgPanel.swift:50-53.
• That stroke uses the GeometryReader’s assigned width and height.
• The aspect-fill image is framed to exactly those same dimensions at lines 29-32.
• Clipping occurs at line 49 before the border overlay.

Therefore:
• The image may overflow internally because of scaledToFill.
• That overflow is clipped correctly.
• It cannot extend the white border.
• If the border reaches beyond Delete, the allocated editor container width is oversized.

8. Recommended minimal correction

Do not continue calculating editor width from four nominal button widths.

Modify only:
• Scrns/Set_Screen/Btm_Area/Set_AvailableDevices.swift

Recommended layout relationship:
• Measure the actual rendered bottom-row control content width, including the intrinsic Help button and current HStack spacing.
• Make the editor viewport use that measured width and the same leading alignment origin as the bottom row.
• Remove the separate reconstructed iPhoneEditorViewportWidth formula.
• Keep the existing vertical stack, top header, Close button, and image-preview component unchanged.

A small preference-key measurement for the bottom HStack’s rendered content bounds is the least invasive approach. The editor should consume that actual width after layout, rather than inferring it from component constants. This shares the same visible trailing boundary as Delete on either phone size and avoids device-specific offsets.

Risk to watch:
• The measured value must describe the HStack’s visible content bounds, not only its enclosing maxWidth frame. Measuring the wrong modifier level would reproduce the current mismatch.
• Initial layout should use a safe provisional width until the measured width is available.
