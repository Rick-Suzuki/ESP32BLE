2. Current viewport hierarchy

Confirmed:

• SettingsScreenBase selects a separate iPad or iPhone layout.
• On iPad, Images replaces the upper left editor area with largeImagePreviewSection. Bottom Settings controls remain below it.
• On iPhone, the fixed-width available-devices column hosts iPhoneImageEditor only while the local iPhone presentation state is active.
• SettingsImagePreviewPanel owns the black image viewport, clipping, border, image rendering, and asynchronous image load.
• The iPhone Close button is outside the preview panel and is a sibling in the top control row.
• The file table and image-navigation controls are outside the preview panel.

This is a good boundary for gestures: the gesture layer can be added inside SettingsImagePreviewPanel without changing any approved editor geometry.

3. Current fitting and clipping behavior

Confirmed:

• iPhone passes usesAspectFill: true, so its initial image is scaledToFill.
• iPad passes usesAspectFill: false, so its initial image is scaledToFit.
• The preview ZStack has a fixed GeometryReader-derived frame, then .clipped(), then the border overlay.
• The iPhone border is one physical pixel: 1 / displayScale.
• At scale 1.0, the current visual behavior is already exactly the required minimum zoom state.

A future zoom transform must be applied to the image content inside this existing clipped ZStack. It must not be applied to the GeometryReader, the outer panel, or the border.

4. Recommended gesture implementation

Use native SwiftUI gestures in SettingsImagePreviewPanel:

• MagnifyGesture for pinch zoom.
• DragGesture for one-finger pan.
• Attach both only to the image viewport content.
• Use simultaneous gestures, but suppress drag updates while a magnification gesture is actively changing. This avoids a two-finger pinch also being interpreted as a pan.
• Do not attach either gesture to the Settings parent, table, navigation controls, or Close button.
• Keep the existing clipping and border outside the transformed image.

The project deployment target is iOS 17.6, so MagnifyGesture is available on the supported iPhone and iPad population. Apple’s current SwiftUI documentation confirms MagnifyGesture supplies a relative magnification value and is intended to be combined with transient gesture state.

For Stage 2B, use center-based scaling. This is the smallest robust change and preserves the approved scale-1 rendering exactly.

Focal-point zoom is better deferred to Stage 2C. It needs careful anchor-to-viewport coordinate conversion and offset correction; it should not be a dependency of basic bounded zoom and pan.

5. Recommended state ownership

Keep all temporary interaction state private to SettingsImagePreviewPanel:

• committedZoomScale: persistent only during the panel’s current lifetime; starts at 1.0.
• activeMagnification: @GestureState holding the in-progress pinch multiplier; starts at 1.0.
• committedPanOffset: @State CGSize; starts at .zero.
• activeDragTranslation: @GestureState CGSize; starts at .zero.
• isMagnifying: transient state used to prevent pinch and drag competing.
• Current viewport size: derive directly from the existing GeometryReader.
• Current image aspect ratio: derive from the already decoded previewImage.

None of this belongs in screen configuration, selectedImageURL, previewImageURL, background persistence, or saved screens.

6. Pan-boundary calculation

Let:

• Vw, Vh = viewport width and height.
• Iw, Ih = decoded image dimensions.
• S = effective zoom scale, clamped to at least 1.0.
• B = the image’s rendered size at its existing scale-1 presentation.

For iPhone aspect fill:

• baseFactor = max(Vw / Iw, Vh / Ih)

For iPad aspect fit:

• baseFactor = min(Vw / Iw, Vh / Ih)

Then:

• baseWidth = Iw × baseFactor
• baseHeight = Ih × baseFactor
• scaledWidth = baseWidth × S
• scaledHeight = baseHeight × S

The permitted pan ranges are:

• maxPanX = max(0, (scaledWidth - Vw) / 2)
• maxPanY = max(0, (scaledHeight - Vh) / 2)

Clamp the rendered offset independently:

• x: -maxPanX...maxPanX
• y: -maxPanY...maxPanY

Important rules:

• At scale 1.0, force offset to .zero and ignore drag input.
• This preserves iPhone’s existing cropped aspect-fill view.
• This also preserves iPad’s intentional black space for an aspect-fit image.
• Pan becomes available only when zoom actually creates movable overflow in that axis.
• The transformed content stays centered and cannot be dragged fully out of the viewport.

7. Minimum and recommended maximum zoom

Minimum zoom: exactly 1.0.

This means the current image presentation, not source-image pixel size:

• iPhone: current aspect fill.
• iPad: current aspect fit.

Recommended Stage 2B maximum: 2.0x.

Reasoning:

• The present decoder targets only the viewport’s largest pixel dimension.
• At 2.0x, quality can soften because the already-downsampled bitmap is being enlarged, but memory use remains stable.
• A 3x or 4x cap without decoder work would make softness more visible.
• Increasing the decode target to support 3x or 4x also multiplies decoded pixel memory substantially, especially on iPad Pro and older iPad mini hardware.

A later Stage 2C can evaluate a higher cap after physical-device testing and decoder tuning.

8. Image identity and reset recommendation

Recommended predictable behavior:

• Selecting a different image: reset zoom to 1.0 and pan to center.
• Reset, Random, Previous, and Next: reset zoom and pan because they replace previewImageURL.
• Image deletion: reset when the preview is cleared or replaced through the existing selection logic.
• iPhone Close/reopen: reset naturally. The conditional iPhone editor is removed from the view hierarchy when closed, so preview-local state is recreated at its default values on reopen.
• Leaving Images or leaving Settings: reset naturally when SettingsImagePreviewPanel leaves the hierarchy.
• Rename: preserve the current zoom and pan where practical.

The current preview identity is URL-path based. A rename changes previewImageURL to the renamed URL, even though it remains the same file content. Therefore, a basic Stage 2B URL-change reset would reset after a rename.

For Stage 2B, that is safe and simple. For Stage 2C, preserve rename state by tracking a stable file resource identifier when available, with standardized URL fallback. That avoids conflating a renamed image with a newly selected image.

9. Image loading, downsampling, and memory findings

Confirmed:

• The current preview task identity includes the image path and viewport pixel dimension.
• The image is downsampled off the main actor in a detached task.
• The decoder creates a CGImageSource thumbnail, preserving orientation transforms.
• Stale results are rejected using previewRequestID.
• Gesture changes will not trigger reloads because zoom and pan do not alter the existing task identifier.

Current decode target:

• max(viewport width, viewport height) × UIScreen.main.scale

This is correct for the approved scale-1 rendering. It is deliberately conservative for memory, but it does not provide source-resolution detail at high zoom.

Recommendation:

• Stage 2B: leave the loader unchanged. Do not reload during pinch or drag.
• Stage 2C: if testing shows unacceptable softness, decode once for the selected image at a capped target suitable for the maximum permitted zoom. Keep the current background decode and stale-request safeguards.
• Do not decode full-resolution photographs just because an image is zoomable.
• Keep at most the current preview bitmap unless physical testing demonstrates a small, bounded cache is necessary.

10. Gesture interaction risks

Low-risk areas:

• The image table is a sibling, not an ancestor or child of the image viewport, so an image-only gesture does not need to affect table scrolling.
• Image application is currently invoked from table double-tap behavior, not from the preview panel.
• Navigation and Close are sibling controls, outside the clipped viewport.

Risks to control in implementation:

• Do not use a parent-level gesture modifier.
• Do not use high-priority gestures that could capture touches intended for controls.
• Do not add a tap or double-tap gesture to the preview.
• Ensure the transformed image remains inside the existing clipped ZStack.
• Re-clamp pan when zoom changes, viewport size changes, or the preview image changes.
• Avoid animation while fingers are moving; optional settling animation can be considered only after testing.
