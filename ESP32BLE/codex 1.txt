A. Executive summary

CONFIRMED FROM CURRENT SOURCE: the tick callback does not set isHelpPresented to false when tapped. It only sets the coordinator’s private shouldBePresented flag to false and starts UIKit dismissal.

The binding is changed to false only after dismissal completes.

This leaves a transition window where SwiftUI still reports isHelpPresented == true. If updateUIViewController runs during that window, synchronizePresentation sets shouldBePresented back to true. The dismissal completion then deliberately schedules a fresh presentation when shouldBePresented is true.

This is the most likely source-supported explanation for the observed immediate reopen.

G. Coordinator presentation logic

synchronizePresentation at lines 6427–6438 always does:

shouldBePresented = isPresented

If true, it calls presentHelpIfNeeded.

presentHelpIfNeeded will not present if:

A Help controller is already stored.

Presentation or dismissal is in progress.

A valid attached presenter is unavailable.

The presenter is already presenting another controller.

A UIKit transition requires one deferred main-queue retry.

If presentation succeeds, it stores the controller, marks isPresentationInFlight true, and calls presenter.present.

The deferred retry at lines 6642–6661 checks shouldBePresented before calling presentHelpIfNeeded.

H. Coordinator dismissal logic

The tick path calls dismissHelpFromCloseButton.

That sets only private shouldBePresented = false, then begins UIKit dismissal.

The binding remains true until the programmatic dismissal completion.

completeDismissal clears stored controller state and flags. It then does one of two things:

If synchronizeState is true, or shouldBePresented is false:
It writes false to the binding.

Otherwise:
It schedules presentHelpIfNeeded on the main queue.

The otherwise branch is intended to support a legitimate request to reopen Help during dismissal. It is also the branch that can cause the observed undesired reopen if shouldBePresented was reset to true by a stale or intermediate SwiftUI update.

I. Presentation delegate behavior

The only implemented presentation delegate callback is:

presentationControllerDidDismiss

It is at lines 6464–6472.

For a native interactive dismissal, it:

1. Sets shouldBePresented = false.
2. Calls completeDismissal with synchronizeState: true.
3. Writes false to the SwiftUI binding.

There are no presentationControllerWillDismiss or presentationControllerShouldDismiss implementations.

The programmatic tick path does not rely on the delegate; it uses the dismiss completion closure. This covers programmatic dismissal even if the delegate callback is not invoked for that path.

The delegate does not itself schedule presentation.

During the dismissal animation, SwiftUI invokes updateUIViewController with the still-true binding. That resets shouldBePresented to true before the UIKit dismissal completion. Completion then selects the re-presentation branch, producing the observed down-and-immediately-reappear behavior.

No current event-specific logs establish that exact timing, but the source contains this complete re-presentation path and the user’s observation matches it.

→ Help form sheet reappears

M. One recommended minimal correction

RECOMMENDATION:

In dismissHelpFromCloseButton, synchronize the SwiftUI binding to false before starting UIKit dismissal.

The future change should be limited to the coordinator at lines 6441–6444:

1. Set shouldBePresented = false.
2. Call setPresentedState?(false).
3. Call dismissHelpIfNeeded.

This makes SwiftUI’s source-of-truth state false at tick time, rather than after the dismissal animation. Subsequent representable updates should then carry false and cannot reset shouldBePresented to true without a new explicit Help-open action.

Do not remove the existing programmatic dismissal completion synchronization. It remains useful as an idempotent cleanup path. Do not change sizing, presentation style, navigation, or diagnostics.
