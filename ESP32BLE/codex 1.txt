C. Why taps near text can clear it

Verified:
• The clear button is a top-leading overlay placed after the preview text view in the view hierarchy.
• The overlay is above SmartPreviewTextView for hit testing.
• Its 56 x 53-point rectangular contentShape intercepts touches before they reach the underlying UITextView.

Likely consequence:
• A touch near the upper-left part of a label, including the upper area of the first character, can land inside the clear button’s rectangular hit region.
• The issue is more likely when text is positioned near the preview’s top-left area or when a smaller preview makes this fixed 56 x 53-point region occupy a larger fraction of the preview.

There is no source indication that the preview background or parent container itself clears text. The overlay button is the direct interception path.

D. iPhone and iPad implementation

Verified:
• Both iPhone and iPad call the same smartButtonPreview function.
• Both therefore use the same smartButtonPreviewClearButton.
• The clear hit area is fixed at 56 x 53 points on both devices.

Layout differs:
• iPad preview height is currently 110 points.
• iPhone preview dimensions are dynamically derived from the right-panel width and preview enclosure height.
• The fixed clear area is therefore proportionally more intrusive on smaller iPhone previews.

E. Smallest safe hit-area reduction

Recommended smallest change:
• Keep the overlay alignment, visible x glyph, font, color, and action unchanged.
• Reduce only the clear button’s local label frame and its contentShape to a compact fixed rectangle around the existing glyph.

A local frame/content-shape adjustment is sufficient. No global button behavior, preview geometry, text view, or layout change is needed.

The current code makes the x visually inset through padding while retaining a 56 x 53-point hit rectangle. The safest implementation would preserve the glyph’s current apparent position while replacing the oversized label/content-shape geometry with a compact explicit hit region.

Exact compact target size should be device-tested. A region around 24–28 points square is likely enough to encompass the existing glyph while avoiding nearby text interception, but this is a product/usability decision and has not been implemented.

F. SmartPreviewTextView interaction

Verified:
• SmartPreviewTextView is a UIKit UITextView wrapper.
• It normally receives taps to become first responder and uses UITextView’s standard cursor placement.
• Its textViewDidChangeSelection records the cursor in smartButtonPreviewSelectionRange.
• The clear button overlays this text view, so touches inside the clear button’s content shape do not reach UITextView and cannot position its cursor.

There is no indication of focus restoration causing the accidental clear. The direct cause is the overlay button’s hit-testing region.

G. Clear action scope and risks

Verified action behavior:
• Clears the right button text through smartButtonTextBinding.
• Does not alter the left command text.
• Does not directly alter smartButtonPreviewSelectionRange.
• Does not directly alter hidden-button metadata.

Color behavior:
• smartButtonTextBinding preserves an existing color prefix by storing colorPrefix: when text is cleared.
• Therefore, it clears the label while retaining color metadata.

SF Symbol behavior:
• If no color wrapper applies, clearing smartButtonTextBinding clears the stored SF Symbol representation and subtitle.
• This matches the control’s accessibility label: “Clear button symbol and text.”

Potential regression checks for a future local hit-area change:
• iPhone and iPad intentional clear taps.
• Ordinary and multiline labels.
• Cursor placement at the first character and near the upper-left text area.
• SF Symbol subtitle mode.
• Color-formatted labels.
• Preview scaling and dynamic font fitting.
• Save, close, and reopen.
• Existing keyboard focus behavior after a non-clear text tap.
