B. CURRENT IPHONE IMPLEMENTATION

The app already separates iPad and iPhone at the SwiftUI layout level:

• iPad uses SettingsSoundPlayerView with usesCompactLayout: false.
• iPhone uses the same view with usesCompactLayout: true.
• The iPhone player is displayed only while Sounds is active, inside SettingsAvailableDevicesPanel.iPhoneSoundPlayerBody.

The current compact layout is not the requested design. It contains:

• Audio filename centered at the top.
• Slider, then elapsed/total time on separate left/right positions.
• Small transport buttons.
• Photo Random button.
• Disabled “Auto Start” and “Random” labels, rather than working controls.
• No Repeat control.

The current iPhone player is already inserted into the same dynamically measured rectangle used for the iPhone large IMAGE/PDF/editor preview. Its width is taken from iPhoneBottomControlsContentWidth; it is therefore the correct integration point to preserve the existing rectangle’s location and width.

Recommended replacement scope:

• Replace only compactPlayerBody in Set_SoundPlayer.swift with a purpose-built iPhone player body.
• Retain iPadPlayerBody, iPadPlayerControls, iPadControlRowLayout, and all shared state/actions unchanged.
• Rename the compact branch conceptually to iPhonePlayerBody during implementation, if desired, but preserve the existing API boundary unless a small clarity-only refactor is clearly safe.

Audio state and player lifecycle already shared by both interfaces:

• start/stop progress task, at 100 ms updates.
• stopSoundPreviewPlayback teardown when leaving Sounds, Settings, deleting an active preview, or superseding preparation.

Preparation is asynchronous and protected:

• Existing preparation cancels the previous task.
• The request identifier, task cancellation state, and selected URL are checked before installing a prepared player.
• AVAudioPlayer construction and prepareToPlay occur off the main actor through AudioSessionOperationCoordinator.
• Completion is accepted only when its playback identifier matches the active player.

Existing navigation behavior:

• Auto Start determines whether manually selected Previous/Next sound begins playback.
• Random Track changes Previous/Next and automatic next-selection to select a different sound whenever possible.
• Repeat takes precedence over Auto Start/automatic navigation on natural completion.
• Natural completion triggers Photo Random once, then Repeat or Auto Start navigation.
• Manual Previous and Next trigger Photo Random after successful sound navigation.
• No second image change occurs for automatic navigation after natural completion because the automatic image selection is performed before the next sound is selected.

Shared image state and behavior:

• availableImageURLs.
• selectedSoundBackgroundImageURL.

The existing loader should be retained unchanged:

• Target-size downsampling.

• Latest pending request wins.

F. IMAGE-CONTROL CATEGORY ROUTING

The outside IMAGE controls remain geometrically independent of the player and are correctly category-routed now.

When Sounds is active:

• Back resets the Sound background image to index 0.
• Previous/Next change settingsSoundBackgroundImageIndex.
• Random selects a different Sound background image when multiple images are available.
• Opacity writes settingsSoundBackgroundOpacity.
• None of these controls select audio tracks or modify the Main Screen background-image state.

When Images is active, the same controls operate the regular preview/Main Screen image selection path instead.

This routing is concentrated in Set_Screen.swift lines 2797–2899 and should not be moved or duplicated.

G. RISKS

• State duplication: Creating separate iPhone audio, image-index, opacity, or player lifecycle state would desynchronize iPhone/iPad behavior and risks stale AVAudioPlayer completion events.
• Completion ordering: Do not move Photo Random into the view. It must remain in the parent’s existing navigation/completion methods to avoid duplicate changes.
• Loader lifecycle: The iPhone view must retain the current playerBackground path so cancellation and generation guards continue to work on category/view transitions.
• Geometry: A fixed vertical stack using iPad-like button sizes can overlap the existing connection controls or bottom strip on XS Max. Size from the player container’s GeometryReader.
• Touch handling: Preserve playerBackground.allowsHitTesting(false); only overlay controls receive touches.
• Visibility: Bright images can reduce white-control contrast. Reuse the existing button fills and white text; do not add a gradient or separate dark image overlay.
• Button target size: Existing compact controls are 32 points, below the conventional 44-point target. The requested large iPhone transport buttons should improve this where space allows; other mode controls should be given the largest adaptive size that preserves no-overlap.
• Audio-session behavior: Settings preparation uses AudioSessionOperationCoordinator, but configurePlaybackSession is currently called through the speech support path, not directly in the Settings Sound methods. This is existing architecture and should not be changed during a layout-only stage.
• AnyView handoff: The existing iPhone panel takes AnyView content. Preserve this handoff for the first layout stage; restructuring it would exceed the requested layout scope.
