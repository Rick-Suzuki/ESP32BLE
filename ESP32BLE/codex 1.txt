3. Current Markdown handling

Confirmed: Settings does not currently discover .md files.

availableTextURLs only accepts the legacy text extension, .txt:
• Set_Screen.swift lines 2892-2899.

There is no .md, .markdown, or Markdown-rendering implementation in Settings.

Markdown is already partially supported elsewhere:

• Main Screen command classification recognizes .md as a file:
   • Main_ButtonBehavior.swift lines 357-375.

• Main Screen preview accepts .md:
   • supportedPreviewExtensions, lines 2450-2452.
   • Preview routing, lines 1726-1738 and 1877-1910.

• That preview reads Markdown as UTF-8 plain text. It does not render Markdown:
   • MainScreenFilePreviewOverlay, lines 24-35.
   • It displays Text(contents) in a monospaced scroll view.

• The Soft Editor Files menu already has a combined Txt/MD category:
   • Main_Screen.swift lines 6733-6749.
   • It allows txt, md, and markdown.

Important inconsistency:
• The Soft Editor picker accepts .markdown.
• Main Screen preview recognition and command classification currently explicitly recognize .md, not .markdown.

No Markdown rendering engine, attributed Markdown parsing, WKWebView renderer, or dedicated Markdown preview exists.

4. Import, backup, persistence, and compatibility

Current Settings import UI is limited to:
• Import Screen(s)
• Restore Full Backup

See Set_Screen.swift lines 977-1027 and 1300-1325.

There is no standalone text or Markdown import route. plainTextImportType exists at lines 3713-3715 but has no current use.

Full backup behavior:
• Exports .txt resources under Text/:
   • Set_Screen.swift lines 5535-5539.
• Restores only .txt from the Text/ folder:
   • lines 4812-4835.

Therefore:
• A .md file is not currently retained through the supported full-backup restore workflow.
• A backup containing an MDs folder or a .md file under Text would be rejected as unsupported.
• Existing .screen, template, image, sound, PDF, and .txt workflows are unaffected unless archive classification is changed.

The current text selection is passed from ContentView:
• ESP32BLE/Scrns/ContentView.swift lines 2902-2930.
• settingsSelectedTextPath is @State, not @AppStorage, at ContentView line 214.

The active Settings category itself is persisted through settingsListMode. Selection state for images, sounds, and PDFs is separately persisted through AppStorage. A dedicated MD table should use its own selection and scroll state rather than overloading text state.

The Main Screen and Soft Editor already tolerate .md as a referenced filename. Adding Settings discovery does not require changing ESP32 firmware, ESPMacHelper, Sentinel, Recall, screen document formats, or saved screen resources.

5. Recommended implementation approach

Stage A — Menu-only structure

Update only:
• SettingsListMode in Set_Screen.swift
• visibleMenuModes
• labels for the new markdown case
• toggle(developerMode:), for consistency
• Settings table ListMode and its switch exhaustiveness

Use a stable raw case name such as markdown, with user-visible title MDs.

Do not rename existing category identifiers. Do not change existing text behavior.

Stage B — Dedicated MDs table behavior

Add a dedicated Markdown data flow, parallel to text:

• availableMarkdownURLs, filtered to exact .md.
• markdownURLs input for SettingsDocumentTableSection.
• .markdown table case.
• A dedicated Markdown row using the current text-row selection, filename copy, and swipe-to-delete conventions.
• selectedMarkdownSelectionPath.
• Dedicated Markdown scroll-position storage, for example settingsMDsScrollPositionID.
• Dedicated selected Markdown URL/title accessors.
• Update validation of remembered selections, editor loading, return-to-main save handling, item count, active row paths, and scroll restoration.

The current text table must remain .txt only.

For the requested scope, reuse the existing plain-text editor and raw UTF-8 file loading. Do not add Markdown rendering. This gives MDs the same selection and editing behavior as text while avoiding a separate preview architecture.

Stage C — Import/export and backup integration

Add an explicit ImportedContentKind.markdown, not merely a relaxed text filter.

Update:
• Full archive export to write Markdown files under a dedicated MDs/ folder.
• Full archive restore classification to accept only .md from that folder.
• Conflict tracking and first-import handling for Markdown.
• Delete-all routing.
• Any future standalone MD importer to use a Markdown UTType, rather than broadening .txt handling.

A separate MD category without this stage would allow files already present in Documents to be listed, but MD files would not survive the supported backup/restore process.

6. Regression risks

• Reordering only visibleMenuModes is low risk, but the dormant toggle order should match it.
• Reusing selectedTextSelectionPath for MDs risks clearing or cross-selecting rows because text and MD lists are different.
• Reusing availableTextURLs would violate the requirement that .txt remain in text and .md appear only in MDs.
• Merely allowing .md in archive Text would blur the category boundary and reduce future maintainability; use a separate archive folder/type.
• The current Main Screen preview shows raw Markdown source, not rendered Markdown. This is compatible with the request not to implement Markdown rendering.
• Existing backup archives must remain accepted unchanged. New MDs archive support should be additive, not require a format-version migration.
• Physical-device validation should cover iPhone and iPad category-menu order, MD selection/deletion, editor save on return to Main Screen, backup/restore, and unchanged .txt behavior.
