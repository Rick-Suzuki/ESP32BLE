A. Executive summary

Confirmed source facts:

• The iPad Help presentation is a SwiftUI sheet with only .presentationDetents([.large]).
• There are no explicit iPad Help width, height, minimum-size, maximum-size, GeometryReader, corner-radius, or presentation-background settings.

Recommendation:

For a future ESP-HELP-008C-2 stage, use an iPad-only fixed preferred sheet content size of 760 x 620 points and increase iPad HTML typography to body 1rem and h2 1.25rem.

C. Current iPad sheet width and height rules

Confirmed from Set_Screen.swift lines 607–621:

• Help is presented with .sheet when isPad is true.
• The only sheet sizing modifier is:

.presentationDetents([.large])

• .large requests the system’s large sheet height.
• No explicit width is specified.
• No explicit height is specified beyond the system large detent.
• No minimum or maximum dimensions are specified.
• No GeometryReader or proportional frame is used.
• No presentation corner radius, placement, background, or adaptation modifier is set.

The visible floating-window size is therefore platform-controlled.

Conclusion: additional sheet width and height should be made available to the topic content and WKWebView after the title, footer, spacing, and outer padding take their required space.

E. Expected behavior on different iPad sizes

Technical inference:

A single larger fixed preferred content size is more predictable than trying to derive a window size from screen dimensions. The existing sheet is system-managed, and the Help view has no current geometry-based sizing mechanism.

A 760 x 620-point preferred content size should:

• Be substantially more useful than a standard narrow form-style sheet.
• Leave meaningful surrounding space on landscape iPad mini, Air, and Pro devices.
• Keep the Help presentation recognizably floating rather than full screen.
• Provide a larger HTML reading region while retaining the existing footer.

The system may clamp a requested sheet size when necessary for the active scene, safe areas, multitasking, or future windowing modes. Physical-device testing remains required.

F. Recommended new window dimensions

Recommendation:

• Preferred width: 760 points
• Preferred height: 620 points
• Intended minimum surrounding visual margin: at least approximately 32 points where the system can provide it
• Reading-width target: approximately 700 points after native outer padding
• CSS maximum reading width remains 48rem, or approximately 768 CSS points

Why 760 x 620:

• It increases the useful reading area without approaching full-screen presentation.
• It stays near the existing CSS maximum content width rather than creating an overly wide text column.
• It accommodates the title, flexible WKWebView area, 44-point footer, 20-point stack spacing, and outer padding.

The exploratory “20% wider and 15% taller” target cannot be calculated precisely from source because the current sheet has no numeric dimensions. The current size is decided by the system.

Recommendation:

I. WebKit scaling considerations

Confirmed source facts:

• WKWebView uses no custom zoom, magnification, user agent, scroll-view inset, or text-scale configuration.
• The device-family script adds esp-ipad for .pad, lines 6045–6060.
• The HTML viewport is width=device-width, initial-scale=1, Help/connect-mac.html line 5.
• The base font remains -apple-system-body, Help/css/help.css line 28.
• Only esp-iphone has text-size-adjust: 100%, lines 59–62.

Technical inference:

Increasing the window width changes available line length and responsive main padding, but it does not directly increase the authored CSS font size. Increasing iPad font sizes must therefore be a separate CSS change.

Do not add iPad text-size-adjust preemptively. The iPhone rule addressed a demonstrated iPhone paragraph-autosizing problem. There is no source or device evidence that iPad currently has the same problem. The larger iPad font should be tested first without altering WebKit behavior.

L. Risks and uncertainties

• SwiftUI/iPadOS ultimately controls sheet dimensions and may clamp the requested frame for available space, safe areas, multitasking, or future windowing modes.
• The current source cannot provide the system-selected sheet’s actual width and height; device measurement is required.
• The 760 x 620 proposal is a preferred content size, not a guarantee that every iPad context displays exactly those dimensions.
• Larger iPad text may increase line wrapping and vertical scrolling, especially on iPad mini.
• No source evidence supports changing iPad WebKit text autosizing. Leave it untouched unless testing identifies a real issue.
