B. CURRENT SPECIAL KEYS FLOW

Special Keys are internally called the “escape code” table.

smartEscapeCodeRows contains a tuple per row:

• English display label
• command token
• help/description

Examples include .ESC, .RET, .BS, .SP, .TAB, colon, arrow keys, control shortcuts, and command shortcuts.

At Main_Screen.swift:3946-3951, each row currently does this in one Button action:

1. Calls insertSmartActionTextAtSelection(escapeCodeRow.command).
2. Assigns smartCommandDescription = escapeCodeRow.description.

The rows are plain SwiftUI Buttons created by smartCommandTableButton at lines 5508-5533. There is no onTapGesture, List/Table selection binding, UIKit recognizer, or persistent selected-row state.

Important current-source finding: the implementation does not retain a selected Special Keys row and does not render a selected-row highlight. The apparent selection is only ordinary Button press feedback.

G. SAFEST GESTURE DESIGN

Do not attach independent single-tap and double-tap insertion handlers. A simultaneous gesture can allow both recognizers to succeed and risks duplicate work.

Also do not leave the existing Button action as insertion while adding a double-tap gesture: the Button would insert on the first tap.

Smallest practical design:

1. Split current row behavior into two helpers:
   • Select/preview: update selected-row state and smartCommandDescription.
   • Insert/apply: call existing insertSmartActionTextAtSelection.

2. Keep the existing text-bearing SwiftUI Button for accessibility and visual structure.

3. Change the Button’s primary action to Select/Preview only.

4. Add a high-priority double-tap recognizer to that same Button for Select/Preview plus Insert/Apply exactly once.

The high-priority recognizer is appropriate because Apple documents that it takes precedence over the view’s existing gestures. The normal Button action can safely run during the first tap because it only selects and shows help; it performs no insertion.

This avoids arbitrary timers. The platform’s normal double-tap recognition interval is inherently required before a single tap can be conclusively distinguished from a double tap.

An alternative is:

TapGesture(count: 2).exclusively(before: TapGesture(count: 1))

This guarantees only one gesture succeeds, but requires replacing the standard Button with a custom tappable row and adds more accessibility work. The retained-Button approach is narrower and safer for this source.

Physical-device testing must confirm that the high-priority double recognizer fires once, that scrolling remains smooth, and that the Button action does not receive an insertion path.

I. ACCESSIBILITY

ACCESSIBILITY VERDICT FOR THE REQUESTED DOUBLE-TAP CHANGE: FAIL if implemented as a touch-only custom double-tap interaction without an accessible insertion action.

Current source status:

• PASS: Current table rows are text-bearing SwiftUI Buttons at lines 5508-5533. Their visible text provides an accessible label and Button trait.
• PASS: Special Keys and Widgets add each row description as an accessibility hint at lines 3951 and 3959.
• PASS: The table-mode icon button has an explicit accessible label at line 5505.

Risk:

VoiceOver’s normal double tap activates a control once; it is not equivalent to two direct physical taps recognized by TapGesture(count: 2). A touch-only double-tap insert implementation could leave VoiceOver users able to preview but unable to insert.

Required accessible alternative in the implementation stage:

• Keep rows as Buttons.
• Make default activation select/preview.
• Add .accessibilityAction(named: "Insert command") that calls the exact same Insert/Apply helper as the direct double tap.
• Add an accessibility hint explaining that activation previews and the Actions rotor contains “Insert command.”
• If selected-row styling is added, expose its selected state with .accessibilityAddTraits(.isSelected).

This keeps command insertion available to VoiceOver, Switch Control, Voice Control, and Full Keyboard Access without requiring inaccessible multi-tap timing.

K. REGRESSION RISKS

Primary risks:

• Duplicate insertion if a single-tap insertion closure remains active.
• A double tap may insert twice if separate tap recognizers are simultaneous rather than exclusive/preemptive.
• A generic change to smartCommandTableButton would affect F1...F20 as well as the two requested tables.
• Function Keys need a new help value; they presently do not set one.
• A new selected-row state can become stale across table-mode switches unless selection is cleared or mode-qualified.
• Changing insertSmartActionTextAtSelection would risk caret placement, command formatting, metadata preservation, and Undo/Redo. It should remain unchanged.
• Replacing standard Buttons with raw gestures would regress VoiceOver semantics unless explicit labels, Button trait, default action, and custom insertion action are supplied.
• Gesture changes must preserve vertical ScrollView drag behavior.
• Updating table-level help text is necessary to avoid a misleading “tap inserts” instruction.
