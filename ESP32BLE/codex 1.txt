3. Confirmed failure cause

Multi-page PDFs are explicitly rejected.

renderedSinglePagePDFPreviewImage requires:

• A valid PDFDocument.
• pdfDocument.pageCount == 1.
• A valid first page.
• Nonzero media-box dimensions.

The page-count condition is at Main_ButtonBehavior.swift􀰓.

For a multi-page PDF, rendering returns nil. The code then attempts UIImage(contentsOfFile:); that also fails because a PDF is not an image. ESP then sets:

• Title: Unsupported File
• Message: Couldn't preview <filename>.

This is application-generated at Main_ButtonBehavior.swift􀰓, not a framework error.

4. Page count involvement

Confirmed: a two-page or larger PDF will fail solely because pageCount == 1 is required.

Other possible causes that follow the same failure path:
• PDFDocument(url:) cannot load the file.
• The document has no accessible first page.
• The first page has zero media-box width or height.
• A malformed, encrypted, or permission-restricted PDF prevents page access.

There is no code checking PDF version, file size, embedded images, filename encoding, or page dimensions beyond the first-page media box.

5. File references and commands

Buttons store a filename command, not an absolute URL.

• Supported preview extensions: txt, md, pdf, png, jpg, jpeg, gif, heic, webp at Main_ButtonBehavior.swift􀰓.
• Resolution searches the app Documents directory first, then bundled resources, at 1912-1929.
• Matching is exact first, then case-insensitive among regular files, at 1931-1950.
• Spaces are retained because the filename is treated as one trimmed string; no command syntax change is needed.
• Renaming a PDF can invalidate an existing button filename reference because there is no persistent file identity mapping.

Settings resolves selected files independently through its Settings file collections; it does not share the Main Screen preview overlay.

6. Current PDF interaction and limits

Current single-page PDF behavior:
• First page is rasterized at its full media-box image size.
• The overlay aspect-fits and centers it.
• Pinch zoom has a minimum of 1x and no explicit maximum.
• One-finger pan is allowed only above 1x.
• Double tap resets the image transform.
• Closing dismisses the full-screen cover and returns to Main Screen.

There is no vertical page scrolling, page navigation, or access to later PDF pages. Multi-page content is not loaded into the overlay at all.

7. Difference from Settings

Settings uses an actual native PDFView in Set_ImgPanel.swift􀰓:
• .singlePageContinuous
• vertical display direction
• native pinch/pan
• min/max PDFKit scale factors
• first-page positioning with PDFDestination

Main Screen uses a rasterized first-page UIImage with custom gestures. The Settings component cannot be reused directly because it is private and has Settings-specific fitting/lifecycle behavior, but its PDFKit configuration pattern is appropriate.

9. Performance and compatibility

Using PDFKit avoids rasterizing every page into large images and is safer for multi-page/image-heavy PDFs. PDFKit performs native page rendering and supports continuous scrolling without an app-managed page cache.

Physical testing should cover:
• Large/image-heavy PDFs.
• Password-protected or malformed PDFs.
• Portrait, landscape, rotated, and mixed-size pages.
• iPad mini memory and responsiveness.
• Reopen after Close.
• Button references after PDF rename or deletion.

The confirmed fix is PDF preview routing plus a native PDFView branch; no programmable-button command change is needed.
