B. CURRENT X BUTTON BEHAVIOUR

There is one generic iPhone preview X button, not separate X buttons per category.

It is supplied by SettingsScreen.iPhoneImagePreviewCloseButton and displayed only in iPhoneImageEditorBody. It hides:

• PDF preview by setting isIPhonePDFPreviewPresented to false.
• IMAGE preview by setting isIPhoneImagePreviewPresented to false.
• Screens, Text, and Markdown editor preview by setting isIPhoneDocumentEditorPresented to false.

It does not clear:

• previewImageURL.
• selected PDF.
• selected screen/text/markdown file.
• persisted file selections.
• document editor contents.

The Sound player currently has no X button. It is displayed whenever Sounds is the active category.

The dedicated full editor’s xmark.circle.fill in Set_TxtEditor.swift is unrelated: it performs Save and Close and must not be included in this change.

C. ESP32/MAC BUTTON BEHAVIOUR

Both buttons call outputModeButton(_:) in SettingsAvailableDevicesPanel.

Current action:

• Plays existing click feedback.
• Calls selectOutputMode(_:) .
• Selecting ESP32 or Mac selects that output mode.
• Pressing the already-selected mode sets output mode to none.

Neither action currently changes preview visibility.

Safe implementation direction:

• Add an iPhone-preview-hide callback from SettingsScreen through SettingsBottomControlsSection to SettingsAvailableDevicesPanel.
• In outputModeButton(:) call the hide callback on every ESP32/Mac press, before or after selectOutputMode(:) .
• Do not place hiding inside selectOutputMode(_:) itself, because that method serves the existing connection-state semantics and is not iPhone-preview-specific.
• The callback must execute even when the tapped mode is already selected, because the request explicitly treats either button press as a preview-hide action.

D. PREVIEW CATEGORIES

Screens, Text, Markdown

• Share isIPhoneDocumentEditorPresented.
• Selecting a file loads it into the shared editor, then presents it on iPhone.
• Hiding does not unload or save/discard editor state by itself.

Images

• Uses isIPhoneImagePreviewPresented.
• Selecting/navigating an image presents the preview.
• previewImageURL remains selected when hidden.
• The applied Main Screen background restoration path is separate and should remain untouched.

PDFs

• Uses isIPhonePDFPreviewPresented.
• Selecting a PDF persists that selection and presents the preview.
• Hiding does not clear the selected PDF.

Sounds

• Has no independent iPhone visibility state today.
• isIPhoneSoundPlayerPresented is currently wired directly to isSoundsListActive at Set_Screen.swift line 2603.
• Therefore, it cannot currently be hidden while Sounds remains selected.
• A new non-persisted iPhone Sound visibility flag is required if the requested ESP32/Mac hide behavior must apply to Sound.

Templates

• No left-side iPhone preview panel is presented.
• Template selection only updates templateDescriptionState for the table-related description presentation.
• No preview X applies.

All Files

• Developer-oriented list mode; no dedicated iPhone preview visibility state or X applies.

E. PREVIEW VISIBILITY LIFECYCLE

Preview appearance:

• Image selection sets isIPhoneImagePreviewPresented true.
• PDF selection sets isIPhonePDFPreviewPresented true.
• Screen/Text/Markdown selection sets isIPhoneDocumentEditorPresented true.
• Sounds are visible merely by entering/remaining in Sounds.

Category changes:

• Leaving PDFs clears the PDF visibility flag.
• Leaving Screens/Text/Markdown clears the shared editor visibility flag.
• Leaving Images is also handled elsewhere through isImagesListActive checks.
• Leaving Sounds stops sound preview playback through selectSettingsListMode(_:), lines 1421–1429.

Settings return/reload:

• Settings onAppear starts image-preview restoration.
• Selected-document changes clear preview image/PDF visibility then begin image restoration.
• Image restoration can re-establish the preview image based on the applied background; it should not be changed in this work.

Visibility state is @State, not @AppStorage. It is not independently persisted.

F. SOUND PLAYER IMPLICATIONS

Hiding Sound requires special care.

If an added Sound visibility flag merely removes SettingsSoundPlayerView from the hierarchy:

• Its onDisappear cancels its background-image loading task and pending image request.
• Its AVAudioPlayer, progress task, selected sound, playback presentation, and completion handling remain owned by SettingsScreen.
• Audio can therefore continue while the Sound UI is hidden.
• Reopening recreates the view, restores its slider from shared playbackPresentation, and requests the current background image again.

This is the safest default for the requested hide-only behavior because it does not introduce audio teardown.

Do not call stopSoundPreviewPlayback() merely because ESP32 or Mac hides the panel. Existing source stops playback when leaving Sounds or leaving Settings, not when dismissing a preview panel.

Important reopening risk:

• Do not make low-level selectSound(_:) unconditionally re-present the Sound UI. That method is also used by Previous/Next and automatic track advancement; doing so could reopen a user-hidden Sound panel unexpectedly.
• Re-present Sound only on explicit table selection and, if desired, when entering Sounds to preserve today’s category-entry behavior.
