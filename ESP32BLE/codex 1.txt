3. Renderer comparison

Approach A — SwiftUI Text with AttributedString(markdown:)

Benefits:

• Native, offline, no WebKit memory cost.
• No network or local-image loading.
• AttributedString.MarkdownParsingOptions supports full Markdown interpretation.
• Strong fit for bold, italic, inline code, and basic links.
• Apple’s API has failure policies and defaults to disallowing extended attributes.

Limitations:

• Full Markdown parsing does not automatically create a polished document-layout renderer in SwiftUI.
• Headings, nested lists, blockquotes, horizontal rules, task lists, and tables need custom presentation logic to look consistently formatted.
• GitHub-style task-list checkboxes and pipe tables are not CommonMark core features.
• A visually correct table renderer and nested-list layout would require a custom block parser or substantial SwiftUI composition.
• Image-reference substitution would still need preprocessing.
• Link-opening policy must be explicitly controlled through the SwiftUI environment.

Conclusion:

• Good for lightweight inline formatting.
• Not sufficient on its own for all required presentation features without effectively writing a bespoke Markdown renderer.

Approach B — local HTML in a dedicated WKWebView

Benefits:

• CSS naturally handles headings, lists, task-checkbox presentation, horizontal rules, links, scrolling, wrapping, and basic responsive tables.
• The existing full-screen preview geometry and close control can remain unchanged.
• Markdown previews remain offline if HTML is generated in memory and no external assets are allowed.
• A dedicated navigation delegate can cancel all page navigation and resource loading.
• The required styling is concentrated in a short local CSS string rather than spread across custom SwiftUI block views.

Limitations:

• WKWebView itself does not parse Markdown.
• The project has no Markdown-to-HTML converter or third-party Markdown package.
• Without adding a package, ESP would need a deliberately limited local converter for the requested syntax.
• WebKit adds more memory overhead than native Text, though it is reasonable for a full-screen on-demand document preview.
• Raw HTML from Markdown must never be passed through unsanitized.

Conclusion:

• Best presentation platform for the requested feature set, but only when paired with a narrow, safe local Markdown-to-HTML converter.

Approach C — existing project support

Confirmed findings:

• No Markdown parser, CommonMark renderer, HTML converter, attributed Markdown use, or third-party Markdown library exists in current project source.
• Existing Help HTML files and WKWebView do not supply Markdown parsing.
• Existing NSAttributedString usage is for text-field placeholders, not document rendering.

4. Recommended approach

Recommend a dedicated, read-only local Markdown preview renderer using:

• a small Markdown-to-safe-HTML helper;
• a new local UIViewRepresentable WKWebView dedicated to Markdown preview;
• a new Markdown preview branch in the existing file preview overlay.

This is preferable because it can meet the required readable output with less custom layout code than a native block renderer:

• headings;
• bold and italic;
• ordered and unordered lists;
• visual read-only task-list checkboxes;
• horizontal rules;
• links;
• basic horizontally scrollable tables;
• responsive landscape layout;
• safe long-word wrapping.

No external package is required if the implementation is intentionally limited to the stated feature set. It should not claim full CommonMark or GitHub-Flavored Markdown compliance.

5. Image-reference filename substitution

This must occur before Markdown-to-HTML conversion.

Recommended behaviour:

• Scan Markdown source for image constructs beginning with ![.
• Parse the matching alt-text closing bracket and destination parentheses with an escape-aware, balanced-parenthesis scanner.
• Never resolve, load, inspect, or verify the referenced target.
• Extract only the final path segment from the image destination.
• Percent-decode the display filename when decoding succeeds.
• Escape the resulting filename as text.
• Emit a non-interactive filename label, not an <img> tag or link.

Examples:

• ![Image](Attachments/example.jpeg) becomes example.jpeg.
• ![Photo](example.png) becomes example.png.
• ![Image](/private/path/Photo%20One.PNG) becomes Photo One.PNG.

Handling details:

• Relative and absolute paths are treated only as strings.
• Directory segments are discarded.
• Uppercase extensions are preserved in the shown filename.
• Escaped parentheses and balanced parentheses must be supported in destinations.
• Multiple images are independently replaced.
• Malformed image syntax must remain escaped source text or harmless plain text; it must never trigger resource access.

A regex-only implementation is not recommended because Markdown destinations can contain escaped or nested parentheses. A small scanner is safer and easier to constrain.

6. Offline and security strategy

Recommended security boundary:

• Generate HTML only from escaped Markdown text.
• Do not allow raw HTML from the Markdown source.
• Do not generate <img>, <script>, <iframe>, <object>, <embed>, <video>, <audio>, stylesheet, or remote-resource tags.
• Disable JavaScript in the Markdown preview WKWebView configuration.
• Load HTML from an in-memory string with no Documents-directory base URL.
• Use a dedicated WKNavigationDelegate that cancels every navigation request.
• Do not allow file:, http:, https:, data:, or custom-scheme navigation from rendered content.
• Render links visibly, but keep them non-navigating in the first implementation.

This provides offline rendering and prevents:

• network image loading;
• remote resource loading;
• local file reads caused by relative image paths;
• embedded HTML or script execution;
• writes to the original document;
• arbitrary navigation outside the preview.

If later requirements need active links, that should be an explicit separate policy decision: intercept only explicit user taps and route valid https URLs through the system URL opener. It should not be added automatically.

8. Required feature support and limitations

Expected support with the recommended limited converter:

• Headings: supported.
• Bold: supported.
• Italic: supported.
• Ordered lists: supported.
• Unordered lists: supported.
• Read-only task lists: supported by detecting [ ], [x], and [X].
• Horizontal rules: supported.
• Links: supported visually; navigation cancelled for safety.
• Basic pipe tables: supported with horizontal overflow contained inside the preview.
• Image references: filename label only; no image access.
• Raw HTML: rendered as escaped text, never executed.
• Unsupported syntax: rendered as readable escaped/plain text where possible.

Features that should be explicitly out of scope for the first renderer:

• Full CommonMark or GitHub-Flavored Markdown compatibility.
• Syntax highlighting.
• HTML passthrough.
• Embedded media.
• Images or attachment lookup.
• Remote resources.
• Interactive task editing.
• Active in-app browser navigation.

9. Edge-case handling

• Empty document: show an unobtrusive blank document or “No Markdown content” message within the existing preview body.
• Invalid UTF-8: retain current unsupported-file handling; do not lossy-decode.
• Malformed Markdown: render safe readable text; do not fail the preview.
• Very large documents: conversion should occur once per preview presentation, not repeatedly during SwiftUI body updates. WebKit scrolling remains efficient.
• Long unbroken text: CSS should use overflow-wrap: anywhere and prevent horizontal page overflow.
• Unicode, emoji, and Japanese: preserve UTF-8 and use system typography; no conversion to ASCII.
• Repeated headings: preserve document order without generated anchors.
• Deep nested lists: cap indentation through CSS rather than attempting complex recovery.
• Image references in lists: replace with a filename label during preprocessing before list conversion.
• Many links: render as visual links while navigation remains blocked.
• Many checkboxes: render non-interactive visual checkbox glyphs or styled spans.

10. Compatibility and regression risks

Main risks:

• A simplistic Markdown parser can misinterpret nested emphasis, code spans, escaped delimiters, or unusual list indentation.
• Pipe tables require a deliberately limited parser and should degrade to paragraph text when malformed.
• Existing .txt preview must remain on the current monospaced SwiftUI path.
• The current preview state uses filename-plus-content; keeping that model avoids changes to command routing and file resolution.
• WebKit must be configured without a Documents base URL, otherwise relative Markdown references could access local files.
• Do not reuse the Help view directly because its read-access scope intentionally includes Help resources.
• Markdown preview must not alter existing image, PDF, sound, .screen, or command paths.
