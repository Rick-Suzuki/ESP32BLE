B. ROOT CAUSE

The current shared comparator sorts full filenames, not the base names shown for Screens.

For example, it compares:

• midi.screen
• midi chords.screen

The shared .screen suffix becomes significant when the shorter base name reaches its extension. Foundation therefore compares the space in midi chords.screen before the period in midi.screen, placing the longer name first.

This is why the displayed Screen name midi appears after the other MIDI screens. It is not a table-specific issue.

• midi sorts before Midi.
• localizedCaseInsensitiveCompare considers them equal.

D. DISPLAY NAME VS FULL FILENAME

Extensions are the direct cause for Screens because the table displays deletingPathExtension().lastPathComponent, while sorting uses lastPathComponent.

The same prefix anomaly can occur in any category whose files share an extension, including Text, Markdown, PDFs, Templates, Images, and Sounds. For most of those categories the extension is visible in the table, but the semantic filename prefix remains the base name.

G. MINIMAL CORRECTION

One focused change in naturalFileURLAscending is sufficient.

Recommended comparison sequence:

1. Compare deletingPathExtension().lastPathComponent first.
2. Use Foundation’s locale-aware numeric comparison with .caseInsensitive and .numeric options.
3. If base names compare equal, compare full lastPathComponent using the same primary options. This retains a meaningful order for distinct extensions.
4. Use literal full filename, then literal path, only as deterministic tie-breakers.

This preserves:
• Natural numeric ordering.
• Exact-prefix-first ordering.
• Case-insensitive primary behavior.
• Unicode/Japanese handling through Foundation and the current locale.
• Determinism through literal fallback.

The correction should remain exclusively in the existing shared comparator. No table, navigation, or storage redesign is needed.

H. SELECTION AND UI RISKS

Most selection state is identity-based and should remain intact when only ordering changes:

• Screens: standardized path selection and path-based scroll restoration.
• Text/Markdown: selected path.
• Templates: selected path.
• Images: selected path/name is primary.
• Sounds and PDFs: persisted path is primary.
• Table rows: ForEach identity is URL path.

Specific risk:
• Sound background image selection is primarily index-based through settingsSoundBackgroundImageIndex (Set_Screen.swift:2162–2191). A changed image order can map an existing index to a different background image. A focused implementation should preserve the currently resolved image URL and remap its index after sorting changes take effect, without altering opacity.

Secondary effect:
• Backup export entry order follows these sorted arrays. Archive content remains identical, but ZIP entry order may change.
• Import and restore do not rename or move files; refreshed tables simply adopt the corrected order.
