1. Actual discovery behavior

Verified facts:

• Mac-mode activation calls macConnection.start() from ContentView.swift:415-426.
• start() creates an NWBrowser for _esp-network-test._tcp at MacConnectionManager.swift:241-278.
• The browser’s browseResultsChangedHandler passes every new result set to updateDiscoveredHelpers at lines 270-275.
• The browser is intentionally kept alive after a TCP connection starts. connect(to:) at lines 470-493 does not cancel it.
• The browser is cancelled only by stop() at lines 374-385, restartSearch() at lines 511-523, or browser failure at lines 259-266.
• Every browse-result update replaces the published discoveredHelpers list at lines 301-322. Therefore, a later second service should update the SwiftUI list.

Important behavior:

• If no preferred helper is saved and the first browse update contains exactly one helper, lines 339-346 immediately call selectHelper(id:).
• selectHelper persists that helper as the preferred Bonjour identity at lines 281-298.
• It immediately starts TCP connection to that helper.
• This automatic choice does not wait for a subsequent Bonjour update that might contain the second Mac.

Conclusion:

Early automatic selection does occur. It is based on “the current result set contains one helper,” not “Bonjour discovery has completed.” Bonjour browsing is continuous and has no final result event.

3. Whether duplicate services are merged

Verified facts:

• The raw Set<NWBrowser.Result> is mapped to helper models at lines 301-304.
• The helper models are then reduced into Dictionary<String, DiscoveredMacHelper> at lines 305-307.
• Any helpers with the same constructed identity overwrite one another.
• Therefore only one item remains for duplicate keys.

This means two helpers will be merged if Network reports the same:

• service name
• type
• domain
• endpoint interface name
• discovered interface-name list

This is a real risk if both helpers advertise the same Bonjour instance name and Network does not expose a distinct interface value for them.

Apple’s Network documentation confirms that NWBrowser delivers a set of results and that each result includes an endpoint and interfaces. It also documents an advertised service’s optional automatic-renaming behavior during a service-name conflict. The ESP project does not inspect the helper’s advertisement configuration, so this probe cannot establish whether ESPMacHelper enables or disables automatic rename.

Hypothesis:

The two archived helpers may both advertise “ESP Mac Helper.” If Bonjour automatically renames one, ESP should receive distinct service names and show two rows. If the helpers publish indistinguishable service registrations, or Network presents them as one result, this implementation merges them into one row.

4. Whether early automatic selection occurs

Verified fact:

Yes.

When the first browse update has one helper and there is no stored preferred identity:

• updateDiscoveredHelpers() calls connectToSelectedHelperIfPossible() at line 322.
• lines 339-346 select and persist the sole currently discovered helper.
• selectHelper() begins TCP connection at line 298.

This means an M1 result arriving before the M4 result causes M1 to become the saved preferred helper before M4 is considered.

After that, later discovery of M4 should still be retained and shown if it produces a distinct identity. The connection itself does not block the browser or suppress list updates.

5. Exact chooser visibility conditions

Its entire body is hidden unless:

• discoveredHelpers.count > 1, or

6. Explanation of “iPad: Searching” versus “M1: Connecting”

Verified facts:

The iPad text is not a direct presentation of connection status.

Set_AvailableDevices.swift:465-473 displays:

• “Mac: Connected” only when macConnection.canSend is true.
• Otherwise “Mac: Searching...”.

canSend requires both:

• status == .connected
• isAuthenticated == true

This is defined at MacConnectionManager.swift:223-225.

Therefore the iPad can show “Mac: Searching...” while:

• a TCP connection is being attempted,
• TCP is ready but authentication has not completed,
• pairing is required,
• authentication failed,
• the helper has accepted a socket but ESP has not yet become authenticated.

The M1 helper showing “Connecting” is consistent with ESP having automatically selected M1 and opened a TCP connection. It does not prove that ESP has authenticated successfully.

Authentication mismatch is likely relevant to the “Searching” text, but does not by itself explain why M4 is absent from the chooser.

7. Forget Mac Helper behavior

Verified fact:

forgetPairedMacHelper() removes only Keychain pairing material at MacConnectionManager.swift:397-405.

It does not remove:

• selectedHelperID in memory
• ESP.PreferredMacHelperBonjourIdentity from UserDefaults

On the next Mac-mode start, start() reloads that saved Bonjour preference at line 245.

Therefore, pressing Forget Mac Helper does not cause ESP to choose another Mac. It can still reconnect automatically to the M1 Bonjour service, but without its old pairing credentials. This directly explains why Forget does not change the observed target.

9. Most likely root cause

Most likely combined cause:

1. M1 is discovered first.
2. ESP immediately auto-selects and persists M1 because the first browse update temporarily contains one result.
3. Pressing Forget removes pairing credentials but leaves the M1 Bonjour preference intact.
4. Re-entering Mac mode therefore targets M1 again.
5. M4 does not appear because either:
   • it is not reaching NWBrowser as a distinct result, or
   • both results are being merged by the identity dictionary.

The physical result is especially consistent with the saved M1 Bonjour selection remaining after Forget.

The current diagnostics cannot distinguish the final two alternatives. Device logs are needed before changing behavior.

10. Recommended narrowly scoped correction

Recommended behavior:

• Keep automatic reconnection only for a previously remembered Bonjour selection.
• Do not persist the first temporarily sole discovery result as the user’s new preferred Mac.
• Provide an explicit “Choose Mac” control while in Mac mode, including when the currently saved Mac is connected.
• Keep the chooser open/dynamic while Bonjour updates arrive.
• Include the connected helper in that chooser.
• Selecting another helper must cancel the old connection before opening the new one; current selectHelper() already does this at lines 292-298.
• Preserve the existing one-pairing Keychain model.
• Keep current explicit pairing behavior for a newly selected helper.
• Decide whether “Forget Mac Helper” should remain pairing-only or whether a separate user-authorized “Forget Selected Mac” action should remove the Bonjour preference. Do not make pairing removal silently alter selection.

Minimum implementation work after diagnostics confirm the actual result set:

• Change lines 339-346 so an unpreferred sole first discovery does not immediately become the persisted selection.
• Add an explicit chooser-entry state/control.
• Improve helper identity handling and collision visibility only if device logs prove two raw Bonjour results are being collapsed.
• Keep use of service name/type/domain as a discovery preference only; continue treating the authenticated helper ID as the authoritative pairing identity.

Required physical-device tests after a narrow correction:

1. No saved preferred Mac, both helpers running: chooser lists M1 and M4.
2. No saved preferred Mac, one helper running: intended single-helper behavior is explicit and predictable.
3. Saved M1 preference, both helpers running: normal reconnect selects M1.
4. Open chooser while connected to M1: both M1 and M4 appear, with M1 marked selected.
5. Select M4: M1 socket disconnects before M4 connection starts.
6. M4 has different pairing identity: pairing-required status appears without erasing M1 credentials.
7. Explicitly pair M4: one saved pairing is replaced only after approval.
8. Forget pairing: confirm the documented selection behavior remains unchanged unless a separate explicit selection-forget action is used.
9. Same advertised helper names: confirm raw-result, mapped-result, and deduplicated-result logs identify whether Bonjour or ESP identity handling is collapsing the helpers.
