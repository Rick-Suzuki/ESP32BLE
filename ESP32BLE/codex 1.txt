B. DIMENSION CONVENTION

The user-facing/Main Screen convention is columns × rows.

A 3×4 grid means:

• 3 columns across.
• 4 rows down.
• 12 positions.

This is confirmed by:

• GridDimensions being declared as (columns, rows).
• Main Screen width calculation using columns.
• Main Screen height calculation using rows.
• Existing grid-control APIs accepting columns before rows.

Important inconsistency: ScreenConfig.Grid stores and initializes fields as rows, columns, and current Template validation errors interpolate rows x columns. The new warning must not reuse that ordering for display. It should explicitly format:

\(grid.columns)×\(grid.rows)

Thus, for three columns and four rows, display 3×4, regardless of storage property order.

C. TEMPLATE EDITING SESSION

TemplateEditingSession currently stores:

• Template URL.
• Original Template bytes.
• Original configuration bytes.
• Original Template text.
• Original description.
• Mutable Template text draft.
• Mutable description draft.
• Saved-state flag.

It does not store a decoded ScreenConfig or a proposed grid.

Safest approach:

• Keep the persisted configuration unchanged while the warning is presented.
• Add transient, non-persisted pending-expansion state, for example a pending choice containing:
   • effective button count,
   • original columns and rows,
   • valid row-expansion candidate, if any,
   • valid column-expansion candidate, if any.
• Do not mutate TemplateEditingSession merely to display the warning.
• On a chosen action, pass the selected candidate grid directly into the existing paired-file save transaction.

The original byte snapshots already provide stale-session protection. If the Template or config changes while the warning is open, the existing save helper should reject it as stale.

D. SAVE ARCHITECTURE

updateTemplateDocument(...) is the correct single save path to extend.

It currently:

1. Confirms valid regular Template/configuration files.
2. Reads both current files.
3. Verifies both match the edit session’s original snapshots.
4. Decodes the current TemplateConfiguration.
5. Counts effective button lines.
6. Validates current grid capacity.
7. Encodes staged Template and config replacements.
8. Verifies staged files.
9. Backs up both originals.
10. Replaces both files.
11. Verifies the result.
12. Restores both originals if publication fails.

Recommended focused extension:

• Add an optional proposed grid argument to updateTemplateDocument(...).
• Decode the existing configuration as today.
• Copy its ScreenConfig.
• Replace only its grid with the user-selected candidate.
• Validate the candidate grid using the existing strict checks.
• Build the updated TemplateConfiguration from that copied ScreenConfig and existing description logic.
• Keep all staging, backup, replacement, verification, and rollback unchanged.

This writes edited Template contents, description, and resized configuration as one paired transaction. No separate configuration write is appropriate.

E. GRID EXPANSION CALCULATIONS

For a current grid of:

• columns = C
• rows = R
• effective button count = B

Current capacity is:

C × R

Increase Rows:

requiredRows = ceil(B / C)

Candidate grid:

C columns × requiredRows rows

Example:

• Current: 3×4
• Buttons: 13
• Required rows: ceil(13 / 3) = 5
• Result: 3×5, capacity 15.

Increase Columns:

requiredColumns = ceil(B / R)

Candidate grid:

requiredColumns columns × R rows

Example:

• Current: 3×4
• Buttons: 13
• Required columns: ceil(13 / 4) = 4
• Result: 4×4, capacity 16.

The implementation should use integer ceiling division and retain the original unchanged dimension. It must never reduce either dimension.

F. LIMIT HANDLING

Use existing global limits:

• Maximum dimension: 50.
• Maximum capacity: 2500.

A row candidate is valid only when:

• requiredRows <= 50
• currentColumns × requiredRows <= 2500

A column candidate is valid only when:

• requiredColumns <= 50
• requiredColumns × currentRows <= 2500

Important current-source finding: Template create, edit, and application validation currently enforce positive dimensions and capacity no greater than 2500, but do not independently enforce that each dimension is no greater than 50. Main Screen controls do enforce the per-dimension limit.

The new expansion calculation should enforce both limits even if the existing Template was created externally with an unusual valid-by-capacity dimension.

If one direction is invalid:

• Keep that action visibly unavailable/disabled, or omit it and clearly state why in the message.
• Keep the valid direction available.

If neither direction is valid:

• Do not offer a save that violates limits.
• Show an existing-style error alert, for example:
“The template has 2100 buttons. Neither rows nor columns can be increased independently within the 50×50 grid limit.”
• Keep both drafts open and unchanged.

Example where neither single-direction action is possible:

• Existing grid: 40×40.
• Buttons: 2100.
• Required rows with 40 columns: 53, invalid.
• Required columns with 40 rows: 53, invalid.
• A combined 50×50 expansion could fit, but it is outside the requested explicit one-direction choices.

G. CONFIGURATION PRESERVATION

ScreenConfig currently contains only global screen settings:

• schemaVersion
• fontSize
• grid
• backgroundImageName
• backgroundOpacity
• buttonsBackgroundOpacity

There are no per-button configuration arrays or positional metadata in ScreenConfig.

Therefore, the safe operation is:

• Copy the decoded existing ScreenConfig.
• Change only grid.rows or grid.columns.
• Preserve all other known configuration values and Template description.

Button definitions reside in the Template text. Increasing rows keeps the existing row-major slot positions stable. Increasing columns reflows later button indices into different visual row positions; this is expected and is precisely why the user must choose the direction.

Risk to note: the current Codable schema does not preserve unknown future JSON keys when it re-encodes a configuration. This is pre-existing behavior. For the current known schema, copying and mutating only .grid preserves all supported fields.

H. UI WARNING

Recommended presentation: an existing SwiftUI .alert, attached at the same Settings presentation level as the current document-save and import alerts.

Use a typed pending-expansion item/state rather than loose text state. This makes the displayed values stable while the alert is visible.

Suggested alert:

Title:
Template Grid Too Small

Message:
This template contains 13 buttons, but its 3×4 grid supports only 12.

You can increase the rows or columns to accommodate the additional buttons.

Actions:

• Increase Rows
• Increase Columns
• Cancel, with .cancel role

Use the exact calculated values and columns × rows display convention.

Why .alert is preferable:

• The project already uses it for multi-action confirmation.
• It is shared by iPhone and iPad.
• It blocks accidental editor interaction while the decision is pending.
• It avoids new custom geometry, popovers, overlays, or platform-specific UI.
• System alerts accommodate the active software keyboard without changing editor layout.

Apple’s SwiftUI alert behavior may reorder actions by role. The two expansion actions should have no destructive role; Cancel should use the cancel role.

I. CANCEL AND FAILURE HANDLING

Cancel:

• Clear only the pending expansion state.
• Keep TemplateEditingSession, Template draft, description draft, focus state, and editor presentation unchanged.
• Do not invoke updateTemplateDocument(...).
• Do not dismiss the editor.
• Do not write either paired file.

Expansion action:

1. Capture the proposed candidate grid.
2. Run the existing paired save with that candidate.
3. On success, refresh the selected Template and call the existing dismissal path once.
4. On failure, retain the editor and both drafts, then show the existing save error.

The current closeDedicatedTemplateEditor() already only dismisses after a successful saveTemplateEditingSession(). The expansion action can reuse this success-only dismissal behavior.

Keyboard handling:

• Do not resign focus before showing the warning; that would be an unnecessary draft/UI change.
• The system alert handles presentation above the keyboard.
• On Cancel, the editor remains present. Physical testing should confirm the desired text field remains usable; no focus-reset logic is required unless device testing identifies an issue.
• On success, the existing dismissal path already resigns first responder and clears editor-focus state.

J. TEMPLATE APPLICATION

The Template application path already reads the Template’s paired TemplateConfiguration, validates its grid against button count, and writes the entire screenConfig to the target Screen.

After a successful expanded-grid save:

• The Template’s new grid is persisted in .template.config.json.
• Application validates against the new grid.
• Application writes the new dimensions and all other preserved ScreenConfig values to the target Screen.
• No Template application change is required.
